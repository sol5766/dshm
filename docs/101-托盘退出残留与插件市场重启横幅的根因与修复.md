# 101 · 托盘退出残留 + 插件市场「一项变更需重启」——两个报障的根因与修复

> 2026-10-06。两个报障一起修：
> **① 插件市场一直挂着一条「1 项变更需重启 DeepSeek Harness 后生效」，重启多少遍都不消**；
> **② 顶栏托盘区的应用图标在应用退出后仍然留着**（用户原话：「右键退出功能执行后，有概率还在」）。
>
> 两条都是**判定错**、不是功能缺失：
> ① 市场把 home 层的一行 `disabled` 读成了「进了 bundle 层但本次没热挂载 ⇒ 重启就生效」；
> ② 摘图标的三条路径同时失效，其中一条还会让**下一次启动**被上一次留下的停止请求当场关停。

## 0. 一页结论

## 1. Bug A：市场横幅「1 项变更需重启 DeepSeek Harness 后生效」

### 1.1 现象与读数

- 市场横幅判据（`client/MarketSection.tsx`）：`activations[*].state === 'restart'` 且本次 boot 未 dismiss ⇒ `restartBanner`。
  dismiss 只写在 `sessionStorage['dshm-restart-dismissed']`，**只对同一个 `status.boot` 有效** ⇒ 重启必再现。
- 修复前 `/dsh-market/installed` 里**唯一**一条 restart 就是它：
  `@smalltailqwq/dsh-client-ui-skin-orca-link => restart`。
- `/dsh-market/check` 里对应这条 override：
  `{"id":"ui-skin-orca-link","layer":"home-patch","overriddenLayers":["@smalltailqwq/dsh-client-ui-skin-orca-link"]}`。

### 1.2 根因（三层，缺一不可）

1. **bundle 层**：orca-link 插件自己的 patch 文件往 profile 里插了一行 `id: ui-skin-orca-link`。
2. **home 层覆盖**：`$DSH_HOME/cordis.patch.yml` 末尾由 dsh-skin 自动生成的互斥块**写了同一个 id**：

   ```yaml
   # --- dsh-skin managed (auto-generated; do not edit) ---
   - id: ui-skin-denia
     disabled: true
   - id: ui-skin-orca-link
     disabled: true      # ← 修复前；它把 bundle 层那一行覆盖成 disabled
   # --- end dsh-skin managed ---
   ```

   于是加载器**不加载 orca-link 客户端**。
3. **市场不读 home 层**（`dist/plugsrc/dshmarket-1.66.8/package/src/verify.ts`）：

   - `const loaderLive = liveIncludes(live, name) || carriedRowLive(...)`（第 339 行）——「本次是否真的挂上来了」；
   - `if (inBundles) { ... return { state: 'restart', reasons: ['已进入 profile bundle 层但本次未能热挂载；重启后生效'] } }`（第 423 行附近）。

   ⇒ 被 home 层禁掉的 bundle 行，与「还没热挂载」在这套判据下**完全同形** ⇒ 判 `restart`。
   而 home 层那一行**市场从来不读** ⇒ 那条真正的病根**永远查不到** ⇒ 重启 N 次横幅照样在。

**为什么 home 层会被写成 `disabled: true`**：skin-manager 的 `ensureSafeInitialState`——皮肤目录 ≥2 个且启用 ≥2 个时，
强制 `useSkin('official')`，把 home 行改写成 disabled；但皮肤市场自己的 `disabledSkinIds` 仍留着。
设备取证：`.dsh-skin-market/state.json` 里 `activeSkinId=None`，而 `activity["small-tailqwq.orca-link"].usedAt = 2026-10-03T04:21:28Z`
⇒ 用户**确实用过并倾向 orca-link**。

### 1.3 A/B 决定性证据

| home 层该行取值 | `/dsh-market/installed` | 市场 UI |
|---|---|---|
| `disabled: true`（用户当时的状态） | `@smalltailqwq/dsh-client-ui-skin-orca-link => restart`（全表唯一 restart） | 出现「1 项变更需重启」横幅 |
| `disabled: false` | `=> live` | 横幅消失 |

### 1.4 修复与留档

设备侧**只改这一个值**（`dsh/home/cordis.patch.yml`，3048 B，`sha256 4bda58ecd5712dab…`），并留三份备份：

| 位置 | 内容 |
|---|---|
| `files/dshm-diag/cordis.patch.yml.bak-20261006` | 3047 B，**修复前**（`disabled: true`） |
| `files/dshm-diag/cordis.patch.yml.bak-false-20261006` | 3048 B，**修复后**（`disabled: false`） |
| `dist/backup/cordis.patch.yml.orig-20261006` | 宿主留档（同上修复前版本） |

⇒ 最终有效配置：`ui-skin-denia disabled: true`（denia 的 bundle 没装，属孤儿行）+ `ui-skin-orca-link disabled: false`。
修复后复核：`restart` 状态 **0** 条、`search: orca-link => live`。

### 1.5 顺带确认为噪音、不是问题的三条

- `/dsh-market/check` 里 7 条 `@deepseek-ai/dshm-* is not installed in the profile — the profile will fail to boot`：
  这 7 个包都在核心树 `node_modules/@deepseek-ai/` 下，loader 走 install anchor 解析 ⇒ **市场误报**（逐个 `Test-Path` 为 True）。
- `ui-skin-denia` 在 `orphans` 里：denia 的 bundle 没装，孤儿行，无横幅影响（判 `disabled` 而非 `restart`）。
- **dismiss 不持久**（只写 sessionStorage）⇒ 即便点了 ×，重启还回来；这不是 bug 而是设计，别拿它当解法。

### 1.6 根治建议（留给上游）

市场 `verifyActivation()` 应把「home/patch 层显式 `disabled: true`」判成 `disabled`（或至少叠加一层 override 提示），
而不是与「未热挂载」同判 `restart`；skin-manager 也不该写出一条与 bundle 行同 id 的 home 行。
本仓侧只做最小止血（改值），不动市场/皮肤管理器的上游实现。

## 2. Bug B：托盘图标在退出后残留

### 2.1 三条叠加根因

1. `BG_TERMINATING` 分支先 `markUnavailable()`（清零 `installed`），紧随其后的 `remove()` 首行 `if(!installed) return`
   ⇒ 这条路径上**一次 `removeFromStatusBar` 都没发出去**。
2. `exitApp()` 把 `remove()` 排在 `await stopHostThenExit()` **之后** ⇒ 停核心是不定长等待，等它回来窗口往往已经不在了；
   而 SDK 对 `removeFromStatusBar` 有硬前置：**无前台窗口时不可删除（`1010710004`）**。
3. 系统发起的退出（窗口右上角「关闭」/ 任务栏右键「退出」/ 托盘右键「退出」）**不经过 `exitApp`**，
   而 10-05 的两次提交分别删掉了 `onPrepareToTerminate` 收尾（`ab996b8`）与 onDestroy 兜底（`5b7d47d`）
   ⇒ 这两条路径**同时没有收尾**。

`installed` 留在 `true` 的后果是：下一次 `install()` 会因幂等早退而**永不再尝试清理** —— 这正是
「概率性残留、重启若干次都还在」的形态（概率来自「主进程被结束」与「后台 Ability 终止事件被处理」的先后）。

### 2.2 第四处、也是最隐蔽的一处：残留的 `host-stop-request` 让**下一次启动**自杀

宿主（`hostcore/app/main.js`）的停止通道是**1.5 s 轮询**看 `$DSH_HOME/host-stop-request`，看到就 `process.exit(0)`。
应用退出是「同步写下请求 → 进程被系统结束」，宿主常常来不及在 1.5 s 内消费掉它。真机实测：

```
02:32:59.930  写 host-stop-request（EntryAbility.stopHostThenExit：应用退出流程）
02:33:39.806  下一次启动的宿主读到它 ⇒ 收到停止请求（host-stop-request 文件：1791253979930）
02:33:39.8xx  !! process.exit(0)：停止路径放行
```

⇒ 表现为「应用刚起来核心就没了、而且没有任何报错」。本轮的退出路径把 `remove` 提到最前、并 `return false` 立即终止
（不给异步收尾留时间），**会让这个环节概率变高** ⇒ 必须清残留。

### 2.3 修复（三处源码）

| 文件 | 改动 |
|---|---|
| `entry/src/main/ets/system/StatusBarTray.ets` | `remove()` **成败都归零 `installed`**（失败时记 `remove failed：…1010710004…`，并靠下次启动的 pre-clean 捞回来）；删除已被替代的 `markUnavailable()`；新增 `diag()` —— 托盘事件追加到 `filesDir/diag-tray`（本机 `hilog` 读不到本应用 ArkTS 输出，概率性故障必须有文件台账） |
| `entry/src/main/ets/entryability/EntryAbility.ets` | 新增 `onPrepareToTerminate(): boolean`；抽出 `finalizeBeforeExit(reason)`：**先 `StatusBarTray.remove()` → 再 `publishExitRequest()` → 最后 `stopHostThenExit()`**（顺序是核心）；`exitApp()` 改走它 |
| `hostruntime/src/main/ets/runtime/DshHost.ets` | `start()` 里先 `clearStaleStopRequest()`：起核心前删掉残留的 `host-stop-request`（只可能是上一次生命写的；留着等于让本次启动自杀） |

### 2.4 为什么挂在 `onPrepareToTerminate`（SDK 判据）

`@ohos.app.ability.UIAbility.d.ts` 原文：

> Triggered by the system just before the UIAbility is about to close (for example, when the user clicks the close button
> in the top-right corner of the application window **or exits from the dock or system tray**) …
> This API executes the callback normally only on 2-in-1 devices and tablets.

且明确两条「不执行」的前置条件——**本工程都不满足**：

- 未实现 `UIAbility.onPrepareToTerminateAsync`；
- 未实现 `AbilityStage.onPrepareTermination(Async)`（SDK 特别注明：实现了它，**右键 dock/托盘关闭时本回调不执行**）；
- 未注册 `window.WindowStage.on('windowStageClose')`（两者只能选一条）。
- 权限 `ohos.permission.PREPARE_APP_TERMINATE` 已在 `entry/src/main/module.json5` 声明。

**`return false` = 不拦截 = 鸿蒙默认退出语义**：这个钩子只用来补收尾，不改变「关闭就是退出」这件事。

### 2.6 仍然存在的边界（诚实登记）

- 系统**直接结束进程**的那类退出（`force-stop`、OOM、崩溃）不走任何回调 ⇒ 图标只能靠**下一次启动的 pre-clean**清理；
  即「不重启应用就一直留着」在这一类下依然成立（这是平台约束，不是本仓能补的）。
- 摘图标依赖「回调触发时仍有前台窗口」。`onPrepareToTerminate` 的语义保证此时窗口还在（窗口销毁**之前**），
  所以正常路径成立；若哪天又出现 `remove failed：…1010710004…`，说明有人把 `remove` 挪到了窗口销毁之后。
