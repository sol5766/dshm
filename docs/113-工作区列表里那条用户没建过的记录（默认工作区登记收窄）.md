# 113 · 工作区列表里那条「用户没建过的 `com.dshm.dshclient`」：根因与收窄

> **触发**：用户报「现在多出一个工作区 `com.dshm.dshclient`，不是我手动创建的，并且三端都有这个，
> 如果是测试的可以清除掉，**不要替用户做选择**，也不要随便加一些无关紧要的东西在里面」。
> **结论**：不是测试产物，是**我们自己**的自带插件 `dshm-workspace-claim` 写的 —— 它原来**每次启动**
> 都往工作区注册表里登记一条 `Download/<包名>/`。本文件记根因、取证、收窄后的纪律与验证。
> **核心树**：`0.2.1-alpha.1+dshm.13`。

## 1. 真机取证（先摆事实，再讲道理）

设备上的工作区注册表 `$DSH_HOME/storages/workspace.json`（经应用自身 Python 桥读出，**原文**）：

```json
{
  "global": { "initialized": true, "workspaceIds": [
      "68bdc566-4958-47c8-9ab3-1e407738d0fa",
      "efdcd677-0a5b-4802-8230-fc208046254d"
  ] },
  "tables": { "workspaces": {
      "efdcd677-…": { "path": "/storage/Users/currentUser/harness",
                      "title": "harness", "sessionIds": [ 8 条 ],
                      "createdAt": "2026-09-25T09:13:19.704Z" },
      "68bdc566-…": { "path": "/storage/Users/currentUser/Download/com.dshm.dshclient",
                      "title": "com.dshm.dshclient", "sessionIds": [],
                      "createdAt": "2026-10-03T09:48:26.464Z" }
  } }
}
```

两条记录并列：`harness` 是**用户的**（8 个会话，2026-09-25 建的）；`com.dshm.dshclient` **0 会话**。

## 2. 根因：自带插件「每次启动都登记」

- 写它的是 `hostcore/plugins/dshm-workspace-claim/lib/index.js`（2026-10-03 随 `570cc2a` 引入，见 `docs/95` §2.3、`docs/103`、`docs/105`）。
  它把 ArkTS 认领到的 `Download/<包名>/`（env `DSHM_PUBLIC_DOWNLOAD`）经官方 API 写进注册表 —— 原实现是
  `Promise.resolve().then(() => ctx.workspaceRegistry.create(target))`，**每次启动都调**（`create()` 幂等：
  路径已登记时只解析、不新增行，所以只留一条，但那条**永远在**）。
- **不是**用户在 UI 里选出来的：`createdAt = 2026-10-03T09:48:26.464Z`，而同一份 `dshm-host.log` 里
  那一次启动是 `2026-10-03T09:48:22.433Z` 的 `--- boot pid=31232` —— 相隔 **4.03 秒**，且 WebView 直到
  `09:48:27.618` 才第一次连上（`IN-UPGRADE /api/remote.mux`）。UI 目录选择器需要界面，先排除。
- **三端都有**：这条链与设备形态无关（PC / 手机 / 平板都设 `DSHM_PUBLIC_DOWNLOAD`），凡是启动过一次就有一条。

## 3. 它当初为什么被这么写，以及那一手为什么是净噪声

两条上游路都堵死（`dsh-workspace/lib/index.js:423-443` 的 `initializeDefault()` 要求「注册表空 + 归档集空 + 会话历史空」，
且其目录来源 `dsh-api-workspace-controller` 的 `defaultWorkspaceDirectory()` 在 linux 分支要 `xdg-user-dir`，沙箱里必失败并**抛错**），
所以需要一个「启动期把注册表弄成非空」的动作 —— 这一点**现在仍然成立**，插件保留。

但「每次启动都登记」这一半是多余的：`cordis.patch.yml` ⑨ 的 **43 号修正（2026-10-03 真机实证）** 已经写明，
官方 Web UI 的落点顺序是 `workspaceId ?? currentWorkspaceId ?? recent`，其中 `currentWorkspaceId` 是
**当前主视图那条会话所属的工作区**；设备上恒有旧会话被恢复 ⇒ **只登记不足以决定新会话落点**。
于是这一手的唯一可见效果，就是注册表里多一条用户没建过的记录。

## 4. 收窄后的纪律（4 条，都在插件里）

| # | 规则 | 判据 |
|---|---|---|
| ① | **注册表非空 ⇒ 一条都不加** | `registry.list().length > 0` 直接返回；只在**注册表为空**（全新安装）时 `create()` 一次 |
| ② | **只撤自己那一条** | 命中条件 = 记录的 `path` 与认领目录同源（末两段 `Download/<包名>` 相同，兼容 realpath 前缀差）**且** 该记录 `sessionIds.length === 0` |
| ③ | **撤完必须仍非空** | `emptyMine.length >= list.length` 时不撤 —— 注册表变空会把 `initializeDefault()` 的短路条件弄丢（回到 §3 那个必失败分支） |
| ④ | **读不到就什么都不做（fail-closed）** | `registry.list()` 非数组/抛错 ⇒ 不新增也不撤回，只打一行日志 |

另：登记时**显式给标题** `DEFAULT_TITLE = "下载"` —— 不让它退化成目录末段（那是包名，在列表里像一条垃圾记录）。
`create(path, title)` 的 title 只在新纪录那一刻生效，用户之后可在 UI 里自行改名。

「只删注册表一行」是刻意的：`workspaceRegistry.delete(id)` 的官方语义就是「删登记，保留目录与所有会话日志」
（`dsh-workspace/lib/index.js:459-469`）—— 本插件**不删目录、不删文件、不碰会话**。

## 5. 验证

### 5.1 离线判据（新增门禁 `tools/check-workspace-claim.mjs`）

用**假注册表**直接驱动真模块（`apply()` 的入参只有 `ctx.workspaceRegistry`），断言「该不该调、调什么」：

| 场景 | 期望 |
|---|---|
| 用户 1 条 + 我们那条 0 会话 | `delete(我们那条)` |
| 只有用户 1 条 | 无调用 |
| 只有我们那一条（0 会话） | 无调用（不能把注册表弄空） |
| 注册表为空 | `create(target, "下载")` |
| 我们那条有会话 | 无调用（用户在用它） |
| 记录 path 前缀被 realpath 解析过 | 仍 `delete` |
| 两条都是我们的、都 0 会话 | 无调用（撤完为空） |
| 我们那条 0 会话 + 用户 2 条 | `delete(我们那条)` |
| `DSHM_PUBLIC_DOWNLOAD` 为空 | 完全惰性 |
| `registry.list()` 抛错 | 无调用、不抛（fail-closed） |

### 5.2 真机（鸿蒙 PC，核心 `0.2.1-alpha.1+dshm.13`）

`+dshm.13` 覆盖安装 + 冷启动：`dsh/home` 指纹 `links=13 size=3440` **前后一字不变**（会话 / 插件 / 核心树全在），
`exec 探测 10/10 全通`，端侧核心树切到 `0.2.1-alpha.1+dshm.13`；`tools/device-code-fingerprint.ps1` 设备树 ↔ 本机树
**5/5 逐字节一致**（设备跑的就是本机这份代码），`tools/device-acceptance.ps1` 自动判定 **5/5 PASS**。

**两次启动各留一条原始日志行**（设备侧 `$filesDir/node-output.log`，每次启动轮转；原文照抄）：

| 时机 | 原始行 |
|---|---|
| 覆盖安装后**首启** `2026-10-07T03:52:51.493Z` | `[dshm-workspace-claim] 已撤回本插件早先登记的一条：/storage/Users/currentUser/Download/com.dshm.dshclient（0 会话；只删注册表这一行，目录与任何会话日志都未动）` |
| **再次启动** `2026-10-07T04:05:03.258Z` | `[dshm-workspace-claim] 注册表里已有 1 条工作区 ⇒ 本次不新增（本插件只在注册表为空时登记一次）` |

**事后读注册表**（经应用自身 Python 桥，`$DSH_HOME/storages/workspace.json` 原文）：`workspaceIds` **只剩 1 条** ——
用户自己的 `harness`（`path=/storage/Users/currentUser/harness`、8 个 `sessionIds`、`createdAt=2026-09-25T09:13:19.704Z`）；
§1 里 `com.dshm.dshclient` 那条**已不在**。同一时刻磁盘上 21 个会话目录一个没少
（`sessions/--storage-Users-currentUser-harness--/` 下 21 个），`Download/com.dshm.dshclient/` 目录本身也仍在（按 §6 的裁定不动它）。

**手机（手持档，`VYG-AL00`，API 26，2026-10-07 覆盖安装）**：`home` 指纹 `links=8 → 8`（数据保全），
端侧切到 `0.2.1-alpha.1+dshm.13`，`toybox=ok`（手持档判据，见 `docs/104`），`tools/device-acceptance.ps1` **5/5 PASS**。
插件行为（两次启动读数一致）：

- `[dshm-workspace-claim] 注册表里已有 2 条工作区 ⇒ 本次不新增` ⇒ **不再增长**
  （该机升级前跑的是 `+dshm.7`，正是"每次启动都登记"那一版）。
- **一条都没撤**，这正是纪律 ② 的预期结果：该机注册表里那条 `Download/com.dshm.dshclient`
  **挂着 1 个会话**（`session/list` 实测：5 个会话中 4 个 `cwd=…/Download/harness`、
  1 个 `cwd=…/Download/com.dshm.dshclient`，后者 `blank=true`、无标题、`updatedAt=2026-10-06T03:50:45Z`）
  ⇒ `sessionIds.length === 1 ≠ 0`，按"用户在用它"处理 ⇒ **不替用户删**。
- 想让它消失只有两条路：① 用户在 UI 里点删除（只删登记，目录与会话日志都保留）、
  ② 把规则放宽成"只挂空白会话也算 0 会话" —— 那会把一个会话变成**无归属**（它仍在磁盘、仍在列表里），
  且"空白"要另引一个会话服务才能判，**本轮不采纳**。

### 5.3 读日志 / 读注册表的口径（本轮**更正**了一条既有误判）

- **更正**：端侧插件的 `console.log` **会**落到 `$filesDir/node-output.log`（进程 stdout 的转写：每次启动轮转、
  权限 `-rw-rw-rw-` ⇒ `hdc shell` 与 `hdc file recv` 都读得到）。此前"插件日志不进任何可读文件、只能靠 UI 复核"
  的结论**不成立** —— 它只对 `dshm-host.log` 成立（那个文件只收 `main.js` 的 `diag()`）。
  ⇒ 插件行为的机器判据 = `node-output.log`，比 UI 复核硬。
- **读注册表仍要经 Python 桥**（日志那条不适用）：`dsh/home` 是 0700，`hdc shell` / `hdc file recv` 都读不到。
  但 token 不必去 0700 目录里翻 —— `node-output.log` 里就有 `dsh web: http://127.0.0.1:3120/?token=…`（`writeHostReady()`
  的捕获源）。取**最新**那一条（token 每次进程启动都换），`hdc fport tcp:<宿主端口> tcp:3120`，
  再打 `/dshm-python/run-get?token=…&code=…` 就能读任意宿主可见的文件（含 0700 目录里的注册表）。

## 6. 影响面与回退

- 只有「注册表为空」这一条路径会**加**东西；已有用户的设备上，本插件从「每次启动写一条」变成
  「什么都不做（外加一次自愈撤回）」。
- 不新增权限、不改上游 dsh、不碰用户自己的工作区；`DSHM_PUBLIC_DOWNLOAD` 为空时仍完全惰性。
- 回退：把 `hostcore/plugins/dshm-workspace-claim/lib/index.js` 回到上一版即可；`dist/sideload/previous-internal-test/`
  留了 `+dshm.12` 与 `+dshm.11` 两个**同签名**整包，可直接 `hdc install -r` 回退。
- **不做**的一件事：不替用户去删 `Download/com.dshm.dshclient` 目录本身 —— 它仍是宿主的默认工作目录
  与 `publish` 工具的目标根（`docs/95` §2.2）。

## 7. 治理

- `coreVersion` → `0.2.1-alpha.1+dshm.13`（`hostcore/core-recipe.json`；插件内容变了，必须递增才不会复用旧树）。
- 门禁接线：新增 `tools/check-workspace-claim.mjs`（离线，不需要核心树与设备）；`tools/check-core-openharmony-patches.mjs`
  的「自带插件包」站点新增 5 条 `forward` 断言（标题常量 / fail-closed / 只撤 0 会话那条 / 撤完非空 / 只在空注册表时 create）。
- `cordis.patch.yml` ⑨ 的注释块同步改写（写明收窄口径与 2026-10-07 实证）。
