## 5. 两条"手滑就破防"的坑（本轮实测新增）

### 5.1 裸跑 `tools/pack-core.mjs` 会让 `check-resfile-core-zip` 判红

**现象**：`dist/core/dsh-core-0.2.1-alpha.1+dshm.13-openharmony-arm64.zip` 的 sha256 从
`eac9393d9a0ecc12…` 变成 `f0233125396d4c4c…`（**字节数一模一样**，都是 59,191,096），
而 `entry/src/main/resources/resfile/` 里那份**没动** ⇒ 门禁报
「✗ resfile 里的容器与 dist/core 的本次产出**不一致** —— 安装包里带的不是你刚打的树」。

**实测根因（逐条目比对 16,487 条）**：**只有 1 个文件变了** —— 树内的 `dshm-core.json`，它的 `builtAt`
从 `2026-10-07T03:51:28.316Z` 变成 `2026-10-07T06:47:02.947Z`。**其余 16,486 条逐字节相同。**

**口径**：`pack-core` 是**构建工具**，它不是幂等读操作 —— 重跑一次就会重新盖时间戳。
⇒ 只想体检**不要裸跑它**；真要重打，就连 `--place-in-app` 一起跑（并按 `AGENTS.md`「出包三坑」第 2 条处理复用目录）。
**还原方法**（本轮用的就是这个，零成本）：`dist/core` 那份是**构建缓存**，`resfile` 那份才是**装机包里真正带的**⇒
用 resfile 覆盖 `dist/core`（或按 `AGENTS.md` 从已装 HAP 里逐字节取出），再把 `dist/core/*.manifest.json` 的 `sha256` 对齐。

### 5.2 裸跑 `tools/place-toolchain.mjs` 会让 resfile 与 HAP 失同步

**现象**：resfile 下 **15 个 `.apk` + 1 个 `cpython-…-musl.tar.gz`** 被重写 ⇒ 与刚打好的 HAP **逐字节不同**
（长度都一模一样）。

**实测根因**：这些归档是**构建期自签名后重新 gzip** 出来的，**变的是 gzip 头里的 MTIME（字节 4–7）**；
把两边的 payload 各自 `gunzip` 再比，**逐字节相同**（例如 `libexpat-2.8.4-r0.apk`：`1f8b0808 01dcb86a …` vs `1f8b0808 01ebc56a …`，内层 225,280 B 完全一致）。
`dshm-signed.txt` 标记**没变**（它记的是归档摘要，不含 mtime）⇒ 设备侧"存在即跳过"的判据不受影响。

⇒ 结论同 §5.1：**体检别裸跑它**；万一跑了，**从已装 HAP / resfile 逐字节还原**即可（本轮还原后：HAP 内 resfile 39 条 vs 磁盘 **39/39 一致**，
`check-toolchain-sign` 与 `assert-resfile-sync` 全绿）。

> **为什么这两条值得写下来**：它们都会**静默地把"交付物与树"拆开**，而链上自检只在你恰好跑了那条门禁时才会喊。
> 记法与 `AGENTS.md`「出包与核心树的三个坑」同源，是它的两个**同族变体**（一个来自 `pack-core`，一个来自 `place-toolchain`）。

## 9. 追加：`device-code-fingerprint.ps1` 的 token 取源缺陷 · 重出包 r4 · 手机端实测

> 本节是 §4–§8 之后的**追加轮**（同日 15:20 前后）。触发点是**质检脚本自身的缺陷**：
> 它把「环境不满足」误报成「未验证」，等于让 §7 第 1 条的装机核对**永远给不出结论**。

### 9.1 缺陷：token 取自日志 `tail -1` ⇒ 手机档偶发 401

**现象**：手机档不喂 token 跑 `tools/device-code-fingerprint.ps1`，脚本走完桥请求后报
`rc=2 未验证`；同一台设备、同一时刻，把 live token 用 `-Token` 手动喂进去立刻 **5/5 一致**。

**根因**：脚本原先从 `<filesDir>/dshm-host.log` 里 **`tail -1`** 抓那行 `dsh web: … token=`。
但这一行是**启动当时**打印的：应用每冷启动一次就写一行新的，而宿主进程重启后 token 会换。
`tail -1` 抓到的可能是**上一个进程**留下的 token（尤其在 `update-device.ps1` 刚做过冷启动、
或设备上先后跑过两轮的环境里）⇒ 请求带着**过期 token** 打到桥 ⇒ 桥回 **401**（`{"error":"token required"}`）。

**证据（可复现）**：同一时刻、同一 token 下，`/dshm-python/status` 返回 **200**，而
`/dshm-python/run-get` 返回 **401** —— 说明「桥通了、但这个 token 当前进程不认」，
不是「桥不通」。原实现把这两种情况都归进「桥都不应答」这一句，读的人无从下手。

**修法（三级优先，来源打进输出）**：

| 优先级 | 取源 | 说明 |
|---|---|---|
| 1 | 命令行 `-Token <tok>` | 人工排障用；喂进去立刻覆盖下面两级 |
| 2 | `<filesDir>/dsh/home/host-ready.json` 的 `"token"` | **权威值 = 当前进程写出的**；实测该文件 **0666** ⇒ shell 身份也读得到 |
| 3 | `<filesDir>/dshm-host.log` 的 `tail -1` | **兜底**，输出里标注「⚠️ 可能是旧进程留下的」 |

配套两处改动：

- 新增 `$TokenSrc`，把来源与长度打进输出 —— 现在桥行是
  `桥：127.0.0.1:3120（token 长度 43，来源 host-ready.json）`，从日志一眼能看出**用的是哪一级**。
- **401 单独判读**：新增 `$saw401`（从 `$_.Exception.Response.StatusCode` 取 401）。
  命中时不再说笼统的「都不应答」，而是直说「桥回了 401（token 不被当前进程接受）——
  token 来源：…；日志里的 token 会随进程重启过期，权威值是 `host-ready.json` 的 token，
  也可 `-Token <live>` 喂进来」。取 token 失败的措辞同步改准：
  `拿不到宿主 token（host-ready.json 与 dshm-host.log 都没有）⇒ 未验证`。

> **本机 + 真机验收**：修前同一条命令 `rc=2 未验证`；修后（不喂 token）
> `token 来源：host-ready.json（长度 43）`、`结论：一致（5/5）`、**RC=0**。
> 本节所有读数都是**手机档**（`62T0225B18039433`）实测，不是推断。
