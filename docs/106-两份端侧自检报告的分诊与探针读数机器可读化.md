## 2 落实①：探针读数写进 `host-ready.json`（`hostcore/app/main.js`）

**为什么**：两份报告的所有开放问题（①§1.1 的"终端能力六行"、②§7 的第 1/2/3 问）
问的都是"**本档到底能不能 exec / 有没有真 shell / python3 能不能跑**"，而这些读数此前
**只进 `dshm-host.log`** —— 于是只能从日志文本反推（报告②甚至把技能文档当成了档位判据，见 §3）。

**做法**：新增 `recordRuntimeProbe(key, value)`，把探针读数补写进 `host-ready.json` 的 `runtime` 段。

| 新字段 | 内容 |
|---|---|
| `runtime.exec.results` / `runtime.exec.summary` | 每项 exec 探针的判定（`ok` / `denied` / `缺` / `so-fail`）+ 与日志逐字相同的汇总行 |
| `runtime.terminal` | `hostDomain`、`toyboxDomain`、`shStat`、`relaySh`、`relayAsh`、`libsExec`、**`realShell: 'yes'\|'no'`**、`note`、`measuredAt` |
| `runtime.python` | `bridge`、`stdlib`、`ready`、`initialized`、`selftest`（`ok`/`fail`/`pending`/`unavailable`/`error`）、`stdout`、`rc`、`elapsedMs`、`note`、`measuredAt` |

三个不许省的细节：

1. **pid 守卫**：文件可能是**上一次进程**留下的（长驻窗口里进程重启）；补写别人的读数会张冠李戴。
2. **`tmp` + `rename` 原子替换**：ArkTS 侧随时可能读该文件取 token；就地截断写会让并发读者读到
   **半个 JSON**（历史上那条"核心已重启，但没读到启动链接"就是这么来的）。
3. **先暂存再补写**（`PENDING_RUNTIME_PROBES`）：`ensureExecutables()` 在 boot 早期就 `setImmediate`
   起跑，而 `host-ready.json` 要等 dsh 把 `authenticatedUrl` 打到 stdout 才**首次落盘** —— 谁先谁后
   **不确定**。跑在前面的探针若直接补写，撞上的是"文件不存在"或"文件属于上一次进程"⇒ **静默丢读数**。
   故一律先暂存，`writeHostReady()` 首次落盘时并进去。

**判据口径**：`realShell` 看**回显 marker**（`DSHM-RELAY-SH-OK` / `DSHM-RELAY-ASH-OK`），**不看 rc** ——
docs/104 §4 的教训：`toybox sh` 会被记成 `rc0`，真相在 stderr 的 `Unknown command`。

## 3 落实②：三份内置技能的"档位口径"（回答报告②§2.2 的"矛盾点"）

报告②的形式是：「`ohos-pc` 技能称本机为 PC/2in1 档 ⇒ 该档预期可执行；实测 `spawn bash EACCES` ⇒ 二者不符」。
核实结论：**报告方的框架错了**（本机是手机档，`deviceType=phone`），**但它暴露了我方文档的真实缺陷**——
`ohos-pc.md` 正文第一句在手机档下会被读成"本机就是 PC 档"。三份技能同步改口径：

| 文件 | 原来 | 现在 |
|---|---|---|
| `ohos-pc.md` | 正文首句直接说"DSHM 当前运行在 HarmonyOS PC 上" | 补 **适用范围**块：本技能描述 **PC/2in1 档**；手机 / 平板档的可执行性判据**不同**，那种情况以 `ohos-shell.md` 与 `docs/104` 为准 |
| `ohos-shell.md` | "沙箱内能否执行**取决于设备档位**：PC/2in1 档可执行；手机档…（`EACCES`）⇒ 此时只能用文件工具完成工作" | 展开成**三档口径**：① PC/2in1 ⇒ 沙箱 ELF 可执行（探针 10/10）；② 手机 / 平板 · 随包 ELF ⇒ 一律 `EACCES`（含 `toybox env <elf>` 中继，**同判**）；③ 手机 / 平板 · 系统 `toybox <applet>` ⇒ **能真跑**（约 149 applet，但**不含 `sh`/`bash`/`ash`**）⇒ 本档**没有真 shell 进程，有的是真 userland 命令** |
| `ohos-python.md` | "沙箱也不能 execve 外部 ELF" | 改为**按档位**：PC/2in1 档可以（探针 10/10），手机 / 平板档被拒（`EACCES`，判据见 `docs/104`） |

> 判据口径的一句话记法：**"取决于档位"不是"就是档位行为"**；而"沙箱 ELF 不能执行"也**不等于**
> "所有命令都不能用"（toybox 可以）——这两处正是报告读歪的地方。

## 4 落实③：Python 的「命令」与「运行时」（回答报告②§7 第 3 问）

报告② §2.3 的矛盾点：`ohos-python` 断言 `python3` 垫片"直接可用"，而 `python3` 垫片与实测失败的
`npm` **同形**（都是 `#!/system/bin/sh`）。**裁定：两条事实都成立，因为它们说的不是同一条路径。**

| | "命令"入口 | "运行时"本身 |
|---|---|---|
| 是什么 | `~/bin/python3`、`~/bin/pip3`（`#!/system/bin/sh` 脚本） | 宿主进程内的 CPython 3.12（NAPI addon `dlopen` libpython + embedding API） |
| 是否需要 `execve` | 需要（脚本要解释器） | **不需要**（在 node 进程内调用） |
| PC/2in1 档 | 可用 | 可用 |
| 手机 / 平板档 | **不可用**（解释器 `/system/bin/sh` 被系统拒绝 ⇒ 整条命令无从执行，与 `npm` 垫片同因） | **可用**（入口是 `/dshm-python/*` 端点） |

⇒ 已据此更正 `ohos-python.md`（正文补"⚠️ 上表的命令行用法只在 PC/2in1 档成立"）与 `ohos-shell.md`
的例外澄清；并给 **`runtime.python`** 加了机器可读读数（§2），下一个自检报告不必再猜。

## 5 为什么不升 `coreVersion`

AGENTS.md 的"坑 2"针对的是 **`dist/core/work/<ver>` 增量复用会静默跳过 pack-core 注入**。
本轮的改动**不在核心树里**：

* `hostcore/app/main.js` → `entry/src/main/resources/resfile/resources/app/main.js`（**HAP 的 resfile**，
  ArkTS 侧按 `${resourceDir}/resources/app/main.js` 直接读，见 `entry/src/main/ets/entryability/EntryAbility.ets:449`）；
* 三份技能 → `entry/src/main/resources/resfile/ohos-skills/*.md`（端侧由 `ensureBundledSkills` 按**内容 sha256** 同步）。

两者**都随 HAP 走**，覆盖安装即生效；核心容器（`dsh-core-…-openharmony-arm64.zip`）一个字节没变。
所以本轮**不升版本、不重跑 `pack-core`** —— 升了只会触发一次无谓的整树重物化，并把 HAP 体积与
`resfile` 里的容器名一起改掉。

> 但"手机档读数落盘"这件事**必须有真机读数才算验完** —— 留作下次连机时的第一步（判据：手机
> `host-ready.json` 里 `runtime.terminal.realShell` 应为 `"no"`、`runtime.exec.results` 里
> `rg/ash/bash=denied`、`runtime.python.selftest=ok`）。

### 7.3 顺带查明并修掉：`/proc/self/attr/current` 的 NUL 把日志行变得"看起来被截断"

本轮自验时先出现一个**假警报**：日志里 `终端能力汇总：…` 只显示到 `宿主域=…:s0`，`grep -c '探针读数'`
又是 **0** ⇒ 一度像是"新代码没生效"。三件事先后被排除/坐实：

1. 设备侧 `main.js` 与工作区**逐字节相同**（`sha256 11636eca…`、269,379 B，经 Python 桥取回校验）；
2. `host-ready.json` 里 `runtime.exec / terminal / python` **都在**（§7.2 原文）；
3. ⇒ 日志"少一行"的真实原因是 **pid 守卫的静默早退**：探针跑在 `host-ready.json` 落盘**之前**，
   读到的是**上一次进程**的文件 ⇒ 走 `payload.pid !== process.pid` 分支直接 `return`。读数没丢
   （由 `PENDING_RUNTIME_PROBES` 兜住），但**日志里没有任何痕迹**。

同时查明 `终端能力汇总` 那行为什么"看起来被截断"：`fs.readFileSync('/proc/self/attr/current','utf8')`
读出的域字符串**尾部带一个 `\0`**，而 JS 的 `\s` **不匹配** `\u0000` ⇒ NUL 原样留在读数里。
设备侧 `grep` 遇到 NUL 就当成行尾 ⇒ **只有在设备侧 grep 时**那一行才"截断"（用 `hdc file recv`
取回本地看，全文 89+ 字节一字不少，`\0` 就在 `s0` 之后）。**这解释了 r4 报告 §1.1 里那行
「终端能力汇总：宿主域=…」为什么短了一截**——报告方看到的是 grep 的假象，不是代码只打了宿主域。

两条处置（`hostcore/app/main.js`）：

* `tidy()` 与 `hostDomain` 读取都先剔 NUL ⇒ 日志行与 `host-ready.json` 里不再有 `\u0000`；
* pid 不匹配分支补一行 diag（`探针读数已暂存（host-ready.json 仍属于上一次进程 pid=…，本进程是 …）`）
  ⇒ 这条路径**从"静默"变成"可读出"**。修后真机读数：

```
[09:43:18.992Z] 探针读数已暂存（host-ready.json 仍属于上一次进程 pid=10947，本进程是 13459）：runtime.python
[09:43:20.134Z] 探针读数已暂存（…）：runtime.exec
[09:43:20.349Z] 探针读数已暂存（…）：runtime.terminal
[09:43:20.179Z] 终端能力 toybox域：rc0 out=[u:r:develop_tools_debug_hap:s0] err=[]      ← NUL 已消失
[09:43:20.349Z] 终端能力汇总：宿主域=u:r:develop_tools_debug_hap:s0，toybox域=rc0，toybox-stat-sh=rc0，
                toybox-exec-sh=rc0，toybox-exec-ash=rc0，libs-exec=err(EACCES)            ← 整行可读、可 grep
```

> **教训（写进本项目的读数纪律）**：一条读数"看起来缺了半行"时，先分清是**数据缺**、**写入截断**，
> 还是**读取工具在 NUL/编码上停住了**。本轮三种都出现过一次（分别对应 404 假象、pid 早退、NUL 截断）。
