## 1. 任务背景与依据

### 1.1 上游事实：dsh 已经是「Host / Client 分层」的可远程化架构

DeepSeek Harness（`dsh`）是 DeepSeek AI 开源的 agent harness，「一切皆插件」架构（Cordis 驱动）。它的既有事实决定了本次开发**不需要、也不应该**去 fork 它的业务代码：

1. **Host 与 Client 分离**：Host（Node.js）挂 `apiProxy` + `webserver`；Client（浏览器）经 `WebApiClient` 走 **HTTP 上行 + WebSocket 下行**。
2. **协议是稳定且独立的**：`@deepseek-ai/dsh-host-webserver` 只提供一张路由表（`exact` / `prefix` / `upgrade` / 单一 fallback），`@deepseek-ai/dsh-client-connection` 与 `@deepseek-ai/dsh-api-gateway` 在 `POST /api/<endpoint>` 上跑 Remote RPC，在 `/api/remote.mux` 上跑 WebSocket 逻辑流复用。**任何能说这两种载体的客户端都是合法的 dsh 客户端**，与浏览器、Electron 无关。
3. **客户端 UI 是插件而不是产品**：`dsh-client-ui-*` 是被 Client 侧 Cordis 组合出来的插件 bundle（preact），`dsh-client-ui-layout` 提供三栏 `AppFrame` + 让步链 + 主题呈现器。也就是说：**UI 层是可替换的**，官方前端不是唯一形态。
4. **安全围栏是显式设计**：`dsh web --host 0.0.0.0` **被上游明确拒绝**（"出于安全考虑"）；`/api` 前有 Host/Origin 信任栅栏 + 启动 token 换签名 cookie 的认证；特权方法（`settings.*`、`credentials.*`、`host.pickDirectory/openPath`、`agentPreset.*`、`llm.discoverModels`）锁定 loopback-only。

> 这四条事实合起来给出结论：**做鸿蒙客户端 = 实现一个协议兼容的原生 Client +（可选的）一个不触碰上游的 Host 接入方案。**

### 1.2 官方桌面端给了什么工程标准

官方 `apps/desktop`（Electron 壳）不是我们要复制的形态，但它的**决策表达方式**是本任务书的写作模板。其中可迁移的 6 条：

| 官方决策 | 可迁移到鸿蒙端的形式 |
|---|---|
| 发布身份：壳 API / Web 客户端 / 后端 / 插件依赖图作为**一个组合**验证，版本不许分裂 | 鸿蒙端与所对接的 dsh 版本组成**受支持的版本矩阵**，矩阵外不承诺 |
| 运行时隔离：绝不使用系统 Node/pnpm，一切走内置运行时 | 鸿蒙端绝不依赖设备上的 Node/终端/包管理器；Host 能力缺失时**降级而非崩溃** |
| 状态归属：Electron 独占 `$DSH_HOME/profiles/desktop`，与 CLI 共享数据但**绝不共享可执行包/锁/插件激活** | 鸿蒙端只做 Client：独占自己的本地缓存与设备绑定，**不写 `$DSH_HOME` 的包状态** |
| 激活事务：staging → 健康检查 → 切换 → rollback 日志 | 连接切换 / Host 版本升级 / 缓存迁移同样走「先验证后激活」 |
| 无共享执行图 / 单实例锁 / 事务锁 | 鸿蒙端多窗口共享单一连接池与单一会话状态机（§7.7.5） |
| 发布验证必须真机 + 上一版本升级路径 | 验收必须在**真机矩阵 + 模拟器**双轨，含跨版本升级（§11） |

### 1.3 社区移植给了什么教训

`fellow99/deepseek-harness-harmony`（Electron-on-鸿蒙，已在 HarmonyOS 6.1.0.135 / API 24 真机跑通 dsh Web UI）证明了两件事，也暴露了一条必须换掉的路线：

**它证明可行的**：dsh Host 能在鸿蒙沙箱里被跑起来（Node 22.17.0），Web UI 同源加载可用，会话持久化（better-sqlite3 aarch64）可用。

**它必须被替换的**（详见 §3 对标表）：内置 `libelectron.so` ≈ **172.7 MB**，dsh 产物打成 **143 MB** `dsh-dist.tar.gz` 启动时流式解压；为绕过鸿蒙 loopback 进程隔离而**绑 `0.0.0.0` 并 patch 掉上游的拒绝检查**，再用 Host 头改写去骗过 loopback-only 围栏；`node-pty` / `koffi` / `sharp` 三个原生模块无 aarch64 产物，导致**终端工具、内容搜索、进程沙箱、图片校验缩略图全部缺失**，agent preset 里 7 个工具行被禁用；`deviceTypes: ["2in1","tablet"]`，**手机不在目标内**。

### 1.4 一句话任务

> **做一个「本体就能跑 DSH」的鸿蒙应用：应用内自带 DSH 核心运行能力（Node 运行时 + dsh 核心树），在本端把 Host 起在 `127.0.0.1` 上，ArkUI 原生页面就是这个本地 Host 的客户端页面；协议完全兼容上游、零上游 patch、覆盖手机到 2in1 全设备形态，并支持插件的增删启停与核心版本的安装 / 切换 / 回滚。**

> ⚠️ **目标已更正（2026-09-12）**：原表述把本项目定位为「PC 侧 Host 的远程客户端」，并把「端侧跑完整 dsh Host」列为非目标。
> 该定位与本项目真实目标相反，已废弃。**权威版本见 [`docs/50-端侧核心运行架构.md`](50-端侧核心运行架构.md)（D6）**，本文与之冲突处以 D6 为准。
> 远程 Host 接入保留为**可选能力**，但不再作为目标与验收口径。

## 3. 对标分析：我们要比谁好在哪

### 3.1 三方能力矩阵

| 维度 | 官方 dsh Web（浏览器） | 官方 Desktop（Electron） | 社区鸿蒙版（Electron-on-鸿蒙） | **本项目（ArkTS 原生）** |
|---|---|---|---|---|
| 运行时 | 系统浏览器 | 内置 Node + Electron | 内置 Node（Electron 37）+ `libelectron.so` | **无额外运行时** |
| 端上体积 | — | 数百 MB 级安装包 + seed | SO ≈172.7 MB + `dsh-dist.tar.gz` ≈143 MB | **目标 ≤ 50 MB 安装包** |
| 冷启动 | 服务器已就绪 | 解压/校准 seed 后建窗 | **流式解压 143 MB** 后建窗 | **目标 ≤ 1.5 s 到可交互（含连接）** |
| 设备形态 | 任意浏览器 | Win/macOS x64/arm64 | 2in1 / tablet | **手机 / 折叠屏 / 平板 / 2in1 PC + 多窗** |
| 手机适配 | 网页降级 | 无 | **不支持** | **一等目标**（单栏 + 底部操作区 + 手势） |
| 终端（bash/pwsh 工具） | 有 | 有 | **无**（node-pty 无 aarch64） | **有**（Host 在 PC 侧，天然保留） |
| 内容搜索（ripgrep） | 有 | 有 | **无**（subprocess 被禁） | **有**（同上） |
| 进程沙箱 | 有 | 有 | **无**（koffi 被禁） | **有**（同上） |
| 图片校验/缩略图 | 有 | 有 | **stub，no-op** | **端侧原生解码 + 缩略图**（ArkTS image） |
| 审批 / 提问交互 | 网页卡片 | 桌面通知 | 桌面通知（弱） | **端侧推送 + 锁屏直达 + 语音答复** |
| 网络暴露面 | loopback | 无监听端口（`dsh-app://` + IPC） | **绑 `0.0.0.0`，且 patch 掉上游拒绝检查** | **不新增暴露面**（loopback 直连 / 显式授权的加密隧道） |
| 上游改动 | 无 | Host 侧私有 overlay | **4 个上游 patch** | **目标 0 个上游 patch** |
| 分发 | — | 签名安装包 + electron-updater | 本地签名 HAP 自用 | 签名 HAP/APP + AGC 内测分发（分阶段） |

### 3.2 差异化定位（对外可宣称的三条）

1. **原生而非套壳**：ArkUI 原生渲染 + 原生协议客户端。没有 172 MB 的浏览器内核，没有 143 MB 的启动解压，没有「先起一个 Web 服务器再套一个 Web 视图」的中间层。
2. **全形态而非只做 PC/平板**：手机竖屏单手可用、折叠屏展开态秒变双栏、平板/2in1 多窗口 + 键鼠 + 拖拽 + 快捷键。手机不是「缩小的桌面」，而是「审批与随行的主控台」。
3. **不打洞而是接入**：不绑 `0.0.0.0`、不 patch 上游安全围栏。跨设备访问走**显式配对 + 加密隧道**，Host 侧仍是纯 loopback，安全语义与上游一致。

### 3.3 明确不做（Non-Goals，v1 范围）

| 不做 | 理由 |
|---|---|
| fork 或魔改 dsh 业务代码 / agent 逻辑 | 上游演进快，维护成本不可控；协议已是稳定接入面 |
| ~~端侧跑完整 dsh Host（Node 运行时进 HAP）~~ | **已移出非目标，改列关键路径**（2026-09-12）：Node 官方已支持 OpenHarmony、dsh 原生依赖已有鸿蒙移植，原判定依据过期。见 D6 |
| 自建模型调用链路（绕过 Host 直连 DeepSeek API） | 会话、工具、审批、权限语义全在 Host；绕过即失去产品价值 |
| 端侧执行 agent 工具（bash/文件/sandbox） | Host 侧执行是正确边界，端侧只需呈现与审批 |
| 复刻官方 Web 前端的全部内部界面 | 我们只保证**协议兼容**，不保证**像素兼容**；必要界面按移动端重设计 |
| 插件市场的完整安装/卸载编排 | dsh-market 的注册表操作归 Host；端侧只做「列出 / 触发 / 展示状态」 |
| 网页版 dsh 的浏览器扩展、桌面 TUI 等其它表层 | 超出范围 |

## 5. 设计目标与核心原则

### 5.1 目标（可度量，验收即按此表）

| # | 目标 | 指标（v1 门槛） |
|---|---|---|
| G1 | 协议兼容 | 通过 §11.2 协议一致性套件；对目标 dsh 版本**零上游补丁** |
| G2 | **自足**（2026-09-12 新增） | 无任何外部 Host 时，应用可独立完成：起核心 → 建会话 → 对话 → 审批 → 文件投喂 |
| G2b | 体积（原 G2，**旧值作废**） | 安装包 ≤ **400 MB**（含 Node 运行时与 dsh 核心，Node 自身即数十 MB，≤50 MB 不可能）；首启解包 ≤ 60 s；常驻内存 ≤ **400 MB**（典型会话，Node + ArkUI 同进程） |
| G3 | 快 | 冷启动到可交互 ≤ **1.5 s**（P50，设备已配对）；会话切换 ≤ 200 ms；流式首 token 呈现延迟 ≤ 150 ms（相对网络） |
| G4 | 全形态 | 手机 / 折叠屏 / 平板 / 2in1 四形态在真机与模拟器均通过 §11.3 布局矩阵 |
| G5 | 移动端一等交互 | 审批/提问 从「收到通知」到「完成答复」≤ **2 步**；离线可读最近 50 条会话 |
| G6 | 不新增暴露面 | 默认部署下不监听任何对外端口；跨设备访问必须走显式配对，未配对设备一律拒绝 |
| G7 | 可诊断 | 任何连接/渲染失败都能在端内「连接诊断」页给出：端点、TLS、认证、协议、Host 版本五项判定 |
| G8 | 可持续演进 | 通过 `Connection` 薄接口替换载体（LAN / 隧道 / 未来端侧 Host），不触碰上层 UI 与状态层 |

### 5.2 核心原则

1. **协议优先于实现**：先把 wire 事实固化成 D2，再写代码；任何协议层猜测必须先用 §附录A 的实测方法证伪。
2. **零上游改动**：所有鸿蒙侧差异都在我们这一端消化；一旦发现必须有上游改动，走 §6.6 的接口申请流程，而不是 fork。
3. **安全围栏不绕过**：不做 Host 头改写、不做 `0.0.0.0` 绑定、不做「关掉校验」的补丁。要跨设备就**加一层我们自己的、显式授权的加密通道**。
4. **能力降级而非崩溃**：Host 侧缺什么（终端/图片/沙箱），端侧只是无法呈现对应入口，绝不让会话不可用。
5. **先桩后真**：UI 与状态层面向 `Connection` 与 `RemoteApi` 接口编程，用「协议录制回放桩」开发，不阻塞在 Host 可用性上。
6. **一条数据流**：所有形态共用同一套状态机与同一套协议层，差异只体现在视图与输入层。

## 6. 总体架构

### 6.1 逻辑分层（A 方案，v1 关键路径）

```
┌─ HarmonyOS 应用（HAP/APP）──────────────────────────────────────────────┐
│  UI 层（ArkUI，一多自适应）                                              │
│    ├ 手机单栏栈式导航        ├ 折叠屏可变栏    ├ 平板/2in1 三栏 + 多窗    │
│    └ 组件：会话列表 / 轨迹 / 工具卡片 / 审批卡 / 输入区 / 设置 / 诊断      │
├────────────────────────────────────────────────────────────────────────┤
│  状态层（ArkTS，无 UI 依赖）                                             │
│    ├ SessionStore（会话投影与增量）  ├ ApprovalStore（待决审批/提问）     │
│    ├ WorkspaceStore / SettingsStore / JobStore                          │
│    └ OfflineCache（最近会话 + 待发队列 + 已读水位）                       │
├────────────────────────────────────────────────────────────────────────┤
│  协议兼容层（本项目核心资产，可单测）                                     │
│    ├ RemoteRpc：POST /api/<endpoint> 信封编解码 + rpcId 关联 + 取消       │
│    ├ RemoteMux：WS /api/remote.mux 逻辑流（open/cancel/item/error）       │
│    ├ EventStream：$events 逻辑流 + opening ready 项 + 重连代次            │
│    ├ AuthSession：token 交换 → 签名 cookie → 自动续期/失效重绑            │
│    ├ TrustHeaders：Host / Origin 的正确构造（不伪造，见 §6.4）            │
│    └ Reconnect：500ms→1s→2s→4s→8s→10s + 50%~100% 抖动的等阶重试          │
├────────────────────────────────────────────────────────────────────────┤
│  设备接入层（Connection 薄接口，可替换）                                  │
│    ├ LoopbackConnection（Host 与端同机：直连 127.0.0.1）                  │
│    ├ LanPairingConnection（显式配对 + 一次性密钥，见 §6.4）               │
│    └ TunnelConnection（PC 侧搭桥服务，TLS + 设备密钥，见 §6.5）           │
├────────────────────────────────────────────────────────────────────────┤
│  平台适配层                                                              │
│    ├ @ohos.net.http（含 enableAutoCookie）/ @ohos.net.webSocket          │
│    ├ 通知 / 后台任务 / 剪贴板 / 分享 / 相机 / 相册 / 语音识别 / 无障碍     │
│    └ 窗口与形态（断点、折叠态、多窗口、悬停态、悬浮窗）                    │
└────────────────────────────────────────────────────────────────────────┘
                                  │  HTTP + WebSocket（dsh 既有载体，不改）
                                  ▼
┌─ dsh Host（**端侧同进程**；也可选地在 PC / 开发机 / 服务器上，上游原样）────────
│  webserver（127.0.0.1 或经搭桥服务受控暴露）                             │
│  ├ /api            → Remote RPC（一元）                                 │
│  ├ /api/remote.mux → WebSocket 逻辑流复用（心跳 2s Ping/Pong）            │
│  ├ /api/events.*   → 转发事件流（$events → ready + 增量）                 │
```

### 6.2 为什么是「端侧自足 Host + 端侧原生页面」（B 方案的论证，2026-09-12 反转）

> **判定已反转**：原 §6.2 判 B（端侧 Host）为 P3、A（PC 侧 Host）为主方案。依据过期（Node 官方已支持 OpenHarmony；
> dsh 原生依赖已有鸿蒙移植），且 A 方案把产品价值绑在「用户另外得有一台跑着 dsh 的机器」上。
> 权威论证与证据见 **[D6 §3](50-端侧核心运行架构.md)**。

| 备选 | 描述 | 判定 |
|---|---|---|
| **B：端侧完整 Host（Node 运行时进 HAP）+ 端侧原生页面** | 应用内自带 Node 运行时与 dsh 核心树，Host 起在 `127.0.0.1`，ArkUI 页面即本地 Host 的客户端 | ✅ **v1 主方案**。真自足；Host 与客户端同进程 → loopback 不跨隔离边界，**不需要绑 `0.0.0.0`、不需要改 `Host` 头、不需要隧道**；核心与插件版本由本应用掌握 |
| A：原生 Client + PC 侧 Host | 端侧只说协议；Host 由用户的 PC/开发机提供 | 🔁 **降为可选接入**（"连接远程 Host"）。仍保留全部既有实现与验收，但**不再是目标**：任何"必须有另一台机器"才成立的功能都不算完成 |
| C：端侧 ArkWeb 复用官方 Web UI + 端侧 Host | 社区路线（Electron/ArkWeb） | ⚠️ **保留为可选页面**：dsh 核心树自带官方 Web dist，可作为"第二页面"；但**不作为主页面**（体积与内存是 Web 级），也不算验收口径 |
| D：端侧原生 Client + 端侧只读缓存（无 Host） | 纯离线阅读器 | ❌ 无 agent 能力，不构成产品 |

> **新门是 M0′/POC-11（运行时门）**：能否拿到一个**能被 HAP 加载且完成鸿蒙代码签名**的 Node 运行时
> （`libnode.so` + NAPI 引导），并在设备上读到 Node 版本与 `zlib.createZstdDecompress`。
> 该门未通过前不开工 M2′ 之后的一切；失败按 D6 §4.2 逐级回退，**不得**用"绑 `0.0.0.0` / 改信任头"绕过。

### 6.4 设备接入与安全设计（本项目最需要评审的一节）

**问题**：上游对 `--host 0.0.0.0` 明确拒绝，`/api` 前有 Host/Origin 信任栅栏 + token/cookie 认证，特权方法 loopback-only。手机要连 PC 上的 Host，必然跨过 loopback。

**我们不做什么**（这些是社区方案的做法，我们明确禁止）：

- ❌ 不 patch 掉上游的 `0.0.0.0` 拒绝检查；
- ❌ 不伪造/改写 `Host`/`Origin` 去骗过 loopback 围栏；
- ❌ 不把「局域网内其他设备也能访问」当作可接受副作用。

**我们做什么**（三条渐进路径，按审批权限分级）：

| 级别 | 场景 | 方案 | 安全属性 |
|---|---|---|---|
| **L0** | Host 与端同机（PC/2in1 上同时跑 Host 与客户端） | 直连 `127.0.0.1:<port>`，Host/Origin 天然 loopback | 与浏览器同源姿态一致，无新增暴露面 |
| **L1** | 局域网内 PC ↔ 手机 | **显式配对 + 一次性密钥**：PC 侧生成短时配对码（二维码/数字码），手机扫码换取**设备密钥**；跨设备访问经我们自己的**加密隧道**（TLS + 设备密钥双向认证），隧道客户端在 PC 侧，隧道出口仍在 Host 的 loopback 上 | Host 不暴露；未配对设备一律拒绝；密钥可单设备吊销 |
| **L2** | 跨网络（外出、多机） | 同上隧道 + 中继（可选自建/自托管）；凭证仍为设备密钥 | 端到端加密；中继不持有明文会话 |

> **关键点**：L1/L2 的隧道**出口在 Host 的 loopback**，所以上游信任栅栏与 loopback-only 特权方法**天然满足**，不需要任何伪造。这是与社区方案的本质区别。

**凭据存储**：设备密钥、签名 cookie、token 一律进 `@ohos.security.huks` 加密存储（或 `preferences` + 加密），不落明文文件；日志脱敏（见 §11.5）。

### 6.5 Host 侧搭桥服务（`hostkit`，P2 交付，不影响 P1 开工）

| 职责 | 说明 |
|---|---|
| 保活与代持 | 以受管方式拉起/守护本机 `dsh` Host（沿用官方 `runProfile` 语义，不改上游） |
| 发现 | 局域网 mDNS/广播播发「可配对的 DSH Host」，供端侧一键发现 |
| 配对 | 生成短时配对码，收端侧公钥，写入设备白名单 |
| 隧道 | TLS 出口 → Host loopback；WebSocket 透传（含 2s 心跳） |
| 审计 | 记录设备接入/吊销事件，端侧可查 |

**约束**：`hostkit` 必须是**可选组件**——没有它，L0 场景必须完全可用。

### 6.6 上游接口申请流程（发现必须改上游时）

1. 在 D2 中登记缺口（现象、复现、最小复现脚本）；
2. 评估三种规避：客户端侧兼容 / `hostkit` 侧补齐 / 配置层覆盖（`cordis.patch.yml` 属于组合配置，不算改代码）；
3. 三者都不可行时，才向 `deepseek-ai/deepseek-harness` 提 issue / PR，并同步本项目 `patches/` 目录**仅作为临时手段**，且必须在任务书中登记为技术债与退出计划。

## 附录 A：协议兼容事实基线（摘要）

> 完整版见 **D2 `docs/10-协议兼容事实基线.md`**，包含每个端点的实测方法、错误码表与探测脚本。

### A.1 载体与路径（已在上游代码中核实）

| 项 | 事实 | 来源 |
|---|---|---|
| 一元 RPC 路径 | `POST /api/<endpoint>`（`endpoint` 由 descriptor 的 namespace/method 拼成，段字符集 `[A-Za-z0-9_$.-]`） | `dsh-client-connection` 的 `createWebConnectionRpc` |
| 一元请求体 | `{ type: "client-request", rpcId, method: endpoint, payload }`，`content-type: application/json` | 同上 |
| 一元响应体 | `{ type: "server-response", rpcId, result }`；`result` = `{ ok: true, value }` 或 `{ ok: false, error: { code, message, details } }` | 同上（`parseConnectionResponse`） |
| rpcId 校验 | 客户端必须校验响应 `rpcId` 与请求一致，不一致即视为传输错误 | 同上 |
| 传输错误语义 | HTTP 非 2xx → `transport failure for <channel>/<endpoint>: HTTP <status>` | 同上 |
| WS 逻辑流路径 | `/api/remote.mux`（精确 upgrade 路由） | `dsh-api-gateway` 的 `REMOTE_STREAM_MUX_PATH` |
| WS 客户端帧 | `{ type: "open", streamId, endpoint, payload }`、`{ type: "cancel", streamId }` | `dsh-api-gateway/lib/client.js` |
| WS 服务端帧 | `item`（逐项 yield）、`error`（终止并抛 `RemoteError`）；正常终止即结束 | 同上 |
| 事件流逻辑端点 | `$events`（payload `{ args: {} }`），另有 `$events/result` 一元端点用于 waterfall 回送 | `dsh-api-gateway/lib/types/stream-protocol.js` |
| 事件流首项 | 唯一 `{ type: 'ready', clientId, host: { home } }`；此后才是增量事件 | `dsh-client-connection` README、`dsh-api-gateway` README |
| 心跳 | Host 每 `websocketHeartbeatIntervalMs`（默认 **2 s**）发 Ping；未在下一周期前回 Pong 则 Host 主动断开 | `dsh-api-gateway` README |
| 重连策略 | 500ms、1s、2s、4s、8s、10s 上限，50%–100% 抖动；10s 档失败后进入 `disconnected` 终态；`reconnect()` 立即从 retry 1 开始 | `dsh-client-connection` README |
| 认证 | 进程级随机启动 token → `GET /?token=...` 换**绑定 authority 的签名 cookie**（host-only、`Path=/`、`HttpOnly`、`SameSite=Strict`、默认 30 天）；静态资源公开；`/api` 全部方法与 WS 均要求该 cookie | `dsh-client-connection` README、`dsh-host-frontend-static` README |
| 信任栅栏 | `Host` 必须 loopback 或匹配 `trustedHosts`；带 `Origin` 时必须等于该 `Host`；`sec-fetch-site: cross-site` 一律拒绝；失败 **403**；Host 可信但未认证 **401** | `dsh-client-connection` README |
| 上游姿态 | `dsh web --host 0.0.0.0` **被启动期拒绝**（安全考虑）；默认 `127.0.0.1`；`--trusted-host` 可追加权威 | `dsh-web-app` README |
| 特权方法 | `settings.*`、`credentials.*`、`host.pickDirectory/openPath`、`agentPreset.*`、`llm.discoverModels` 等锁定 loopback-only | 社区工程的实测记录（§18.7 问题 2） |
| Host 路由表 | `exact` > 最长 `prefix` > 唯一 fallback；upgrade 仅精确匹配，未命中直接关闭连接 | `dsh-host-webserver` README |

### A.2 另一条可用协议（备选，非 v1 载体）

`@deepseek-ai/dsh-sdk-protocol`：**按换行分帧的 JSON-RPC 2.0**，方法 `initialize` / `session/prompt` / `shutdown`，通知 `session.event` / `session.status` / `subagent.started` / `subagent.finished`。它是 stdio 载体，服务端插件为 `dsh-sdk-jsonrpc-server`（`dsh --profile sdk`）。

**用途**：① 作为 §附录C POC-11（端侧 Host）的最小验证面；② 作为「端侧无 webserver」场景的备选接入方式。**它不是 Web 客户端的载体，不能替代 `/api`**。注意其已知限制：无取消方法、无会话关闭方法、无协议版本协商。

## 附录 B：产品需求与体验规范（纲要）

> 完整版见 **D3 `docs/20-产品需求与体验规范.md`**。

1. **信息架构**：会话（列表/轨迹/输入）· 待决（审批/提问）· 工作区（文件/交付物）· 设置（通用/模型/凭据/插件）· 诊断；
2. **三形态导航模型**：手机栈式（列表→会话→详情下钻，系统级手势返回）；折叠屏可变栏（展开自动双栏，折叠记忆上次栏位）；平板/2in1 三栏（导航/会话/详情）+ 详情栏可收；
3. **一多断点策略**：以窗口宽度为主断点 + 折叠态/悬停态为特征断点；采用 `GridRow/GridCol`、`SideBarContainer`、断点监听；组件级细化用 API 26 的 `ContainerReader`；
4. **关键组件规格**：会话列表项（标题/时间/状态/未读）、轨迹消息（角色/时间/耗时/折叠）、工具调用卡（名称/参数摘要/状态/结果折叠/耗时）、审批卡（动作/影响/原始载荷/三选）、提问卡（选项/自由文本/多选）、输入区（附件/@引用/命令/发送/停止）、待决徽标与聚合页；
5. **交互细则**：长按复制/引用/分享；侧滑操作；下拉刷新与「连接中」态；错误态与空态文案；弱网提示；
6. **快捷键与手势表（2in1）**：新建会话、搜索、切栏、发送、换行、停止、上下条导航、批量复制代码；
7. **通知文案规范**：审批/提问/完成/失败四类，含会话标题与动作摘要，不含敏感内容；
8. **无障碍规范**：可朗读标签（消息、卡片状态、按钮）、焦点顺序、动态字号、对比度 4.5:1；
9. **视觉与主题**：跟随系统、品牌色映射、深浅色 token 表、代码高亮主题与 Web 端一致性抽样验收。
