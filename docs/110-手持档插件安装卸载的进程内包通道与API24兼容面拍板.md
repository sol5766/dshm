## 1 根因：一条"spawn 到不了"的链路，与它的决定性反证

### 1.1 失败链（两份报告一致，本轮逐环复核到源码）

```
设置 → 插件 → 卸载
  └─ pluginManager/removeBundle                      （HTTP 一律 200，失败折叠进返回值）
      └─ dsh-plugin-manager types/index.js removeBundle()
          └─ runPnpm(['remove', name])               （:682）
              └─ operations.js runProfilePnpm()
                  └─ execa(options.command ?? 'pnpm', […])     ← 最后一跳，失败点
                      └─ <sandbox>/bin/pnpm  第 1 行 = #!/system/bin/sh
                          └─ execve(/system/bin/sh) ──✗ EACCES（三方应用域被拒）
                              ⇒ Node 抛 "spawn pnpm EACCES"
                                  ⇒ 假壳里唯一干活的实现（:173-223 写 <base>.rem）
                                      ⇒ **结构上不可达**（一行都没执行）
                                          ⇒ 清单未变、队列里也没有任何残留
```

### 1.2 决定性反证：PC/2in1 档上**同一个假壳能跑**

这一点是本轮的判据基础，必须在文档里钉住（否则下一轮又会有人去改 shebang 交差）：

```
[dshm-market-bridge] 随包 bin/pnpm 假壳可执行 ⇒ 不接管（市场走已验收的假壳链路）   ← 鸿蒙 PC 实测
exec 探测：… rg=ok, ash=ok, bash=ok, system-sh=ok   realShell=yes                   ← 同一台
head -1 <files>/bin/pnpm  =  #!/system/bin/sh                                      ← 旧 shebang 照旧
```

⇒ 假壳的 shebang **不是**"写错了"，而是"在本档无解释器可用"。因此：

- **方案 B（改 5 个假壳的 shebang）在手持档必然无效** —— 本档连 `/system/bin/sh` 都读不到，
  随手包 `ash` 也不行（`ash=denied`、`libsExec=err(EACCES)`）。报告 §4.6 已判"不要在这条路上花时间"。
- 反过来说，"改 shebang"在 PC 上是**行为不变**的（`#!/system/bin/sh` 本来就解析得动），
  所以它既不能修缺陷、也不会伤害 PC —— 它是**一致性整理**，不是修法。本轮**不做**，理由见 §6-3。

### 1.3 为什么纯配置解决不了

上游确实留了钩子 `profileContext.packageManager`（`types/index.js:340/:401/:729`、boot 里 `:261` 注入），
但它只能改"**spawn 哪个可执行文件** + 带什么 env"，最终仍落到 `execa(command, args)` ——
本档**任何** command 都点不着火（`toybox` 能跑，但实测**不带 `sh`/`ash` applet**：
`toybox-exec-sh=rc1` / `toybox-exec-ash=rc126`）。

⇒ 要修只能**在 `runProfilePnpm()` 内部、`execa` 之前**插一条分叉。这是核心补丁（`+dshm.*`）级别的事。

### 1.4 市场与设置页的**非对称性**（报告的第 10 环，也是本轮选址的依据）

同一个假壳、同一条队列协议：市场早已被 `@deepseek-ai/dshm-market-bridge` 救活（进程内写
`install-queue/*.req`，由宿主进程内的 `dshm-installer.js` 接单），**而同一处补丁没给
`dsh-plugin-manager` 任何东西** ⇒ "装得上、卸不掉"。
⇒ 本轮就是把这个"市场桥的客户端"复制成第二处使用（**方案 A**），而不是发明第三套协议。

## 2 判据与协议：与市场桥**逐条同源**

| 项 | 取值 | 为什么是这个 |
|---|---|---|
| 启用判据 | `shimRunnable()`：`spawnSync(<sandbox>/bin/pnpm, ['--version'])` 的 `status === 0` | 与市场桥同一函数同一写法。**能跑 ⇒ 本桥完全惰性**（返回 `undefined`，调用方照旧 `execa`）⇒ PC/2in1 档行为零变化 |
| 调试覆盖 | `DSHM_PROFILE_PNPM_BRIDGE=force` 强制接管 / `=off` 强制不接管 | 真机排障时能把"接管分支"从"假壳判据"里解耦，单独验通道 |
| 队列目录 | `$DSH_HOME/install-queue`；缺 `DSHM_HOME` 时按 `<HOME>/profiles/<name>` 反推 | 队列与 profile 永远同源，不会"装到别的 HOME 去了" |
| 投递 | `add` → `<base>.req`＋`<base>.dir`；`remove` → `<base>.rem`（`.dir` 用 `profileContext.dir`） | 与 `bin/pnpm` 假壳、市场桥**同一份协议**。`.dir` 是权威值（Host 原样采纳）⇒ 不能写错 |
| 取值口径 | `--dir`/`--profile` **连值一起跳过**，其余 `-` 开头单跳过 | 与假壳 `shimSkipOptValuesLines()` 同口径。真机踩过：`--dir /x/y` 的 `/x/y` 会被当成第二个包名 |
| 结果 | Host 回写 `<base>.done`/`.fail`（JSON），桥读到即删自己那份 | Host 只在 mtime 超 1h 时清陈旧文件 ⇒ 正常路径必须自清 |
| 接管面 | **只** `add|install|i` 与 `remove|rm|uninstall` | 其余子命令（`view`/`config`/`list`…）返回 `undefined` ⇒ **照旧 spawn**。与其假装成功，不如如实沿用原有失败形态 |

## 3 落实了什么

### 3.1 新增自带插件 `hostcore/plugins/dshm-profile-pnpm/`（`@deepseek-ai/dshm-profile-pnpm`）

导出四件（全部为离线可断言）：

| 导出 | 作用 |
|---|---|
| `shimRunnable(env)` | 同步探随包 `bin/pnpm --version`（与市场桥同判据） |
| `queueDirFor(profileDir, env)` | `$DSH_HOME/install-queue`（缺 `DSHM_HOME` 时反推） |
| `bridgeTargets(args)` | **命令字之后**取目标（`--dir`/`--profile` 连值跳过） |
| `bridgeRunProfilePnpm(args, ctx)` | 主入口：`undefined`（不接管）/ `{ exitCode, text }`（接管） |

纪律：**不新增权限、不动用户数据**（只写 `install-queue`，真正的改动由宿主进程内的
`hostcore/app/dshm-installer.js` 的 `installSpec`/`removeSpec` 完成 —— 与假壳走的是同一个函数）；
**失败不抛**（任何异常收敛成 `{ exitCode: 1, text }`，与 `execa` 失败同形）；失败文案是**中文、可行动**
（它会被上游 `throw new Error(output)` 原样呈现给用户 ⇒ 报告 §4.6 的方案 C 顺带落地）。

### 3.2 `tools/pack-core.mjs` 的注入 `patchProfilePnpmBridge()`

- 打的是 `@deepseek-ai/dsh-plugin-manager/lib/types/operations.js`，标记 `DSHM_PROFILE_PNPM_BRIDGE`。
- **锚点**（上游原文，逐字）：兼容性预检的拒绝分支
  `if (preflight.length > 0) / return rejected(preflight, 'nothing was installed');`
  ⇒ 注入点落在**预检之后、`const cancellation = new AbortController()` 之前**：
  回滚语义（profile 清单快照 + `rejected`）**一个都没动**，而 `execa` 还没被调用。
  此处 `log`/`append`/`output`/`truncated`/`logPath`/`incompatible` 都已在作用域内。
- **返回形状与 execa 路径完全一致**（`{ exitCode, output, truncated, logPath, incompatible }`）并写进
  同一份 `.plugin-manager/logs/operation-<id>/pnpm.log` ⇒ 上游"失败 ⇒ `throw new Error(output)`"
  链路**一个字都不用改**（UI 报错文案链路原样）。
- 幂等（按标记跳过）；**找不到锚点即 `die`** —— 上游改了这段就在**打包期**暴露，而不是静默失效成
  "平板档又卸不掉插件了"。
- 自带插件清单 `DSHM_PLUGIN_PACKAGES` 加一项；`embedDshmToolPackages()` 的**集合回归锁**因此
  从 6 个 `dshm-*` 变 7 个（树内目录集合 = `dsh-web-app` 依赖声明集合 = 清单，三处相等）。

### 3.3 `coreVersion` `+dshm.9` → **`+dshm.10`**

核心树内容变了（新增插件 + 新注入）⇒ 按 `AGENTS.md` 的"升版本"铁律递增，端侧目录名与自检输出
都能一眼看出设备在跑哪一版。出包带 `--place-in-app`，随后 `check-resfile-core-zip.mjs`
断言 resfile 里**只有 1 份容器**且 sha256 与配方、与本次产出三者一致（实测 `c990e802…`，85,212,985 B）。

### 3.4 门禁

| `tools/check-profile-pnpm-bridge.mjs`（新增） | **离线**、进 CI | A 启用判据（含"假壳真能跑 ⇒ 不接管"的**对照臂**）/ B argv 口径 / C `.rem` 与 D `.req` 分流 / E 失败语义 / F 拒绝面 / G 取消 / H 打包三处接线。另有 `--self-test`：**4 个变异体**各改一处源码锚点（`VALUE_OPTS` 清空、`REMOVE_COMMANDS` 清空、`.rem` 改写成 `.req`、`off` 开关失效）⇒ 对应判据必须红（证明不是恒真摆设） |

## 5 API 24 兼容面拍板（把 `docs/108` §6-2 结掉）

### 5.1 拍板：`compatibleSdkVersion` = **`6.1.1(24)`**（与 `targetSdkVersion` 一致）

`docs/108` §1 把本地那份改成 `6.1.0(23)` 只做了一件事——**证明"能更低"**（编译期 0 ERROR，
代码侧代价是 6 处 `Circle().fill()` 的重载遮蔽，已改成视觉等价的 `Row + backgroundColor`）。
那一轮的 §6-2 把"最终取 23 还是 24"留给用户拍板。**本轮用户口径：面向平板端、API 24** ⇒ 取 **24**。

三条理由（按权重）：

1. **没有 API 23 的验证设备** ⇒ 把未验收的兼容面（23）当成产品口径，等于对用户承诺我们没跑过的档位。
   24 与 `targetSdkVersion` 一致，也是 `README.md` 的「构建」小节与 `docs/device-validation.md` 的 D4 记的**既有决策**
   （2026-09-14"暂保持 24"，沉浸光感因此不用 —— `HarmonyMaterial.IMMERSIVE_ENABLED = false` 是配套决策）。
2. **23 相对 24 只多一层"未验收的向下"**，对"修一层 API 就要重测一轮"的成本结构不划算；
   真需要覆盖 6.1.0 设备时是**一行**改动（`compatibleSdkVersion` 回 `6.1.0(23)`），路径已在 `docs/108` §1 留全。
3. 与"PTC/沙箱等运行期能力"无关：那些是**运行时**判据（`docs/104`/`108`），不随 API 级别变化。

### 5.3 仍未做 / 不在本轮范围

1. **API 24 真机未实测**（本轮只有 PC/2in1 与"设备侧报告所述平板"间接证据）⇒ 装机后请用户
   在平板档按 §7 复核；`minAPIVersion` 只保证"装得上"，**不保证**运行期逐项可用。
2. **"6.1 设备装不上"的第二个候选原因与我们无关**：调试签名 profile 的

3. **不申请三条目录权限**（`READ_WRITE_{DOWNLOAD,DOCUMENTS,DESKTOP}_DIRECTORY`）：裁定仍走 `docs/108` §2.3 的
   方案 A（零权限 + 回落提示），因为方案 B 要动**签名面**，与"别把 PC 端改坏"直接冲突。

## 6 未做项与遗留（都写了理由，避免下一轮从错前提出发）

1. **报告 §4.7-1（Host 侧是否实现 `.rem`）—— 答复：实现了**。
   `hostcore/app/main.js:5093-5103` 显式匹配 `.rem` 并调 `pluginInstaller.removeSpec()`
   （`:5183`），实现在 `hostcore/app/dshm-installer.js:1181 / :1296`（`:1174` 的注释就写着
   "web 插件页『卸载』通过 pnpm rm → 假壳写 .rem 请求 → 本函数"）⇒ **方案 A 的第一前提成立**。
2. **报告 §4.6 的三条验收用例（卸载 `billion-context`、再装卸 ×2、重启回归）留给真机**：
   它们要动用户的真实 profile 清单，属于"用户界面触发"的动作，不由开发端代跑。
   `billion-context` 当前仍在清单里，正好是一号用例。
3. **不做方案 B（统一 5 个假壳 shebang）**：§1.2 已证它在手持档**点不着火**（本档没有任何可 execve
   的解释器），在 PC 上又**行为不变** ⇒ 当前没有任何档位会因此变好。触发条件写在这里：**若将来出现
   "`ash=ok` 且 `/system/bin/sh` 不可用"的档位**，就把这 5 处与 `bashShimLines()` 同法（`interpreterShebang(binDir)`
   两形态探测）一起改 —— 那时它才是修法。现在的形态差异已记进 `ohos-shell` 技能口径。
4. **失败后的半状态**：本轮**不做**额外清理。理由：接管分支的失败是"宿主安装器给的原因"，
   `.fail` 的文案就是安装器写的；上游 `runProfilePnpm` 自己保存 `package.json`/`pnpm-lock.yaml`
   快照并在拒绝时 `restore()` —— 加一层清理反而会与上游语义打架。
5. **报告 §5 的两条"顺带观察"未结**：`dsh-hos-scrcpy` 那次安装的 `aborted` 措辞（像被主动中止），
   以及 `@linxin666/dsh-pet@0.4.5` 记为 `exit=0 hot=true` 却不在清单/`node_modules` 里。
   两者都在**市场通道**上，与本轮的设置页通道无关；登记为待查（需要宿主侧日志，超出该报告的可观测面）。
6. **不升 `targetSdkVersion`**：保持 24（决策 2026-09-14，沉浸光感不可用的代价已入档）。

## 7 复测步骤（真机）

**平板 / 手机档（本轮的主目标）**

1. 覆盖安装新包（**只走 `.\tools\update-device.ps1`**，它只用 `hdc install -r` 且装后验数据）。
2. 设置 → 插件 → **卸载**一个还在的包（报告现场现成用例：`billion-context`）。
