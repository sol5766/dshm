## 0. 移植的两个根本约束（先说这两条，后面所有坑都是它们的推论）

整场移植的困难几乎都可回溯到下面两条。**先理解它们，再看具体坑会快得多**。

### 0.1 约束一：`jitless` ⇒ `WebAssembly === undefined`

不申请 `ALLOW_WRITABLE_CODE_MEMORY`（该权限在手机上不可申请，E13）⇒ Host 全程 `--jitless` ⇒
V8 的 `--jitless` 与 `--expose_wasm` **互斥**（启动即打 `disabling flag --expose_wasm`）
⇒ **端侧 `typeof WebAssembly === 'undefined'`，恒定，不是配置问题**。

由此推出的一条对上游代码的硬判据：

> **凡上游直接 `import('undici')` 的功能，在端侧都会失败** —— undici 的 HTTP 解析器是 WASM。

已实证的受害者：`web_fetch`（`dsh-web-fetch-http` 自建 Agent + dispatcher）。而 `web_search`
正常，因为它走的是全局 `fetch`（我们的纯 JS 垫片）。**同一核心树、同一个本地 HTTP 服务，
只有 `--jitless` 一个变量就能复现两组结果**。

### 0.2 约束二：execve 受**签名域**策略管辖 ⇒ 第三方 ELF 全被拒

鸿蒙对"应用沙箱里执行第三方原生二进制"的判据**不是权限位、不是创建者、不是 inode**，
而是**签名域**。真机实测（E369 的对照实验**否定**了旧假设「执行许可绑创建者」）：

| 对象 | 能否 execve | 说明 |
|---|---|---|
| HAP 内随包分发的 ELF（**已签名**） | ✅ | `libnode.so`、我们自建的 `.so` |
| 系统二进制（`/system/bin/sh`、toybox） | ✅ | 内核 exec 的是**系统**路径 |
| **脚本**（`#!/system/bin/sh`） | ✅ | 因为内核 exec 的是**系统**那个解释器 |
| 我们写到沙箱里的**未签名 ELF**（busybox / rg / git / python3.12） | ❌ | `inaccessible or not found` |
| 同上，但**自签名后** | ✅ | `binary-sign-tool -selfSign 1` |

⇒ **所有要在端侧跑的原生二进制，都必须在构建期自签名**。这条约束直接决定了
`tools/pack-core.mjs`（签 core 树的 rg）与 `tools/place-toolchain.mjs`（签工具链归档）的存在。

### 0.3 由这两条推出的"能跑 ≠ 跑通"

本文反复出现的一个模式：**修掉一层后，下一层才浮现**。因为端侧工具链是
"起进程 → 找辅助程序 → 连远端 → 认证"这样的长链，每一环都可能被 0.1/0.2 波及。

## 1. 平台与进程模型

### 1.1 原生库不能从沙箱 `dlopen`，但可以从 HAP `libs/` 加载（E14 / E18 / E39④ / E40）

- **现象**：`Error loading shared library …/cores/<ver>/node_modules/koffi/build/koffi/linux_arm64/koffi.node: No error information`
- **根因**：运行时**解包到沙箱**的原生库，`dlopen` 被系统拦；而放在 HAP `libs/` 里的**不拦**
  （E18 已证，**即使没有 `.codesign` 也能加载**）。
- **修法**：核心树里的原生件（koffi / node-pty / sharp，共 3 个包）**必须由 HAP 的 `libs/` 提供**。
  ⇒ 副作用（重要）：**"核心版本切换"只能切纯 JS 部分，原生部分与应用版本绑定**。
- **落地**：`main.js` 的 `NATIVE_LIBS` 重定向——见 §1.3。

### 1.2 hvigor **只打包扁平的 `libs/<abi>/*.so`**（E40①）

- **现象**：把 `build/koffi/linux_arm64/koffi.node` 放进 `entry/libs/arm64-v8a/`，**构建产物里没有它**
  （嵌套的 `.node` 不会被复制进 HAP）。
- **修法**（不碰任何第三方包）：原生包的 loader 在 `require` 之前都会先 `fs.existsSync(候选路径)`，
  而真正加载 `.node` 一定经过 `Module._extensions['.node']` ⇒ **同时接管这两处**，
  把沙箱内的 `.node` 请求**重定向**到 HAP `libs/` 下的扁平文件。命名约定：`lib<去掉扩展名的包名>.so`。
- **真机验证**：`原生库重定向已启用：libs=/data/storage/el1/bundle/libs/arm64`

### 1.3 `.node` 的符号作用域：`DT_NEEDED` 是**结构性**保证，事后补丁只是权宜（E40 / E43 / E44 / E51）

- **现象**：`Error relocating …/libkoffi.so: napi_fatal_error: symbol not found`，
  而 `libnode.so.127` **确实导出**这些符号（`nm -D` 可见 196 个 `napi_*`）。
- **根因**：**不是符号不存在，而是 `dlopen` 出来的对象看不到 libnode 的符号**。
  dlopen 的对象按「自身 + 依赖闭包 + 全局组」解析；`libkoffi.so` 的 `DT_NEEDED` 只有
  `libc++_shared.so` / `libc.so` ⇒ 它的作用域里**一个 Node 运行期符号都没有**。
  **musl 下 `RTLD_GLOBAL` 首载也进不了后续 `.node` 的可见集**（E43 实测）。
- **修法（两个层次）**：
  - **权宜**（E43）：原地改写 `libkoffi.so` 的 `.dynstr`，把 `DT_NEEDED: libc++_shared.so`
    （16 字节）改成 `libnode.so.127`（14 字节）+ NUL 补齐——**等长内更短 ⇒ 纯字节替换，
    不动 ELF 任何结构/偏移**。工具 `tools/patch-native-needed.mjs`（幂等 + `.orig` 备份）。
  - **正解**（E51）：**自建 koffi 3.x**，用 CMake `MODULE` 目标把它加进
    `entry/src/main/cpp/CMakeLists.txt` ⇒ 链接器保证依赖闭包（`NEEDED: [libnode.so.127, libc++_shared.so, libc.so]`），
    **不再依赖事后字节补丁**。
- **附带坑**（E44）：**node-pty 的报错文本会把人带偏**——它把每个候选的异常都记进 `lastError`
  再统一抛，最后留下的是**最后一个**候选的 `Cannot find module './prebuilds/linux-arm64//pty.node'`，
  而真正失败的是**前一个**候选（解析成功、**重定位失败**）。照着它的文本去补文件会白忙。
- **附带坑**（E41①）：把 `libnode` 从 `libdshhost.so` 的 `DT_NEEDED` 里去掉后，**真机零日志**
  （连一条 `DSHM-*` 都没有）——因为 `dlopen("libnode.so.127")` 按**裸 soname** 找库，
  而 bundle 的 libs 目录未必在默认搜索路径里。修法：用 **`dladdr` 问出本 `.so` 自己的路径**，
  同目录下的 `libnode.so.127` 用**绝对路径**首载。
- **额外坑**（E41④）：**hilog 默认缓冲太小**，`hilog -G 64M` 被拒（上限 16M），
  应当用 **`hilog -G 16M`** —— 这一步没做会白费数轮读数。

### 1.4 `libuv` 的 `io_uring` 在鸿蒙被 seccomp 杀（E42）

- **现象**：`SIGSYS(SYS_SECCOMP) syscall 425`。
- **根因**：`deps/uv/src/unix/linux.c:482` **仅**在 `!(flags & UV__IORING_SETUP_SQPOLL)` 时才读
  `UV_USE_IO_URING` 环境变量 ⇒ **设环境变量那条路根本走不到**。
- **修法**：改源码为**无条件 `return 0`**，重建 libnode。
- **意义**：这是**"自建 Node 能在鸿蒙上跑"的第一条完整正面证据**。

### 1.5 平台标识 `linux` 而移植件在 `openharmony_arm64`（E39②）

- **现象**：真机读数 `platform=linux arch=arm64`（gyp `OS=linux` ⇒ Node 按 linux 编译），
  而 OHOS 移植件放在 `openharmony_arm64` ⇒ koffi 按 `platform_arch` **找不到**。
- **修法**：`pack-core.mjs` 增加**复制**形式的平台别名（`linux_arm64` / `musl_arm64` /
  node-pty 的 `linux-arm64`）。**【注意】沙箱禁符号链接 ⇒ 必须用复制，不能用 symlink。**
- **同源坑**（E368）：`flock.js` 的平台门**只认 `linux`/`darwin`**，而端侧
  `process.platform === 'openharmony'` ⇒ **会话恢复失败（"无法对话"）**。
  修法：非 win/darwin 一律按 linux 处理。

### 1.6 `flock` 自建：npm 的预编译件在端侧**符号解析不到**（E103）

- **根因**：npm 上的 musl 预编译件**只 `DT_NEEDED libc.so`**，dlopen 后 napi 符号解析不到
  （与 koffi 同一个坑）；且 `libc.so` 是必需项、**不能被替换掉**。
- **另一个原因**：npm 在 Windows 上装树时**不会**装 `@deepseek-ai/node-addon-system-linux-arm64`
  （optionalDependencies 只装当前平台），而端侧 `process.platform=linux/arch=arm64`
  ⇒ 加载器找不到它（真机报错：`Cannot find module '@deepseek-ai/node-addon-system-linux-arm64/package.json'`）。
- **修法**：**自建**（`node-addon-system/src/flock.c` 用 CMake 编，显式把 `libnode` 写进链接行）。

### 1.7 子进程类操作：平台 libc 缺"取消点控制"（E376）

这是移植中最"典型"的一类坑——**上游代码把平台调用当成"不该失败"**。

- **现象**：`git clone / fetch / pull / push / ls-remote` 一律 `rc=134`（SIGABRT）：
  ```text
  BUG: run-command.c:525: disabling cancellation: Operation not permitted
  ```
- **根因**：git v2.47.3 `run-command.c` 的 `atfork_prepare()`：
  ```c
  CHECK_BUG(pthread_sigmask(SIG_SETMASK, &all, &as->old), "blocking all signals");
  CHECK_BUG(pthread_setcancelstate(PTHREAD_CANCEL_DISABLE, &as->cs), "disabling cancellation");
  ```
  `CHECK_BUG` 的语义是"**这个调用不该失败**"——失败即 `BUG()`（abort）。而**鸿蒙 musl 缺
  取消点控制**（该调用返回 EPERM）。⇒ **不是 git 用法错，是平台 libc 缺这一块能力**。
- **修法（不重编 git）**：新增 `entry/src/main/cpp/gitcompat.c` → `libdshm-gitcompat.so`，
  对这两个调用做 **LD_PRELOAD 垫片**。口径是**透明优先**：
  **先调 libc 真身，真身成功就原样成功**；只在真身缺失或返回非 0 时才改判成功
  （⇒ 在真 Linux 上完全透明，不掩盖真实错误）。
  - **两个一起兜**：只兜 `pthread_setcancelstate` 会在修好后紧接着炸在同块的 `pthread_sigmask`。
  - `DT_NEEDED` **仅 libc.so**（LD_PRELOAD 的库若拉几十 MB 的 libnode 会污染 git 进程）。
- **为什么不是重编 git**：git 是**动态链接的 PIE**（`DT_NEEDED libc.musl-aarch64.so.1`，
  用**系统 musl**、我们没随包带 libc）⇒ 重编要配整套 Alpine musl 交叉工具链，且产物还要再过签名域。
- **第二层（修好第一层后才浮现）**：垫片生效后 stderr 变成
  `git-upload-pack: inaccessible or not found` ⇒ `usr/libexec/git-core/` 下 **141 个 symlink**
  （138 个指向 `../../bin/git`）在 hmfs 上**解不出来** ⇒ 子命令辅助程序一个都不存在。
  原先的 `GIT_SYMLINK_REPLICA` **只硬编码了 1 条**。
  修法：`readGitCoreSymlinks()` —— **从本版 git 的 apk 归档直接读 symlink 表**
  （纯 JS 扫 tar 头，不解包），按需以**真身拷贝**补齐。⇒ 名字永远与这一版 git 一致。
- **顺带**：`git init` 的 "templates not found" 警告 → 显式设 `GIT_TEMPLATE_DIR`（存在才设）。
- **判决性验收锚点**：`execProbeTargets()` 新增 `git-ls-remote` —— `git ls-remote file://<本地裸仓库>`。
  它会走 `start_command()`（即那两处 `CHECK_BUG`），但**不需要网络**，是最小、可重复、
  不受外部服务波动影响的判据 ⇒ 每次启动自动产出机器可读结论。

### 1.8 `process.execPath` 兜底与 relaunch 助手（E372）

- **现象**：`spawn` 自身的 `process.execPath` 会失败。
- **修法**：`installExecPathSpawnGuard()` 包装 `spawn/execFile/execFileSync/spawnSync`，
  命中时以 `EPERM` 拒绝；**但放行 relaunch 助手**（`args[0]==='-e' && args[1].includes('waitForParent')`
  → `requestAppRestart()`），否则"重启"能力被自己的守卫挡住。

### 1.9 `cwd` 为 `/` 是一切的起点（E370 / 报告 7 §1a）

- **现象**：`EACCES: mkdir '/node_modules'`。
- **根因**：dsh 起子进程时 **cwd 常为 `/`**（真机已证），宿主安装器按"请求方 cwd"落位 ⇒ 装到根目录。
- **修法**：假壳里统一归一化 —— `--dir` > **有效** `$PWD`（非空且非 `/`）> `--profile` >
  `host-ready.json` 的 profile > 常量 `ondevice`。见 §4.2。

### 1.10 bash 子进程的 env 是**白名单**构造（批次十）

- **现象**：pnpm 假壳报 `pnpm(shim): 缺少 DSH_HOME 环境变量（Host 未注入 PATH 环境）`。
  （相比更早的 127 `command not found`，这是**前进一层**：假壳已被 PATH 找到并执行，
  撞到的是假壳自身的运行时 `$DSH_HOME` 读取。）
- **根因（上游证据，非猜测）**：`dsh-bash-local` 的 `spawnSpec`（`lib/index.js:209`）
  构造 bash 工具子进程环境为**白名单合并**
  `{...ENV_OVERRIDES, ...spec.env, ...spec.dshEnv}` —— **不 spread Host `process.env`**。
  `ENV_OVERRIDES` 只有 NO_COLOR/TERM/PAGER/GIT_PAGER 四项；PATH 经 `spec.dshEnv` 到达
  子进程（所以假壳找得到）；而 `main.js` 设的 `process.env.DSH_HOME` **两头都不沾**
  ⇒ **子进程里恒空**。
- **顺带的教训（两枚）**：
  - **旧报错文案是误导的**（PATH 与 `DSH_HOME` 是两回事）；
  - **上轮 `npx -v ✓` 没暴露此洞**，因为 `-v` 快速分支排在 `DSH_HOME` 检查**之前**
    ⇒ **版本探测不等于功能路径探测**。
- **修法**：不再运行时读 `$DSH_HOME`，改为**生成时写死** `QDIR="${HOME_DIR}/install-queue"`
  （与 python 垫片写死 `HOME_DIR`/`PORT` 同模式）；另加 `HOME_DIR` 空串守卫
  （不布置，退化为 127 行为）。
- **门禁补缺**：原四套断言**均未覆盖 CLI 假壳** ⇒ 新建 `tools/assert-cli-shim.mjs`（19 项），
  并**负测试先行**（对修复前 `main.js` 跑出 `FAIL 1` 后才改代码）。

## 2. 文件系统（hmfs）

hmfs 是鸿蒙的应用沙箱文件系统，它有一组**与常规 Linux 不同**的行为。这一节是移植中
second-most 容易踩的地方（仅次于 §1）。

### 2.1 元数据**全不可信**：`stat`/`lstat`/`access` 会撒谎（批次五·七）

- **现象**：`bin/` 里 `ash`/`bash`/`busybox`/`nc`/`unzip` 5 个文件 stat 显示 `?????`
  （hdc 视角元数据不可读），其余 7 个完好。
- **更狠的一例**：apk 内 `git-remote-https` 本是 symlink → `git-remote-http`，
  tar 在 hmfs 留下"**残缺链接占位**"（`l????????`），而 Node 的
  `statSync`/`lstatSync`/`accessSync` 对占位**全部返回成功且 `mode=0777`**
  （symlink 固有 x 位）⇒ **按元数据判"可执行"永远被骗**，补齐逻辑被跳过。
- **修法**：判据只用**真实数据面** —— `isElf()`：`open` + `read` 前 4 字节验 ELF magic
  （`\x7fELF`）。**骗不了**。

### 2.2 "封存态"：曾布置过的文件可能 chmod 与覆盖写**都被拒**（批次五③）

- **现象**：03:04 首次布置 busybox 11 副本成功（全新文件 chmod 755 通过）；06:10 幂等
  chmod 仍通过；**07:57 起每次 boot 对同路径 chmod 全部 EACCES**。
- **后果**：`ensureBusybox` 按设计整体放弃返回 `''` ⇒ PATH 未注入 ⇒ 假壳/wrapper/解包**全链跳过**
  ⇒ **四命令（python3/git/npx/rg）全 127**。
- **修法**：`rewriteExecutable` —— 直写 → 失败 → **删除重铺全新 inode** → chmod → X_OK；
  **删除重铺实证可救**。健康快路径改双条件（`statSize` 一致 **且** `execOk`）+
  `bin-<pid>` fallback 目录 + `cleanupStaleBinDirs`。

### 2.3 tar 的 `settime` 在 hmfs 上恒 EACCES，但**内容与权限恢复不受影响**（批次五⑤）

- **现象**：解包 4530 文件全部 `tar: settime: Permission denied`。
- **实测**：**内容与权限恢复不受影响**（`python3.12` 23MB `rwxr-xr-x` 实证，`mode 755`
  由 tar 正常恢复）。
- **修法**：`tar -m`（`--touch`）—— 消掉噪音与 `tar: had errors`。
- **推论**：**不要因为看到 EACCES 就认为解包失败**；要看真实数据面（文件大小 + ELF magic）。

### 2.4 symlink：属主**透明跟随**，hdc 看到的拒绝只是跨 uid 观测限制（批次五⑧）

- **现象**：hdc（shell uid）对 symlink 占位 `stat`/`open` 全拒；而 **app（属主 uid）
  `open`+`read` 占位成功且读到真身 ELF**。
- **结论修正**：D6 §4.1.3 的"沙箱禁 symlink"限定于**其探针场景**（mkdir/创建期 EPERM）；
  files 区 tar 场景对属主是"**跟随可用、元数据撒谎**"。
  ⇒ `git-remote-https` **实际可执行、无需补齐**（`isElf` 防御保留兜底）。
- **但仍不能用 symlink 归档**：见 §6.4（Windows 侧 tar 处理）。

### 2.5 tar 在 Windows 上**无法从归档创建 symlink**（E373）

- **三种工具的行为**（实测）：
  | 工具 | 行为 | 后果 |
  |---|---|---|
  | `bsdtar` | **丢弃 symlink 条目** | **不可逆地损坏归档** |
  | `7z` | 把 symlink **物化**成真文件 | git-core 8MB → **1.3GB** |
  | **Python `tarfile`** | 逐条目复制，symlink 保持 symlink | ✅ **唯一安全** |
- **修法**：`tools/sign-tar-elf.py`（基于 `tarfile` 的逐条目改写）。
  ⇒ 这也是为什么 **README 把 Python 3 列为构建前置**。

### 2.6 删除大目录会锁死 ArkUI 主线程（E45）

- **现象**：换核心包后启动，应用"起来就消失"，`pidof` 为空且**连一条 `DSHM-*` 日志都没有**。
- **系统日志真因**：`Reason:LIFECYCLE_TIMEOUT` + `FreezeDetector: SaveFreezeExtInfoToFile`。
- **根因**：`BundledCore.installBundledCores` 用 `fs.rmdirSync(旧核心树)` 删
  **216 MB / 25k 文件**，这是在**主线程**上做的（异步函数里的同步段同样阻塞 ArkUI 线程）。
- **修法**：改为 `fs.renameSync` 挪成 `<coreDir>.stale-<ts>.tmp`（毫秒级元数据操作；
  `.tmp` 后缀被 `CoreStore.listInstalled` 明确忽略），安装末尾再用**异步** `fs.rmdir` 清理。
- **纪律**：**安装/删除路径上不得出现任何"删几万个文件"的同步调用。**

### 2.7 25k 文件树的删除在桥里超时（批次十一·二）

- **现象**：python 桥 `shutil.rmtree` / `os.system rm -rf` 25k 文件树 → `rc=124`
  （桥 `run-get` 默认 120s SIGALRM 超时）。
- **修法（两步）**：① `os.rename` 成 `.tmp` 后缀（**原子瞬间完成**，`listInstalled`
  立即视同不存在）；② `os.system('rm -rf …')` 配 `&timeout=300`（`run-get` 参数 clamp 1..300）
  后台慢删。

### 2.8 `fs.mkdirSync(path, true)` 与 Node 的 `recursive:true` **语义不同**（E32）

- **现象**：`建立端侧核心目录失败：13900015 File exists`。
- **根因**：OHOS 的 `fs.mkdirSync(path, true)` 在**目标目录已存在时抛错**，
  而 Node 的 `recursive:true` 是幂等的 ⇒ "幂等"的 `ensureLayout()` 第二次调用**必然失败**
  （安装与启动都会调它）。
- **修法**：先 `fs.accessSync` 判存在。

### 2.9 `hdc shell` 读不到应用私有目录（贯穿全程）

- **可读**：`files/`（含 `files/bin/`、`dshm-host.log`、`node-output.log`）。
- **不可读**：`dsh/home`（**700**）—— 所以 `host-ready.json`（含 token）取不到；
  `toolchain/` 目录也读不了。
- **不可读**：`cacheDir`（`Permission denied`）⇒ **诊断日志落点必须用 `filesDir`**（E32②）。
- **推论**：**凡需要跨 uid 观测的东西，都必须由宿主自己写到 `files/` 下**。
  这条直接催生了 §7 的"诊断通道"设计。

## 3. 打包与资源

### 3.1 **HAP 打包丢弃所有 dot-前缀条目**（E369 踩坑二）

- **实测**：dotfile 条目数 = **0**。
- **后果**：用 `.dshm-signed` 做签名标记 ⇒ 标记**丢了** ⇒ 端侧永远认为"未签名"。
- **修法**：标记文件名**不能以点开头** ⇒ 改成 `dshm-signed.txt`。

### 3.2 签名产物会**被后续补丁覆盖**，位置必须排在最后（E369 踩坑一）

- **现象**：签名"做了但无效"。
- **根因**：最初把 `selfSignNatives()` 放在 `replaceKoffiJs()` 之后，而
  `ensureRipgrepPlatformPackage()` 会**重写 rg** ⇒ 把签名冲掉。
- **修法**：移到 `pack()` 之前。⇒ **构建流水线里"改写产物"的步骤之后才是签名**。
- **顺带**：`pack-core` 的补丁顺序是显式的（见 `docs/50` §12.10）——
  顺序本身就是知识，改动要连着顺序一起想。

### 3.3 "**存在即跳过**"的缓存判据必须配**版本标记**（E369 踩坑三 / E47）

- **现象**：端侧的"存在即跳过"门（`gitReady()` / `pythonReady()`）让**构建期的改动永不到达设备**
  （签名改了，设备上还是旧文件）。
- **修法**：加版本标记文件（`TOOLCHAIN_SIGN_MARKER = 'dshm-signed-v1'`）+
  `readArchiveSignMarker` / `readExtractedSignMarker` / `needsReextractForSign` ⇒
  **标记不符就强制重解包**。
- **同一类坑的第二处**（E39③）：`BundledCore` 原先"版本已装即跳过"，
  导致**换了核心包端侧仍跑旧树**。改用**资源包大小**做指纹（写在 `<coreDir>/.dshm-bundled-stamp`）。
  > **这不只是为调试** —— 否则"核心版本安装/切换/回滚"这条功能形同虚设。

### 3.4 资源路径与 `resourceDir`

- HAP 内的资源在安装后解压到沙箱，可按**真实路径**只读访问 ⇒ 入口脚本以
  `<resourceDir>/resources/app/main.js` 的真实路径被读取。
- **因此入口脚本必须是 HAP 里的真实文件**（不能是软链/引用）——见 §3.5。

### 3.5 入口脚本一度从 HAP 里消失（阶段一 Electron 链移除的余波）

- **现象**：HAP 内不再有 `resources/resfile/resources/app/` ⇒ **Host 永远起不来**。
- **根因**：入口原先靠 `web_engine` 那个 HAR 的 resfile 合并进 HAP；Electron 链移除后，

  （`hostcore/app/` → `resfile/resources/app/`）。

## 4. dsh 上游集成（profile / 插件 / 安装器）

这是"移植"里最像"移植"的一节：**上游是为一台常驻桌面机设计的，端侧的生命周期与
文件布局都不同**，于是每一处假设都要单独核对。

### 4.1 `--jitless` 引爆 undici ⇒ 必须**两层**垫片（E35–E39）

**定位链条**（值得整体记住，因为它是"顺着栈帧找真凶"的范例）：

| 步 | 假设 | 实验 | 结论 |
|---|---|---|---|
| E35 | 加 `--no-experimental-fetch` 能不装 fetch | 症状**不变** | 仍有代码显式用 undici |
| E36 | 覆盖 `globalThis.fetch` | 症状**不变**；且**不能先读原值**——Node 用 getter 惰性装 `fetch`，一读就触发 undici 初始化 | 触发者不是 `fetch` |
| E37 | 只有两个包用 undici：`dsh-web-fetch-http`、`dsh-http-proxy` | 两次"禁行"实验**都无效** | **保留意见**：patch 格式**从未验证**过，所以否定结果什么也证明不了 |
| E38 | 加大栈深度 | 关键帧 `at lazyUndici (node:http:123:21)` | 触发者是 **`node:http` 自带的惰性 undici 加载器** |
| E38 | 把 `dsh-http-proxy` 移走 | 错误变成 `ERR_MODULE_NOT_FOUND`，且 **boot 文件哈希变了** | ① 该包被 profile boot **静态 import**，**不能靠删包绕开**；② **patch 确实生效**（哈希变化是证据） |
| E39 | 封掉 `node:http` 上全部惰性 getter | 症状**消失**（本机 + 真机） | ✅ 真凶确认 |

**修法（两层，缺一层就会出现"Host 起来了、模型也能回话，但某个工具静默坏掉"）**：

| 层 | 做什么 | 不做的后果 |
|---|---|---|
| 全局 fetch 垫片（`fetch-shim.js`） | 用 `node:http/https`（原生 llhttp）重写 `fetch/Request/Response/Headers/FormData` | **调模型就走不通**（dsh 调模型就是用 fetch） |
| `undici` **模块名**解析钩子（`undici-shim.mjs` + `undici-loader.mjs`） | 让上游的 `await import("undici")` 拿到同一个垫片，并把 `dispatcher` 翻译成 `lookup` | **`web_fetch` 打不开任何网页**（`web_search` 却正常，因为后者走第一层） |

第二层由 `main.js` 的 `installUndiciNameHook()` 在 `WebAssembly` 不可用时注册；
**不改上游源码、不改核心树**。由 `tools/check-web-fetch-jitless.mjs` 守着——它自带对照实验：
不注册钩子时必须失败（并给出 WASM 因果证据），注册后必须全过，且**跨源跳转仍须被拒**。

### 4.2 假壳（`pnpm`/`npx`/`dsh`）：端侧没有 node 包管理器（E86 / 报告 1 / 报告 7）

dsh 的插件安装链 spawn 的是 `pnpm` / `npx` / `dsh` CLI，**端侧一个都没有** ⇒ 用**POSIX sh 假壳**
把命令转成"安装队列投递"（Host 进程内安装器接单；协议 `*.req` → `*.done`/`*.fail`）。

踩过的坑（按发现顺序，**都是"各写各的又各漏一处"**）：

| # | 坑 | 现象 | 修法 |
|---|---|---|---|
| 1 | bash 子进程 env 白名单 | 读 `$DSH_HOME` **恒空** | 生成期把路径**写死进脚本**（§1.10） |
| 2 | `--dir <path>`（**空格形式**）只被"跳过"、**从未取值** | 市场 `prefetch()` 的**隔离预取失效** ⇒ 包落进 profile、临时目录空 ⇒ 市场读不到 manifest ⇒ `installed package manifest missing`，且包/行/依赖全部泄漏到 profile | 用"下轮取值"标志（`want_dir`）**同时完成取值与消费** |
| 3 | 单引号 JS 字符串里的 `${HOME_DIR}` **不插值** | 脚本里是**字面量** `${HOME_DIR}`（shell 展开成空）⇒ 归一化路径变成 `/profiles/<name>` | 凡出现 `${HOME_DIR}` 的行一律用**模板串** |
| 4 | `npx` / `dsh` **根本没有** `--dir` 解析 | `.dir` 直接写 `$PWD`；而 cwd 常为 `/` ⇒ `EACCES: mkdir '/node_modules'` | 三处统一走**共用**的归一化函数 |
| 5 | **count 循环没跳过 `--dir` 的值** | `--dir /tmp/x` 的 `/tmp/x` 被当成第二个包名（`count=2`）⇒ 若用户只给 `--dir` 不给包名，会误判"有包" | 第一趟计数与第二趟投递**同款消费口径** |

**"共有片段"的修法**（报告 7 §1）：抽出 `shimDirResolveLines()` / `shimSkipOptValuesLines()`，
三个假壳统一调用 —— 报告指出**三处各写各的正是漏因**。

**验收（在设备上用真实脚本跑）**：
```text
pnpm add foo --dir /tmp/x   → DIR_OPT=[/tmp/x]        (§1c 空格形式)
pnpm add foo --dir=/tmp/y   → DIR_OPT=[/tmp/y]
pnpm add foo   (cwd=/)      → DIR_OPT=<HOME>/profiles/ondevice   (§1a 归一化)
dsh plugin --profile ondevice install foo → DIR_OPT=<HOME>/profiles/ondevice
```

### 4.3 `dsh` 里"禁一行"**不是局部操作**（E53）

- **现象**：只禁了 8 行，却出现 `dsh: 4 entries did not activate`：
  ```text
  permission-presets: pending (waiting for service: shell)
  api-session-controller: pending (waiting for services: attachments, fileUploads)
  client-file-upload: pending (waiting for service: attachments)
  client-ui-deliverables: pending (waiting for service: sessionController)
  ```
- **根因**：**禁一行会沿服务依赖链把消费者拖成 pending**，而 boot 要求**所有行都 activate**。
  两条链：`attachment-local`(attachments) → `file-upload`(fileUploads) →
  `session-controller`(sessionController) → 客户端行；`bash-sandbox`/`pwsh-sandbox`(shell) →
  `permission`(permission-presets)。
- **附带坑（静默失效）**：patch 里的 **id 与包名不同名** ——
  `@deepseek-ai/dsh-permission-presets` 的行 id 是 **`permission`**。写成 `permission-presets`
  时 patch **静默不生效**（无任何报错），表现为"禁了却仍 pending"。
  ⇒ **写 patch 前必须回查 `dshm-core.json` 的 `plugins[].id`**。

### 4.4 preset 副本在 `isolate` 作用域内，**profile patch 够不着**（E371）

- **现象**：禁用 workflow 的 patch 写了但无效。
- **根因**：agent preset 的工具清单在 `dsh-web-app/presets/*.patch.yml` 里，
  位于 `cordis:group` 的 **`isolate` 作用域**内 ⇒ **profile patch 层的 id 查找命中不了**，
  `applyEntryPatches` 会 warn 然后**静默跳过**。
- **修法**：两处都改（profile patch + 打包期直接补丁 preset 文件），
  且 preset 补丁要**幂等**（用标记 `DSHM_WORKFLOW_DISABLED`，并区分 `touched` 与 `alreadyDone`
  —— 早期版本把"已打过"误判成"结构变了"而 `die`）。

### 4.5 `&path:` monorepo 子目录皮肤（E374）

- **现象**：`HTTP 404 https://codeload.github.com/…/tar.gz/<commit>&path:/maid-atelier`。
- **根因**：`parseGitHub()` **先按 `#` 切分**，把 `&path:/maid-atelier` 并进了 ref。
- **修法**：不按位置切，而是用正则**从整串各自摘出** `[&?]path[:=]` 与 `#<ref>`
  ⇒ **两种先后顺序都兼容**（市场数据里都出现过）。
- **踩到的第二个坑**：codeload 的 tarball 恒有一层 `<repo>-<ref>/` **外壳目录**，
  且该外壳**没有 `package.json`** ⇒ 用 `realRoot` 拼 subpath 会漏一层
  （报 `spec 声明了子目录但该处没有 package.json`）。
  修法：以 **`soleDir`**（唯一顶层目录，不要求含 package.json）为基准。

### 4.6 卸载：**引号**才是删不掉行的真凶（E377）

- **现象**：卸载后包与依赖都删了，`.dshm-plugin-rows.yml` 仍留着
  `@dsh-external/dsh-client-ui-skin-maid-atelier`。
- **根因有两层，**只修第一层仍复现**（报告 7 修过、报告 8 复现）**：

| 层 | 问题 |
|---|---|
| ① 名字来源 | 卸载用 spec 解析出的名字，而**行名来自子目录 manifest 的 `package.json.name`** |
| ② **引号** | `composeUserRows` 把 `@scope/name` **回写成** `- id: '@scope/name'`，而删行用**裸名精确比较** ⇒ **永不等** |

- **②才是那道门**：即便候选名对了，`m[1] === name` 里 `m[1]` 带引号，比较永远为假。
  这精确解释了现象——**包与依赖都删了（那两处用裸名集合，不受引号影响），唯独行留着**。
- **修法**：`removeRowBlockById` **剥引号再比较**；另加 `removeRowBlockByIdSuffix`
  （后缀匹配，前一个字符必须是 `-`/`/`/`@` 之一）兜"包与依赖都已删"的残局
  （scope 前缀只存在于**已删的 manifest** 里，永远推不出完整名）。
- **五场景验证**（用真实 `removeSpec`）：正常 ✓、**残局**（依赖 0、包已删、行带引号）✓、
  不误伤 ✓、**反向不串味**（装 `orca-link` 不误删 `maid-atelier`）✓、npm 包回归 ✓。

### 4.7 profile 合并**只做并集 ⇒ bundle 永久沉积**（E378）

- **现象**：`package.json` 的 `bundles` 里**始终**留着 `…dsh-experimental-voice-input-bundle`，
  改种子 patch、禁 4 行都只是"在半条链上补洞"。
- **根因**：`main.js` 的 profile 合并
  ```js
  const merged = new Set((cur.dsh.profile.bundles || []).concat(seed.dsh.profile.bundles || []));
  ```
  **只做并集、从不移除** ⇒ 任何进入过设备 profile 的 bundle **再也去不掉**（种子删了也被加回来）。
- **修法**：引入**显式移除清单** `dsh.profile.removeBundles`（写在种子 package.json），
  合并口径改为 **「种子顺序并集 − 移除清单」**：
  - 尊重用户自加 bundle（插件页启停是产品能力，**不能"完全以种子为准"**）；
  - 又能表达"这一版我们确定不要它"，且上游加回来/用户曾启用过都能清掉。
- **真机读数**：`profile bundles 已移除（按种子 removeBundles 清单）：@deepseek-ai/dsh-experimental-voice-input-bundle`

### 4.8 插件安装器的其它静默失效点

| # | 坑 | 修法 |
|---|---|---|
| E370 | 依赖值记录：写 `^version` 会让下次预检认为"与已审阅源不符" | `dependencyValueFor(item)`：git/GitHub spec **逐字记录**、`name@range` → range、裸名 → `^version` |
| E370 | 纯库也写用户行 ⇒ 污染 `.dshm-plugin-rows.yml` | `appendUserRow` **门控**：只在顶层包声明 `dsh.bundle`/`dsh.bundles` 时写 |
| E371 | 入口校验**误杀**：`exports` 存在但无根候选 ≠ 半残包 | `entryCandidates()` 返回 `[]`（不做 `index.js` 兜底）；`userRowLoadable()` 对空候选**放行** |

### 4.9 `dsh.profile.bundles` 的坏行会拖垮启动（D27，四个落点）

**根因链**（"坏引用 ⇒ profile 起不来"这条死锁有**四个**落点，只堵一处没用）：
① 用户行 `.dshm-plugin-rows.yml` → ② `dependencies` 逐条预检（整棵依赖树）→
③ home 层 `$DSH_HOME/cordis.patch.yml`（`readProfilePatches` 每次启动都读，**种子覆盖够不着**）→
④ 种子 bundles 预检（`resolveBundleDir` 先查核心树再查 profile）。

**关键修正（防误杀）**：`sanitizeDependencies` 必须补 `anchorDirs: [CORE_DIR/node_modules]`
—— 只查 profile 侧会**洗掉合法的 `OPTIONAL_BUNDLES` 两行**
（真机实证误杀 `dsh-experimental-agent-team-*`）。

### 4.10 启动自愈：失败后隔离用户插件行

`quarantineAfterBootFailure()`：上次启动失败 ⇒ 先隔离用户插件行再拼装
（必须在种子覆盖/`composeUserRows` **之前**）⇒ 本次启动就是**纯种子 profile**。
原始文件**原样保留**（可手工恢复），并记 `BOOT_FAIL_MARKER`。

## 5. 工具链（busybox / python / git / rg）

端侧 PATH 里只有 `/bin/sh` 与 toybox：**没有 bash、unzip、xz、less**。
所以"工具链"这一节本质是**在受限环境里重建一套开发者习以为常的工具**。

### 5.1 busybox applet 的选择与"未编 applet"陷阱

- `BUSYBOX_APPLETS = ['ash','bzip2','xz','hexdump','less','nc','unzip','vi']`
  —— **`bash` 与 `hush` 被移除**：busybox **未编**这两个 applet，留着只会让
  `bash` 看起来"存在但报 `applet not found`（exit 127）"。
- **修法（bash 垫片）**：`ensureBashShim(binDir)` 写一个**文本脚本**：
  真 bash → busybox ash → `/system/bin/sh`，`exec` 直通。
  - **为什么脚本可以**：脚本由**系统** `/bin/sh` 执行 ⇒ 不受 §0.2 的签名域约束。
  - 真机读数：`bash=ok`。

### 5.2 rg：平台包已注入但 execve 被拒 ⇒ 走纯 JS 降级（批次七）

- **现象**：`rg` execve 被拒（`exec 探测` 矩阵 `rg=denied`）⇒ `glob`/`grep` 恒 `SEARCH_FAILED`。
- **修法**：移植 `apply-dsh-ohos-adapt.sh` 的 **fs-search 降级 patch**（打包期注入 core 树）：
  三段锚点 patch（helpers 五函数 + spawn 段替换 + 输出段替换，**保 `{text,lossy}` 形状只换 text**）。
- **本项目特有增强**：移植件的场景是"**平台包已注入（`resolveRgPath` 成功）但 execve 被拒**"，
  而上游底本只覆盖"包缺失" ⇒ 补 `rgExecutable()` 探测（spawn `[rg,--version]` 一次，
  进程内 memoize；**abort 竞态不记忆**）。
- **依赖边界坑**：目标文件只 import 了 `existsSync`/`parse` —— 上游底本的
  `statSync`/`basename` 直接移植会 `ReferenceError` ⇒ 改写为 `existsSync` / `parse(x).base`。
- **PC 侧两枚坑**（assert 行为测试抓住，**未流出到设备**）：
  - `.mjs` 模板字符串**转义多一层**：`"\\\\n"` 产出源码 `"\\n"`（字面反斜杠+n）⇒
    `expandBraces` 正则与 NDJSON 换行全废；修正为 `"\\n"`/`"\\{"`。
  - **negation 的实际形态**：fs-search 发 `--glob=!**/name`（而底本的 `--glob!` 分支**永不命中**，
    是底本自己的 bug）⇒ 实现改为值级 `!` 前缀过滤。

### 5.3 内嵌 Python 桥（批次六）

- **动机**：execve 被拒后，给"需要真 CPython"的场景一条**进程内**通道。
- **坑**：`exec -m pip` 冷路径**卡死**——`captureRun` 是**同步 NAPI 调用**，
  Python 卡多久 node 事件循环就卡多久（status / dsh web 全挂 4 分钟+，只能 force-stop）。
- **修法**：每个执行请求注入 **SIGALRM**（默认 120s，`&timeout=1..300` 可调），
  超时 handler 抛 `SystemExit(124)` 由 `captureRun` 捕获；请求后**统一清 itimer**
  （防 pending alarm 在下个请求的字节码检查点误杀）。
- **桥的第二个致命坑**：`ErrPrint` 必须在 `GILRelease` **之前** ——
  释放后再调 CPython API 直接 fatal（真机实证：清 itimer 的 `runString` 遇 `NameError`
  → `ErrPrint` 在已释放 GIL 上执行 → **进程暴毙**）。
- **桥的第三个坑（批次九）：`-V|--version` 快速分支**盖过了 `pipMode` ——
  `pip3 --version` 被拦截、直接 echo Python banner（表现为"exit 0 但无 pip 26.x 字样"，
  而 pip 本体无恙：exec 端点 `-m pip list` → pip 26.2.1 rc=0）。
  修法：**pipMode 不再生成 `-V|--version` 分支**（转发 `-m pip --version`），
  保留 `-h|--help` usage 提示；断言 65 → **66**（新增 `...(pipMode ? [] : [` 结构锁）。
  - **通用教训**：**"快速分支"常常绕过后面的功能路径** —— 同一现象在 §1.10 也出现过
    （`npx -v ✓` 没暴露 `DSH_HOME` 缺失，因为 `-v` 分支排在检查之前）。
    ⇒ **版本探测 ≠ 功能路径探测**。
- **日志通道澄清**：`log()`/`stage()`/`DSHM_READY` 走 **stdout**（`node-output.log`），
  `diag()` 走 **stderr**（`dshm-host.log`）⇒ **两个文件都要拉**。

### 5.4 工具链自签名的三踩坑（E369）

见 §3.1–§3.3。要点：
- `binary-sign-tool sign -mode localSign -selfSign 1 -inFile <f> -outFile <g> -signAlg SHA256withECDSA`
  → `SelfSignSignProvider`，加 `.codesign` 段（4096B），**跳过 `.profile`/`.permission` + 证书链**
  ⇒ **不需要 keystore 密码**。
- 验证：`display-sign` → `code signature is self-sign`。
- **只签"会被 exec 的独立件"**（如 rg），不必签每个 `.so`。

## 6. 构建期工具链与 Windows 侧

### 6.1 Windows 上改 tar 归档必须用 Python（§2.5）

`bsdtar` 丢 symlink（不可逆损坏）、`7z` 物化 symlink（8MB → 1.3GB），
**只有 Python `tarfile` 安全** ⇒ `tools/sign-tar-elf.py`，README 把 Python 3 列为前置。

### 6.2 `podman` 里没有 node / cmake ⇒ 不走 WSL（E51②）

koffi 3.x 的编译**不用 WSL**（那里**没有 node、没有 cmake**），而是把 koffi 作为
**CMake `MODULE` 目标**加进 `entry/src/main/cpp/CMakeLists.txt` ——
hvigor 天然按 ABI 各编一份、按 `lib<name>.so` 打进 HAP（**正好命中原生库重定向的命名约定**）。

### 6.3 交叉编译的**静默失败**：目标对象可能由宿主编译器编出（E50）

- **现象**：`toolchain-env.sh` 注释里警告过的那类静默失败。
- **修法（判据）**：检查日志里出现的是 `x86_64-unknown-linux-ohos-clang++`（1495 次），
  **未见宿主 g++ 编译目标对象** ⇒ 确认目标对象确实由 OHOS clang 编译。

### 6.4 脚本的 `HERE` 陷阱（E48）

`HERE` 原先在脚本中途 `cd` 到源码树**之后**才用相对路径解析 ⇒
以相对路径调用必然失败（`cd: tools/node-runtime: No such file or directory`）。

### 6.5 改 JSON / 文本文件**不要经过 PowerShell 的默认编码与正则**（E63）

- **现象**：生成 recipe 用 `Get-Content -Raw` + `-replace` + `Set-Content`，
  写进了一个**控制字符** ⇒ `pack-core` 在 `JSON.parse` 直接报
  `Bad control character in string literal`。
- **修法**：`[System.IO.File]::ReadAllText(path, UTF8)` + `String.Replace` +
  `WriteAllText(…, UTF8Encoding($false))`。

### 6.6 把"没有出处的脚本"变成有说明的工具箱（E216）

`docs/50` §15 按三类登记 `tools/`：**门禁**（每次都该跑）、**生成器**（产物提交进仓库，
漂移由门禁检测）、**开发与排障**（按需使用）。

## 7. ArkTS / UI 侧

### 7.1 ArkUI 与 Web 的语义差异

| 差异 | 说明 |
|---|---|
| **SVG 裁剪 vs `Shape` 不裁剪** | SVG 默认把溢出 `viewBox` 的墨迹**裁掉**，ArkUI `Shape` **不裁** |
| `Shape.viewPort` **不做缩放** | 见 §7.2（这是"鲸鱼歪"的真因） |
| **`@Builder` 可以多根，`build()` 只能一个根** | `@Builder` → 组件搬迁时，多根必须先包一个容器（E324 / E335，**踩了六次**） |
| `@Builder` 调用返回 `void` | 不能链属性修饰 ⇒ `margin`/`height` 要放外层容器 |
| `@Builder` 里的 `this.x()` 就是**再调一遍自己** | Builder **没有"上层"**这个概念（E343） |
| `$r` 只能字面量 | 模型持不了 `Resource` ⇒ 图标/文案映射必须留在 `view/` 层 |

### 7.2 鲸鱼"歪"：`Shape.viewPort` 没把路径缩放进组件盒（E380）

这是**"测量方法错误"**的教科书案例，值得完整记录（我连续几轮都在错误的层次上打转）。

| # | 我原先的判断 | 实测结论 | 怎么发现的 |
|---|---|---|---|
| ① | 测量：鲸鱼墨迹 33×34px、宽高比 0.97，"不是等比" | **测错对象**：我在整屏 x∈[0,140] 找暗像素，量的其实是**窗口外**的桌面图标 | `uitest dumpLayout` 给出**权威坐标**：窗口从 x=357 起、`Shape` 盒在 `x[374..416]` |
| ② | 结论：路径墨迹**溢出**官方 viewBox（`x=-0.2229 w=23.3967`），故 viewPort 要用"墨迹盒" | **结论是错的**：那个盒是**贝塞尔控制点**包围盒，而控制点会落在曲线**外面**。把每段 C 曲线**离散成 400 点采样**后，真实紧包围盒 = `x 0.0000 w 23.1600 h 17.0434`，**恰好等于官方 viewBox**（**零溢出**） | 写脚本解析 path + 采样求极值 |
| ③ | 数据：路径"逐字节取自官方" | **抄错 1 位**：`12.6435` 应为 `12.643`（3449 字符里错一个控制点，轮廓就会变形）。字符串比对显示 378 处差异，但**语义级比对**（拆成命令+数值序列）后真正的差异**只有这 1 处** | 逐字节 + 数值双重比对 |

**真因**：`Shape.viewPort` 没有把路径缩放进组件盒 —— 鲸鱼以"1 用户单位 ≈ 1 物理像素"的
自然尺寸画在**左上角**：

```text
Shape 组件盒 : x[374..416] w=42px  y[390..421] h=31px   （比例 1.355 ≈ 官方 1.359 ✓ 盒子本身是对的）
盒内墨迹     : x[374..398] w=25px  y[391..408] h=18px
左留白 0px / 右留白 18px   ⇒ 鲸鱼贴在盒子左上角，只占 ~60%
```

**修法**：改用**官方 SVG 素材 + `Image.fillColor`**（等比缩放交给图片组件），
不再依赖 `Shape.viewPort` 的缩放语义。
- `fillColor` 对单色 SVG 是**整体重着色**（把非透明像素统一替换），等价官方 Web 的 `fill: currentColor`；
- 新增 `tools/gen-fish-logo.mjs`（**生成式**，两条自检）：
  ① 断言"真实紧包围盒 == 官方 viewBox"（上游换几何时**停下要人确认**）；
  ② 断言"落盘后路径仍与官方逐字节一致"。

### 7.3 ArkUI 的**响应式**：读到非 `@State` 字段 ⇒ 改它不触发重渲染（E379）

- **现象**：状态栏跟随外观生效了，**但鲸鱼不变**。
- **根因**：`fishMarkColor()` 读的是**普通 private 字段** `systemBarApplied` ⇒
  **改它不触发重渲染**；而顶栏底色 `topBarBg` 是 `@State` 所以会变
  ⇒ **"两个值一个响应式、一个不是"** 的典型症状。
- **修法**：引入 `@State themeMode`（与 `systemBarApplied` 分开，后者用于"设置失败可重试"的幂等闸门）。
- **位置确认**：ArkTS 侧**只有一个**自绘品牌标识（`@Builder FishMark`）；
  启动画面用的是**位图** `app.media.logo_dark`，与顶栏无关。

### 7.4 状态栏跟随「设置→外观」（E375）

- **web 侧** `THEME_SHIM_JS`（`javaScriptOnDocumentStart` 注入）：
  读官方锚点 `getComputedStyle(documentElement).colorScheme`（**比 body 背景色更权威**——
  皮肤会改 body 底色，但 `color-scheme` 是浏览器级语义）；
  `matchMedia('(prefers-color-scheme: dark)')` 覆盖"系统里切深浅"，
  `MutationObserver(documentElement)` 覆盖"应用内切外观"。
- **ArkTS 侧** `DshThemeBridge`（`javaScriptProxy` 同步回传）→ `applySystemBarTheme(mode)`：
  `setWindowSystemBarProperties({statusBarColor, statusBarContentColor, isStatusBarLightIcon})`，
  并**同色** `setWindowBackgroundColor` ⇒ **消除切换闪白**。
- **兜底**：10s 的 DOM 探针也调同一个函数（桥万一没装上也能收敛），两条路径共用**幂等闸门**。

**踩到两个坑**：
1. **注入到 web 的脚本，注释里不能出现反引号** —— ArkTS 模板字面量用 `` ` `` 定界，
   注释里的反引号会**截断它** ⇒ 编译期报 `';' expected`，且位置**指向注释行**（很误导）。
2. **`(void)force;` 在注入脚本里是语法错误**（`void` 缺操作数）—— 我最初写了个 `force` 参数
   想让"首次必定上报"，改了三次才收敛成"**只按 `last` 判**"（首个定时器若 `color-scheme`
   未写入返回 `''` 被拦下，`last` 仍是空，第二个定时器自然补报 ⇒ 不需要 force）。

### 7.5 `javaScriptProxy` 只支持**同步**调用（D6 §12 / 批次十二）

- **官方 FAQ 定论**：异步方法无法把结果回传 H5。
- **修法（目录选择三段式）**：同步 `startPick(id)` → 异步拉起系统选择器 →
  `runJavaScript` 回调垫片把结果送回 H5 的 Promise。
- **禁止重复注册**：只用**属性形式**（`.javaScriptProxy({...})`），
  **禁止**在 `onControllerAttached` 里用 `controller.registerJavaScriptProxy` 重复注册——
  实测后者会先 `RemoveNamedObjectInternal` 移除属性注册的对象、再把新对象**推迟到"下次页面加载"**
  才生效 ⇒ 页面 stub 还在（`typeof "object"`）但 native 端**已除名**。

### 7.6 `setWindowDecorVisible(false)` 后系统仍保留右上角三键

⇒ 顶栏右侧必须**动态避让三键区**（`TitleButtonRect`，单位 vp）。
全屏无装饰抛 801 属**预期**（手机全屏场景）。

### 7.7 顶部浮层门户要挂在**页面根**，不能挂在单栏根节点（E292）

- **现象**：双栏/三栏下点了没反应。
- **根因**：`bindSheet` 原先只挂在 `buildSingle` 的根 `Column` 上，而
  `sheetKind()` 覆盖的六类浮层里**四类的触发点都在主区内容里** ⇒ 双栏/三栏够不着。
- **修法**：门户（`bindSheet` + `sheetContent()` 分派 + `closeSheet()` 复位）提到
  **页面根** `Index.build()`，与形态无关。（官方 Web 的 portal 同样挂在 `App` 根、不属于任何 pane。）

### 7.8 `@Builder` 兜底分支**自递归**（E343）

- **现象**：冷启后**点一下界面就被系统杀进程**（`Stack overflow`）。
- **根因**：`MainShell.mainContent` 的尾巴是 `} else { this.mainContent(this.compact) }`
  —— **自递归**（条件不变，每次调用都重新走到这条 `else`）。本意是"剩下的面板交回上层继续分派"，
  但 **`@Builder` 没有"上层"这个概念**。
- **为什么所有门禁都拦不住**：① 语法/类型/编译全过（自递归是合法调用）；
  ② `check-feature-wiring` 只管"调用点还在不在"，不管"调的是谁"；
  ③ 那两行**读起来像控制流，实际是无限循环**；④ 它甚至**不影响首次渲染**
  （首次只走一个分支），要**第二次更新**才炸 ⇒ "起来看着好好的"。
- **修法**：兜底 = 渲染**真正拥有这些内容的那一束组件**。
- **新增门禁**：`tools/check-builder-recursion.mjs`（剥注释后扫 `this.<自己>(`），
  并**用修前的提交跑同一检测器归真**（命中 `MainShell.ets:380`）
  ⇒ **门禁必须先在已知坏版本上红过一次，才算证明它有用**。

### 7.9 ArkWeb 默认**丢弃** `window.open` / `target="_blank"` ⇒ 「设置 → 登录」点了没反应（m00001）

- **现象**：鸿蒙端点「设置 → 登录」，**不弹浏览器、不弹框、无报错、界面无任何变化**。
- **根因（两层，缺一层都修不好）**：
  1. **引擎层**：ArkWeb 的 `multiWindowAccess` 默认 **false**（`ets/component/web.d.ts:6816-6826`）
     ⇒ `window.open` 与 `target="_blank"` 一律**静默丢弃**。本仓全树 grep
     `onWindowNew|multiWindowAccess|allowWindowOpenMethod|onLoadIntercept|onOverrideUrlLoading`
     **零命中** ⇒ 没有任何地方接过这个语义。
  2. **前端层**：登录路径上**根本没有可点的外链**。唯一带授权页锚点的是
     `dsh-client-ui-settings-account/lib/client.js:2435-2451` 的 AccountSection
     `<a target="_blank" href={authorizeUrl}>`，但 AccountSection 只在
     `snapshot.view?.status === "credential-stored"` 时注册 `settings.section`
     （`:4397-4419`）⇒ **未登录时它不存在**。未登录能点的只有 SignInDialog
     （`:989-1107`），而它**没有任何 href、也没有 `window.open`**，只有一个「复制链接」。
     ⇒ **光接住 `target="_blank"` 是不够的**。
- **为什么官方桌面版没这问题**：Electron 主进程用 `setWindowOpenHandler` +
  `shell.openExternal` 接住外开 —— 那是**壳外代码**。全 core 树 grep
  `setWindowOpenHandler|shell.openExternal` 零命中；`dshDesktop` 契约只有
  shortcuts / keyboard / updates / browser 四类能力，**没有任何外开 API**
  ⇒ **外开必须由本壳自己实现**。
- **authorizeUrl 从哪来**：**只**出现在 `account/watch` 流里。host
  `dsh-deepseek-account-platform/lib/index.js:933-940` 的 `update()` **每次都剥掉**
  `authorizeUrl`（`const { authorizeUrl: _url, ...rest } = attempt.view`），
  只有 `:1012 update(attempt, { phase:"waiting-browser", authorizeUrl, expiresAt })`
  那一次带上，经 `changed()`（`:890-912`）推给订阅者。前端订阅点：
  `dsh-client-ui-settings-account/lib/client.js:4194 open: (signal) => ctx.remote.account.watch(signal)`，
  该流就是 `/api/remote.mux` 上的 `new WebSocket(...)`
  （`dsh-api-gateway/lib/client.js:507`，帧格式 `{type:'item',streamId,value}`，
  `value` 即整份 AccountView）。
- **为什么不能在本 WebView 里打开它**：`loginSource` 是 `"desktop"` ⇒ 回调收尾是
  **HTTP 204**（`lib/index.js:834-840`，只有 `login_source=web` 才返回关页 HTML）
  ⇒ 在应用内打开会把整个界面替换成空白页。
- **修法**：`WebApp.ets` 新增文档开始垫片 `OPEN_LINK_SHIM_JS`（与目录选择、外观跟随同范式），
  三条独立路径 + 一个同步桥：
  - 路径 1：包 `globalThis.WebSocket` 构造器，听 `message` 帧，`frame.type === 'item'` 时取
    `frame.value.attempt`，`phase === 'waiting-browser'` 且带 `authorizeUrl` ⇒ **自动外开**
    （无确认，这是壳职责，与官方 Electron 壳同构）。
  - 路径 1b：包 `globalThis.fetch`，只处理 URL 含 `account/` 的响应，`response.clone().json()`
    后同样扫描（一元 `startSignIn` 的响应是兜底；**必须 clone**，原 body 要原样交回调用方）。
  - 路径 2：捕获阶段听 `click`，在 `a[target="_blank"]` 且 href 是 http(s) 时**二次确认后**外开
    （用量/充值等外链不是壳职责，按规范先确认）。
  - 路径 3：包 `globalThis.open`（官方的「联系我们」，`settings-account/lib/client.js:4265`）。
  - 桥契约：`__DSHM_BRIDGES__.openExternal(url, mode)`，`mode='auto'` 直接开、
    `mode='confirm'` 交 ArkTS 弹确认框；ArkTS 侧用 `platform` 的 `openExternalUrl`
    （`context.openLink`）落地。**桥必须并入 `this.bridges` 一个对象并加进 `methodList`**
    —— 理由见 §7.5。
- **为什么不走 `onWindowNew` + `multiWindowAccess(true)`**：签名已核（`web.d.ts:6816-6826`
  `multiWindowAccess`、`:4877 OnWindowNewEvent`、`:1997 ControllerHandler`），但那是
  **引擎级行为开关**，一开全仓生效（文档明确警告新窗口来源不可确知、可能来自第三方 iframe），
  且我们还得自己接管 `ControllerHandler` 的控制器并负责销毁。收益不如「只拦我们要拦的 URL」明确。
- **三个非显然的坑**：
  1. **包 `WebSocket` 必须保住静态常量**。gateway 直接用裸 `WebSocket.OPEN` 比较
     `readyState`（`dsh-api-gateway/lib/client.js:555`）⇒ 包装器若丢了静态量，
     **整条 account/events 流都建不起来**（比原 bug 严重得多）。修法：拷贝
     `Object.getOwnPropertyNames(NativeWS)`，并用规范固定值兜底
     （CONNECTING=0 / OPEN=1 / CLOSING=2 / CLOSED=3），仍不成立就**回滚成原构造器**
     —— 宁可丢自动外开，不能弄坏连接。
  2. **投递失败不能吞掉这次点击**。`out()` 返回布尔值：桥还没就位时返回 false，
     点击路径据此**不** `preventDefault`（放行给 WebView 默认行为，仍是丢弃 = 与改动前一致），
     自动外开则**入队重试**。否则只是把「点了没反应」换成另一种「点了没反应」。
  3. **授权页只推一次**：`waiting-browser` 那一刻推过后就不再带 `authorizeUrl`
     （`update()` 会剥掉）⇒ 桥的注册时机与垫片执行时机的先后**必须容错**。
     故自动外开加了 15s 有界重试泵（250ms 轮询、URL 去重、投递成功才记账）。
- **验证状态（2026-09-28 真机复核通过）**：ArkTS 编译通过（`assembleHap` BUILD SUCCESSFUL，exit 0）；
  真机（设备 `86E0226429000417`，当时的 HAP `314,673,276 B` / `updateTime 1790600982722` = `2026-09-28 21:09:42 CST`；
  该包为核心 `0.2.0-rc.1`，**现已不是交付包**——交付包已于 2026-09-30 刷到 `0.2.0-rc.2` 的 `314,166,762 B`）
  四步全通：① 授权页 `auto` 外开；③ 回跳后设置面板出现「账号与余额」section
  （该 section 只在 `status === "credential-stored"` 时注册）；④ 外链点「查询用量」⇒ 弹
  「打开外部浏览器？」⇒ 点「打开」后 `ei.hmos.browser` 真被拉起并加载 `platform.deepseek.com/usage`。
  第 4 步做过阴/阳对照：**取消** ⇒ `diag-openlink`/桥调用数/浏览器进程**三者都不动**；
  「打开」⇒ 三者一起动。累计 `diag-openlink` 6 行（1×`auto` + 5×`confirm`），
  **无 `failed` / `error` 行**。逐条读数与两个取证坑（设置对话框的 tab 记忆、本项 hilog 抓不到）
  见 `device-validation.md` 的 D28。
- **本项踩到的方法坑（值得与上面"三个非显然的坑"并列）**：外开链路的真机取证**不能靠 hilog**——
  `hilog -x -T DshWebApp` 与按关键字筛都是空的，唯一可靠通道是 `diag-openlink` 文件 + `uitest dumpLayout` 前后 diff。
  另：设置对话框会**记住上次的 tab**，点账号区坐标前不先点「账号与余额」会打在插件明细上（造成过一次误判）。

## 8. 工程方法与流程（**最值得复用的一节**）

前面每一节讲"哪个平台的哪里不同"，这一节讲"**我们在排查这些差异时反复犯的思维错误**"。
它们是跨平台的。

### 8.1 「测量口径」纪律（本文出现次数最多的一类错误）

| 坑 | 说明 |
|---|---|
| **测错对象比红更危险** | 断言绿不等于测对了东西。`assert-fs-search-fallback.mjs` 曾**写死旧版本路径** ⇒ 升级后断言**悄悄测旧树**（绿但无效）。修法：改为读 `corerecipe.json` 的 `coreVersion`（唯一事实来源） |
| **测错坐标系** | 鲸鱼"歪"排查中，我从**整屏像素**猜位置，量到的是**窗口外**的桌面图标。`uitest dumpLayout` 才是 ArkUI 层级的权威坐标源 |
| **控制点包围盒 ≠ 可见墨迹包围盒** | 贝塞尔控制点可落在曲线外；要"看得见的边界"必须**离散采样** |
| **统计前先定口径** | 事件清单曾因"按通用字段名 `type` 遍历"而**虚增 4 种**（把 `assistant/message.data.stream[]` 里的流式记录当成了事件类型）⇒ 差一点据此建出"并不存在的事件族"。**多统计与统计错对象，比少统计更危险** |
| **跨来源比对必须先确认字段对等** | 本项目已因此得到过一个"看起来很有说服力的错误结论"，并差点据此**删掉一处正确的防护** |
| **脚本化搬迁的头号坑：替换点在被删区间之前 ⇒ 后面所有行号整体偏移** | 一次搬迁里的所有改动必须按**原始行号降序**施加（E293 / E318 / E336 **三次**） |

### 8.2 「静默失效」家族（编译不报、界面无感，只是让下一个人以为还在用）

| 形态 | 例子 |
|---|---|
| **通道有、没消费者** | `tabFacade`（E343c）、`settingsStates` 死链（E346b）、`mobileDrawer` 躺了几轮（E306）、`selectedRightPanel`（E316）—— 共 7 例 |
| **搬迁搬走了消费者，留下成员与导入** | 搬迁后对宿主跑"成员名全文件出现次数 == 1"的扫描（== 1 即只有声明）。靠它一次点出 15 个 |
| **死代码** | `SessionListPane`（221 行）**是死代码，而文档一直说它在用**（E298）；`credentialsTab()` 全仓零调用（E333） |
| **patch 静默不生效** | id 与包名不同名（`permission` vs `permission-presets`）⇒ 无任何报错（E53） |
| **约束静默不生效** | ArkTS 的 `@State`（读到非响应式字段 ⇒ 改它不触发重渲染，E379） |
| **"状态写了但没人读"** | 定时器 `jobsTick++` 而渲染不读它（E312b）⇒ 把刻度放进 `ForEach` 的 key 才有**真依赖** |

### 8.3 门禁必须**先在已知坏版本上红过一次**（E344）

新增门禁用**人工注入的样例**能过，只证明"检测器会匹配我写的样例"，
**不能**证明"它会命中真实的那行代码"。
⇒ 必须做**归真验证**（`git show HEAD:<file>` 存成临时文件 → 扫 → 命中）。
为此检测器要导出 `scanText` 而不只在 `main()` 里跑。

### 8.4 用户报"还是不对"时，别重做同一个修法，先换测量工具（E376 / E377 / E380）

三次实证：
- 报告 7→8 同一个卸载残留行 bug **复现**，因为我上批只修了"名字来源"、**漏了引号**
  ⇒ 要问"**这条链上还有几个判据**"，而不是重做同一个修法。
- 鲸鱼"还是歪的"：前几轮都在**布局层**打转（viewBox / 尺寸 / 位置），
  一拿到 **UI 树坐标**就立刻定位到 `viewPort` **未缩放**。
- git 子进程：修好 abort（垫片）后**下一层**（symlink）才浮现。

### 8.5 序列化会改字面量（E377）

凡"**写进去的和读出来的不是同一串**"的地方都要单独验：
YAML 自动加引号 ⇒ `m[1] === name` 永假 ⇒ 这是"包删了行还在"的真凶。
**字符串比对会被格式噪声淹没**（378 处差异），**语义比对**才看得出真差异（1 处）。

### 8.6 只做并集的合并逻辑会变成"**永久沉积累**"（E378）

`bundles` 的 `cur ∪ seed` 让任何 bundle 一旦进入就再也去不掉。
⇒ 凡"合并"都要能表达"**移除**"（显式移除清单），否则配置收敛能力会随时间退化。

### 8.7 "修半条链"不等于修根因（E378 vs 批次十三）

"禁 4 行插件"（半条链）≠"从 bundles 移除"（根因）。
同样：**修症状 ≠ 修根因** —— 要问"这个东西还**能从哪里被挂起来**"。

### 8.8 "能跑"与"跑通"是两件事（E376）

端侧工具链是长链（起进程 → 找辅助程序 → 连远端 → 认证），
**每一环**都可能被 §0.1/§0.2 波及。⇒ 凡"某功能整条链不可用"，
先把链上**每一步**都列出来，逐层验。

### 8.9 平台 libc 的"缺能力"可以用 **LD_PRELOAD** 兜，不必重编（E376）

**前提**：目标程序是**动态链接**的。口径是**透明优先** ——
先调真身、成功就透传 ⇒ 垫片在正常平台上是 **no-op**，不会掩盖真实错误。

### 8.10 硬编码的清单会在升级时**静默失效**（E376）

`GIT_SYMLINK_REPLICA` 只有 1 条而实际 141 条 ⇒
改为**从归档现读**（`readGitCoreSymlinks`）。
同类：平台别名表、preset 补丁的标记。

### 8.11 "文档说了、配置没做"比单个 bug 更危险（本轮清理发现）

`docs/README.md` 的「清理与留档纪律」早就写着"临时过程产物一律只落 `dist/`（**已 gitignore**）"，
而 `.gitignore` **从未包含 `dist/`**。下一个人会按文档行事（以为不会误提交），
直到某次 `git add -A` 把 500MB 中间产物带进去。
⇒ **修配置，不修文档措辞。**

### 8.12 「快速分支」常常绕过后面的功能路径（§1.10 / §5.3）

两次实证，**都是"探测显示 ok，功能实际坏着"**：
- `npx -v ✓` 没暴露 `DSH_HOME` 恒定缺失 —— 因为 `-v` 快速分支排在 `DSH_HOME` 检查**之前**；
- `pip3 --version` 用了 `-V|--version` 分支，被拦截去 echo Python banner —— 而 pip 本体无恙。

⇒ **版本探测 ≠ 功能路径探测**。验收要靠**功能路径**的探针（如 `ls-remote`、
`-m pip list`），不能只靠 `--version`。

### 8.13 「写死总数」的断言会让人放松警惕（E381/E382 门禁自身的修）

`assert-cli-shim` 里有五条断言**本来就在红**（与当次改动无关的历史遗留）：
- 三条是 `总数 === 2`（`QDIR 写死次数`、`仍在等待 Host 安装`、假壳名字表的整行字面量）
  —— 后来加了第三个假壳（`dsh`）就变成 3，于是每加一个同类实体都要改断言；
- 两条锁的是**已被取代的文案**（`端侧暂不支持卸载`，而后来补了卸载通道）。

**为什么这比单个 bug 危险**：判据写死总数 ⇒ 加实体就得改断言 ⇒
而"**改断言让它变绿**"这个动作会让人习惯性放松。更糟的是这五条**红了却没人发现**
（`assert-cli-shim` 当时不在必跑链里）——**没接进门禁的断言等于没有**。

⇒ 判据应锁 **"每个都满足"**（逐实体断言），而不是"总数恰好是 N"。
⇒ 新增断言后**接进必跑链**，否则红多久都没人知道。

**同一形态在 2026-09-28 又抓到三处**（不是门禁，是交付/排查脚本，所以更没人盯着）：
- `tools/update-device.ps1` 的 exec 探测判据写死 `$okCount -ge 7`；
- `tools/func_test_final.py` 的 `T0.2` 同类 `>= 7`，以及 `T0.3` 写死核心版本 `'0.1.7-rc.2'`；
- `tools/scan-core-plugins.mjs` 的默认 `coreDir` 写死 `dsh-core-0.1.5-rc.2`（早于当时树两代，一跑就报 `no node_modules under …`，现场像"没物化"，其实是版本陈旧）。

三处的危害都是**新版失败不会被发现**：`update-device.ps1` 若哪天新增第 8 个探测目标，
8 项里只 ok 7 项**仍判通过**；`func_test_final.py` 在核心升级后 `T0.3` 会 FAIL，
现场像"核心没升上去"。处置统一为**读 `hostcore/core-recipe.json`（版本的唯一事实来源）或逐项判定**，
详见 `docs/90` §8.1 与 `docs/device-validation.md` 批次三十六。

### 8.14 负测试「没生效」比负测试「失败」更危险（E381/E382）

按纪律做负测试（把修复临时还原、确认断言变红）时，我第一版按 `\n` 拼锚点，
而文件是 **CRLF** ⇒ 替换**没生效**，脚本却只打印一句"锚点没对上"就**继续跑完**，
最后报了"✓ 负测试通过" —— **一个虚假的安全感**。

⇒ 负测试必须**断言篡改本身真的发生了**（替换前后字符串不等），没发生即**报错退出**。
⇒ 这与 §8.2「静默失效」同族：**检测手段自己静默失效，比没有检测更坏**。

### 8.15 「能工作」不等于「定义正确」（E383）

真机出现"装了 `0.1.7-rc.2` 却仍跑 `0.1.7-rc.1`"。根因：`DshHost.start()` 在
`state.current` 为空时取 `installed[0]`，而 `listInstalled()` 返回的是
**`fs.listFileSync()` 的目录枚举顺序（未定义）**。

**为什么潜伏这么久**：设备上**长期只有一棵核心树** ⇒ `installed[0]` 恰好总是对的。
文档还把它记成一条"设计"（「current 恒空 ⇒ 永远 `installed[0]` ⇒ **删旧树即切换**」）
——其实那是**掩盖未定义行为**。一旦两棵树并存（本次升级就是），立刻暴露。

⇒ **凡把"顺序"当依据的地方，都要问一句"这个顺序是谁定义的"**：
目录枚举、`Object.keys`、`Set`/`Map` 迭代顺序都是这类。
⇒ 顺带：修好后 `compareVersions` 的两个错（`0.1.7-rc.1 > 0.1.7` 违反 semver；
`beta.1 < alpha.9`）**都是单测抓的，不是评审抓的** —— 判据函数必须可单测。

### 8.16 升级手册的每一步都在挡某个具体的东西（E383 / 批次十六）

本轮升级时发现：上一轮升到 `0.1.7-rc.1` **漏跑了「重生成上表」这一步**，
导致提交基线停在 `0.1.5-rc.2`。后果**不是红灯**，而是
**无法区分"新漂移"与"旧欠账"** —— 漂移报告打出 70 处，其中 58 处是上一轮的欠账。

**怎么拆开的**：直接对比 rc.1 与 rc.2 两份契约，发现"7 个被移除的端点"
**在 rc.1 里就已经不存在**。若没做这一步，就会误以为 rc.2 删了 7 个端点，
进而做无谓的降级处置（甚至"修"一个不存在的问题）。

### 8.17 诊断通道的设计（因为 §2.9 观测受限而被迫发明）
| 手段 | 用途 |
|---|---|
| `BOOT_xx` 阶段标记 | 把启动切成显式阶段（`BOOT_00_NODE_START` → … → `BOOT_70_HTTP_READY`）；失败一律打 `BOOT_ERR after=<最后一个成功阶段>`。**`BOOT_70` 是自探**（`node:http` GET 一次 `/`），因为"dsh 说它绑了端口"与"端口真的应答"是两件事 |
| **抓 stdout 转 hilog** | 应用进程 stdout 在设备上不可见，`filesDir` 又给 hdc 读 ⇒ 在 `dshhost.cc` 里 `freopen` 到 `node-output.log` + `dup2(1,2)`，`node::Start` 返回后逐行 `OH_LOG_Print`（**E33** 首次用上，从此成为常规手段） |
| 文件标记（**追加模式** + ISO 时间戳） | hilog 在本机有**丢日志前科** ⇒ 链路每个阶段都以文件标记取证 |
| `uitest dumpLayout` | ArkUI 层级的**权威坐标与文本**（图片判定会误判品牌词） |
| `exec 探测` | 每次启动自动产出的机器可读结论（六项 + `git-ls-remote`） |
| 本机以端侧同参复现 | `node --jitless --no-experimental-fetch hostcore/app/main.js` ⇒ **秒级迭代**，只把最终结论拿到设备验证（E36/E52） |

### 8.18 比对型门禁要问"两边分别是哪一版"（E384 / 批次三十五）

升级到 `0.2.0-rc.1` 时，端点表已重生成、`SUPPORTED_VERSIONS` 已置新，
但 **`compat-drift.mjs` 的默认契约快照**（`.research/protocol/contracts.json`）还是上一版的。
门禁于是打出：

```
上游移除端点（3）—— 这些调用会返回 HTTP 404
```

**方向完全相反**：事实上是上游**新增**了 3 个 `productAnalytics/*`。
而且这份输出看起来同样具体、同样有依据（连 `.meta.json` 里显示的版本号都是旧的，
却不会有人怀疑它）——若照它行动，就会去"修"一个不存在的问题、甚至压低版本。

**修法**：新契约连同 `.meta.json` 一起覆盖默认快照（两行 `cp`），重跑即 138/138 零漂移（当时基线为 `0.2.0-rc.1`；**2026-09-29 升到 `0.2.0-rc.2` 后为 140/140**，见 `docs/parity-matrix.md` §3.1）。

**两条可复用的判据**：
1. 比对型门禁（基线 vs 被测物）**必须回答"两侧各是哪一版"**；
   只说"有差异"的门禁，在基线掉队时会**系统性地把"多了"读成"少了"**。
2. **看到"删除/移除"先怀疑自己的基线，再怀疑上游** —— 上游删端点是低频事件，
   基线掉队是每次升级都会发生的事件（E383 §8.16 记的是同族错误：那时是"无法区分新漂移与旧欠账"）。

## 10. 语音识别：从 HMS 换成 SenseVoice 端侧离线模型（E-SV1 … E-SV8）

### 11.1 为什么换：HMS 流式听写的硬约束（七轮真机实测）

HMS `speechRecognizer` 是**流式听写引擎**，带内建 VAD 端点检测：

| 事实 | 证据 |
|---|---|
| 单会话只处理**开头 4~5 秒** | 喂入 4025~4152ms 即提前结束；4.0/8.0/13.82s 音频**返回同一结果** |
| 端点检测不可关 | `extraParams` 全 SDK 只有 `locale`/`recognizerMode`/`online` 三个键 |
| `recognizerMode:'long'` **更差** | 实测**禁用** VAD（`vadBegin=false`）、喂满全长、返回**空** |
| `{mode}/{type}` 对象形式**无效果** | 与不传完全相同（喂入 4111/4140ms，VAD 照常触发）|
| 前导静音**有害** | 中段音频 +220ms 静音即让 VAD 完全不触发（0/3 复现）|
| 无独立文件转写 API | 全 SDK 搜 `transcribe`/`longAudio`/`enableVad`/`maxSpeechDuration` 零命中 |
| 中段"可识别"是**偶发** | 一次成功（`什么？`）后连续 3 次全空；官方黑盒 7 窗口扫描亦未复现 |

⇒ **结论：4~5 秒是引擎固有行为，不是配置问题。长语音在此路线上无法稳定实现。**

### 11.2 换成什么：sherpa-onnx 官方**已有**鸿蒙移植（E-SV1）

**这是本次最重要的发现，也是"不要重复造轮子"的直接命中。**

| 事实 | 内容 |
|---|---|
| OHPM 官方包 | `sherpa_onnx@1.13.3`（Apache-2.0，**58 个版本**）|
| 源码内置 | `harmony-os/` 下 **6 个官方鸿蒙示例 App**（含 `SherpaOnnxVadAsr`）|
| 官方构建脚本 | `build-ohos-arm64-v8a.sh` / `-armeabi-v7a.sh` / `-x86-64.sh` |
| 作者预编译 | `onnxruntime-ohos-arm64-v8a-1.16.3.zip`（HF 镜像 `hf-mirror.com`）|

**HAR 内含四个 arm64-v8a 库，依赖闭包全在鸿蒙系统内：**

```
libc++_shared.so          NEEDED: libc.so
libonnxruntime.so         NEEDED: libc++_shared.so, libc.so
libsherpa-onnx-c-api.so   NEEDED: libhilog_ndk.z.so, librawfile.z.so, libonnxruntime.so, libc++_shared.so, libc.so
libsherpa_onnx.so         NEEDED: libace_napi.z.so, libhilog_ndk.z.so, librawfile.z.so,
                                  libsherpa-onnx-c-api.so, libonnxruntime.so, libc++_shared.so, libc.so
```

⇒ **零 glibc 依赖**；`libace_napi.z`/`libhilog_ndk.z`/`librawfile.z` 都是 OHOS 标准系统库。

**教训（方法论）：GitHub 搜 `sherpa-onnx + openharmony` 返回 0 结果，不代表没有现成方案 ——
要看项目源码里的 `build-*.sh`。`build-ohos-arm64-v8a.sh` 一直都在。**

### 11.3 为什么不能用官方 release 的 linux-aarch64 预编译件（E-SV2）

onnxruntime 的 `linux-aarch64` 包（7.2MB）**不可用**：

```
libonnxruntime.so  NEEDED: libdl.so.2, librt.so.1, libpthread.so.0, libstdc++.so.6,
                           libm.so.6, libgcc_s.so.1, libc.so.6, ld-linux-aarch64.so.1
```

八个依赖**全是 glibc 专有**，鸿蒙一个都不提供 ⇒ 必须用作者为 OHOS 编译的那份
（`NEEDED: libc++_shared.so, libc.so`）。

### 11.4 交叉编译 onnxruntime 的坑（E-SV3 … E-SV6，留档以免重走）

即使最后没用自己的编译产物（改用官方预编译件），这些坑都真实存在：

| 编号 | 现象 | 根因 / 修法 |
|---|---|---|
| E-SV3 | `unrecognized arm64` | OHOS toolchain 只认 `OHOS_ARCH=arm64-v8a`（不是 `arm64`）|
| E-SV4 | `--gcc-toolchain ... unused` 触发 **-Werror** 编译失败 | OHOS clang 用不上该参数（正常警告），而 onnxruntime 带 `-Werror` ⇒ 加 `-Wno-error=unused-command-line-argument` |
| E-SV5 | `Failed to connect github.com:443` 拉依赖失败 | `github.com` 不通但 **`codeload.github.com` 可达** ⇒ 用等价的 codeload URL 预取 zip 放进 FetchContent 期望路径 |
| E-SV6 | `Could NOT find Python3` | onnx/onnx 的 `CMakeLists:125` 是 `find_package(Python3 REQUIRED Interpreter)`，**无条件**；Windows 侧取便携版 `python-3.12.10-embed-amd64` 解压即用 |

**CMake 配置确实跑通了**（`Configuring done` + `build.ninja` 生成），证明 OHOS 工具链
能编 onnxruntime —— 只是有更省事的官方预编译件可用。

### 11.5 sherpa-onnx 的 CMake 读**环境变量**而非 `-D`（E-SV7）

`cmake/onnxruntime.cmake` 用 `$ENV{SHERPA_ONNXRUNTIME_INCLUDE_DIR}` /
`$ENV{SHERPA_ONNXRUNTIME_LIB_DIR}`（第 156/170 行）。

**传错形式的后果很误导**：传成 `-D` 变量 ⇒ 它没看到 ⇒ 走 `download_onnxruntime()`
⇒ 平台白名单里没有 OHOS ⇒ 报

```
Only support Linux, macOS, Windows, and Android at present. Will support other OSes later
```

—— 看着像"不支持 OHOS"，实际只是**环境变量没给到**。给对了就完全绕过平台判定。

### 11.6 provider 侧只需替换识别后端，协议不动

`HmsSpeechBridge.ets` 里只有**一行**是识别调用点（`handleRequest` 内），
队列协议（`.req`/`.wip`/`.done`/`.fail`）与 provider 的 `transcribe()` 全都不动。

- `SenseVoiceRecognizer`（新）：持 230MB 模型，**必须单例**（懒加载、复用）
- 桥：`SenseVoice 优先 → 失败回退 HMS`（保留回退便于对照）
- `location` 从 `'cloud'` 改 `'host-local'`：模型随包内置，语义正确；
  **不会**因此弹"需安装依赖"——官方 UI 的门是
  `needsSetup = phase === 'unprepared' && location === 'host-local'`，
  而本 provider 不提供 `preparation` ⇒ `snapshot()` 补成 `phase='ready'` ⇒ 门不成立

### 11.7 打包的两个必做步骤（E-SV8）

1. **`pack-core.mjs` 必须带 `--place-in-app`**
   —— 否则 zip 只落在 `dist/core/`，**不会进 `entry/src/main/resources/resfile/`**，
   HAP 里就还是旧 core 树。provider 改动会静默丢失。
2. **核心 zip 的幂等优化会吃掉小改动**
   —— 只改 `hms-provider.js`（`11086 → 11347` 字节）不足以触发重打包；
   验证 HAP 里 core zip 的 mtime 与源文件 mtime，必要时**先删 zip 再打包**。

**验证到"HAP 内 core zip 内"这一层才算数**：

### 11.8 ArkTS 侧 API 对照（已逐项核对官方示例）

```ts
import { OfflineRecognizer, OfflineRecognizerConfig, OfflineStream,
  OfflineRecognizerResult, SileroVadConfig, TenVadConfig, SpeechSegment,
  Vad, VadConfig } from 'sherpa_onnx';

const config = new OfflineRecognizerConfig();
config.modelConfig.senseVoice.model = 'sensevoice/model.int8.onnx';
config.modelConfig.tokens = 'sensevoice/tokens.txt';
config.modelConfig.senseVoice.language = '';      // 留空 = auto
config.modelConfig.senseVoice.useItn = true;
const recognizer = new OfflineRecognizer(config, resourceManager);  // mgr 用于读 rawfile

const vad = new Vad(new VadConfig(
  new SileroVadConfig('sensevoice/silero_vad.onnx', 0.5, 0.25, 0.5, 512, 20),
  new TenVadConfig('', 0.5, 0.25, 0.5, 256, 20), 16000, false, 1), 60, mgr);

// 识别（SenseVoice 是离线批处理：一次给整段、一次出结果，无端点截断）
const stream: OfflineStream = recognizer.createStream();
stream.acceptWaveform({ samples, sampleRate: 16000 });   // samples 是 [-1,1] Float32
recognizer.decode(stream);
const result: OfflineRecognizerResult = recognizer.getResult(stream);  // result.text
```

**注意类型名**：`getResult` 返回 `OfflineRecognizerResult`（不是 `OnlineRecognizerResult`，
后者是流式那套的）。`SpeechSegment` 只有 `{samples: Float32Array, start: number}`。

### 11.10 签名 profile 绑定 bundleName —— 改 bundle 名会连带改签名（E-SV9）

**现象**：把 `build-profile.json5` 的 `bundleName` 从临时的 `com.dshm.micverify`
改回正式的 `com.dshm.dshclient` 后，构建在 `SignHap` 失败：

```
ERROR: 00303074 Configuration Error
The bundleName in app.json5/hvigorfile.ts does not match
the bundleName in the generated SigningConfigs.
```

**根因**：`signingConfigs.default.profile` 指向

```
%USERPROFILE%\.ohos\config\default_desktop.ohos.arm64_<hash>.p7b
```

这个 `.p7b` 是 **provisioning profile，内部绑定了一个具体 bundle-name**。
DevEco 在创建 `com.dshm.micverify` 时自动生成的就是**绑 micverify 的那一份**，
里面明文写着 `com.dshm.micverify`（当时 `~/.ohos/config` 下只有这一份 .p7b；**2026-09-30 复核：现已有 3 套**）。

⇒ **不能靠改 JSON 换回正式包**；换回必须在 **DevEco GUI 里对
`com.dshm.dshclient` 重新走一次自动签名**（需登录华为账号 + 设备在线）。

**教训**：改 `bundleName` 不是一个"只影响装到哪个包"的单点动作 ——
它同时决定了**签名材料**，而签名材料是 GUI 生成的、不在仓库里。
所以"临时改 bundle 验证、验完改回"这个计划里，**改回这一步是有外部依赖的**，
不是删两行注释就完事。

**当前处置（2026-09-30 更新：本节结论已被推翻，保留作历史）**：
`bundleName` 已于 2026-09-27 之后**改回 `com.dshm.dshclient` 并成功构建**。
证据：`AppScope/app.json5:3` 为 `com.dshm.dshclient`；**已构建产物**（读 HAP 内 `module.json`，
非读源码）`entry-default-signed.hap`（314,166,762 B，2026-09-29 22:48）的
`app.bundleName = com.dshm.dshclient`。`~/.ohos/config` 现有 **3 套**签名材料
（2026-09-27 11:17 / 09-27 21:49 / 09-28 08:49），不再是"只有绑 micverify 的那一份"。
⇒ 上面"不能靠改 JSON 换回正式包"的推论**在当时成立、现已不成立**：重新走一次
DevEco 自动签名即可，无需保持临时包名。装机纪律不变：只 `hdc install -r`（见 `tools/update-device.ps1`）。

### 11.11 与官方示例的两处刻意偏离（E-SV10）
| **E-SV11** | **下载保存失败：把 228MB 全读进内存** | 界面报"磁盘空间不足或没有写入权限"，实际磁盘空闲 174GB。原实现 `chunks.push` 累积后 `Buffer.concat`，峰值内存 ≈2×228MB；端侧嵌入式运行时分派失败，且被错误分类成 `storage`。改为 `openSync`+`writeSync` 边读边写盘，PC 实测峰值 heapUsed 9.9MB |
| **E-SV12** | **新增模块未被打包** | `pack-core` 只拷 `speech-provider/index.js` → `lib/hms-provider.js`；provider 以 `../speech-models/index.js` 引用下载器 ⇒ 解析到 `<pkg>/speech-models/`。不显式拷贝则运行时 `Cannot find module`。已在 pack-core 拷贝且**缺失即报错** |
| **E-SV13** | **全新安装首次录音必失败（权限从未申请）** | 官方流程是「Web `getUserMedia` → `onPermissionRequest` → 申请权限」，但**原生采集覆盖绕过了 `getUserMedia`** ⇒ 申请路径永不执行 ⇒ `createAudioCapturer` 失败 ⇒ 界面报「录音中断，请重试」。测试包早前已授权所以掩盖了该缺陷。修法：`startNativeCapture` 先 `ensureMicPermission()`；JS 等待窗口 3s→15s（首次要弹系统授权框）|
| **E-SV14** | **补丁注入的幂等陷阱：改了但没生效** | pack-core 的守卫是"文件含标记就整段跳过"，核心树里已有旧版注入 ⇒ 新增的 `amplitude` 覆盖**从未被注入**，而 pack-core 仍报"✓ 完成"。改为**版本标记**判断（`@v3-…`），版本不同则先删旧注入段再注入。**同类问题凡"改注入代码无效"优先怀疑此处** |
| **E-SV15** | **频谱恒为最小值** | 官方 `Waveform` 每 50ms 调 `recording.amplitude()`，它读 `this.analyser`；而原生采集覆盖了 `start()` ⇒ 创建 analyser 的那段被跳过 ⇒ 恒返回 0。修法：覆盖 `amplitude()` 改读 ArkTS 侧 `rms`。**用 RMS 而非峰值**（官方按下式用 level：`height=1+min(1,level*5)*17`；真机实测平静说话 peak/4 已达 14.6/18，而 RMS 与官方同口径 9.1）。平方和在**已有**采样循环里顺带累加，不新增遍历（新增遍历曾致丢块、VAD 失效、识别全灭）|
| **E-SV16** | **装机后首次打开白屏（启动竞态，非代码缺陷）** | 为强制重解包核心树（25,914 文件）每次装机删 `.dshm-bundled-stamp` ⇒ 宿主该次启动 `+6648ms`；WebView 早于它就绪发起加载 ⇒ **HTTP 404** ⇒ `fail()` ⇒ `phase=ERROR` ⇒ 白屏。**重启即恢复**（实测转 200）。**诊断教训**：`BOOT_*`/`DSHM_READY` 打在 **node-output.log**，不在 `dshm-host.log`，只看后者会误判成"宿主从未就绪" |
| **E-SV17** | **`check-native-closure` 白名单漏登记系统库 ⇒ 门禁长期 FAIL** | 白名单把 `libace_napi.z.so`/`libhilog_ndk.z.so` 列为系统库，**漏了 `librawfile.z.so`**（`docs/70` 的依赖表把三者并列，明说都是 OHOS 标准库）。sherpa 自引入起依赖它 ⇒ 门禁一直报"1 个依赖无法解析"。**判定"是否本轮引入"用 A/B**：拿备份的原始 HAR 解出 `.so` 跑同一判定，同样 FAIL（我只删了 x86_64，arm64 字节未动）⇒ 既有缺陷。补白名单后转 PASS |
| **E-SV18** | **打开即白屏（其他人也遇到）—— "一次竞态后再无自愈"** | 宿主**首启解包后固定要 6～7 秒**才可用（真机 `+6384/+6610/+6645/+6885ms`，几乎每次），而 WebView 的 `src` 直接绑 `launchUrl` ⇒ 页面在"端口未绑"窗口里请求 ⇒ **HTTP 404** ⇒ `fail()` ⇒ ERROR 且**原实现停住不动**（只能手动点重试）⇒ 表现为白屏。**竞态无法消除，修在自愈**：新增 `scheduleAutoRetry()`（退避 0.6s→1.2s→…，最多 6 次）。**次生陷阱**：`onPageEnd` 在失败时也触发（加载的是 ArkWeb 错误页）且只晚 10ms，会**无条件置 READY 抹掉 ERROR** ⇒ 用户连"重试"按钮都看不到；须用 `loadFailed` 标志阻断。真机取证（文件标记）：`404 → 排第 1 次重试(600ms) → 1.6s 后 200` |
| **E-SV19** | **HAR 自带多 ABI 库，`abiFilters` 拦不住** | `build-profile.json5` 的 `abiFilters: ["arm64-v8a"]` **不影响 HAR 内的 `libs/x86_64`** ⇒ 20.4MB 无用库进 HAP（先前 `nativeLib.filter.excludePattern` 尝试亦无效）。改在源头：HAR 是 tar.gz，解包删 `package/libs/x86_64` 后重打包（备份 `.har.bak`）。**还必须清 `oh_modules/.ohpm` 的 sherpa 解包缓存并 `ohpm install`** —— ohpm 按 lock 判定，不会因 har 文件变化重新解包，否则旧缓存把 x86_64 带回来。HAP 320.1 → 299.5MB |
| **E-SV20** | **诊断踩坑：`BOOT_*`/`DSHM_READY` 不在 `dshm-host.log`** | 本轮据 `dshm-host.log` 判定"宿主从未就绪"，据此得出"真实启动失败"的**错误**结论；实际这些标记打在 **`node-output.log`**，宿主完全正常（`BOOT_60/65/70` + `DSHM_READY` 齐全）。**另一条**：本机 **hilog 会丢日志** ⇒ 时序类排查必须用**文件标记**取证，不能凭"日志没出现"下结论 |
| **E-SV21** | **门禁里存在自相矛盾的断言（命名往返的化石）** | `assert-python-bridge.mjs` 同时断言 `includes('/dshm-python/')` 与 `!includes('dshm-python')` —— **不可能同时成立**。它长期"通过"是因为当时文档里是 `hdsh-python`，恰好一条命中一条不命中。文档注释里"（DSHM 版曾标注不支持）"暴露了这是 **DSHM→HDSH→DSHM** 的往返，该断言是更早一轮的"清除 DSHM 残留"守卫。修法：方向翻转到旧名 `hdsh-python`，守卫意图不变 |
| **E-SV22** | **改标记名后 pack-core 重复打补丁 ⇒ 打包 die（同一类共 7 处）** | pack-core 用**字面标记**判"是否已打过"（`text.includes('DSHM_ORIGIN_LIST')`），而树里是**上一版**打的旧标记 `HDSH_ORIGIN_LIST` ⇒ 判成未打过 ⇒ 重复替换 ⇒ 锚点已消失 ⇒ `die`（严格性正确，正是它暴露了问题）。涉及 ORIGIN_LIST/LINK_SANDBOX/CREDENTIALS_MODE_EXEMPT/READONLY_STACK_GUARD/FS_LOCAL_SANDBOX/ATTACHMENT_SANDBOX/WORKFLOW_DISABLED。**两步修**：① 判定兼容新旧名；② 删 `dist/core/work/<ver>` 重新 npm install 物化，让旧标记随上游解包消失（验证：旧标记残留 **0**）。**通用教训：凡改幂等标记名，必须同时认旧名**，否则老产物无法增量重建 |
| **E-SP1** | **启动页过后约 2 秒白屏** | 启动页只挂在 `BOOTING`，而阶段流转是 `BOOTING → enterLoading() → LOADING → 200`。**`LOADING` 没有任何覆盖层** ⇒ 直接露出底层 Web（未渲染完的空白 / 上面那次 404 的错误页）⇒ 那 2 秒白屏。修法：启动页条件加 `LOADING`。**但必须带 `!everReady`** —— `onPageBegin` 在整页导航时也会把 `READY` 打回 `LOADING`，只看 phase 会让**每次应用内跳转都闪启动页**（自身回归，已自查修掉）|
| **E-SP2** | **启动进度条不准 + 中途冻结** | 原实现 `setInterval(…, 220)` 每拍 `+3`：① 走满需 **7.3s**，与真实耗时接近纯属**巧合**，首启（30–60s）时会"跑满一圈又重来"；② `phase !== BOOTING` 就 `stopLoadTicker()` ⇒ 进 LOADING 后**冻结**（那时其实还在加载）。修法（第一版）：**按经过时间渐进** `90×(1−e^(−t/τ))`，τ=3200ms，上限 90%，就绪时置 100%；覆盖 BOOTING+LOADING 全程。⚠️ **该指数方案已被 E-SP5 取代** —— 实测开头 28%/s、末段 2.3%/s 相差 12 倍，用户复报"还是冲"；现为**匀速直线**（11.5%/s → 92% 后 0.3%/s 慢爬，上限 98%）|
| **E-SP3** | **启动慢的主体在 dsh 上游，不在本项目** | 实测分段：`aa start`→Node ~2.1s；→`BOOT_40` 0.3s；**→`BOOT_50` 7.4s（`runProfile` 内部）**；→`BOOT_70` 0.2s；WebView→200 1.7s；合计 **~10.1s**。7.4s 是 dsh 加载插件树，属上游（项目纪律：对上游零 patch）。要真正缩短只能减少启动插件数（设备上 19 个非种子行），属产品决策。**量化手段**：临时给 `runProfile` 前后插计时桩读到 `+7261ms`，**插桩已完全撤除**并核验无残留 |
| **E-SP4** | **`aa start` 失败要先读 Error Code，别急着怀疑代码** | 本轮排查中一度误判"应用崩溃"（进程 0、无 diag、hilog 无异常）。真实原因：`Error Code:10106102 The device screen is locked during the application launch` —— **设备锁屏**。教训：`aa start` 的返回值一定要读，设备状态问题与代码问题表现相同但成因完全不同 |

官方 `harmony-os/SherpaOnnxVadAsr` 是**示例**，用法与本项目的集成有两点不同。
两处都是**有意识的选择**，这里记下理由，免得后来人以为是疏漏。

**① 官方把 ASR 放在 worker 线程；本实现放在桥的线程。**

- 官方：`Index.ets` 用 `worker.ThreadWorker('entry/ets/workers/NonStreamingAsrWithVadWorker.ets')`，
  模型初始化与 decode 全在 worker 里，主线程只收发消息。
- 本实现：`SenseVoiceRecognizer` 直接在桥的上下文里跑。
- **为什么这样**：桥本身是 ArkTS 侧的子任务（`setInterval` 轮询文件队列），
  不在 UI 渲染路径上；再加一层 worker 会引入"worker 生命周期 + 消息序列化"
  两个新的失效面，而识别是**串行、用户显式触发**的，没有并发需求。
- **补偿措施**：加了 `warmUp()`（见下），把最重的模型加载挪到空闲时。
- **若日后发现卡 UI**：把 `SenseVoiceRecognizer` 整体搬进 worker 是干净的改法
  —— 它已经是**无 UI 依赖的独立类**，接口只有 `recognize(pcm)`。

**② 官方在 `aboutToAppear` 里 `postMessage({msgType:'init-...'})` 显式初始化；
本实现用 `warmUp()` 预热 + `ensureReady()` 懒加载兜底。**

- **为什么必须预热**：provider 侧单次识别预算 `TIMEOUT_MS = 25000`
  （`hostcore/speech-provider/index.js` 的 `awaitResult`，且对长音频按
  `audioMs + 15000` 伸缩）。若不预热，**第一次**点麦克风要在这 25 秒里
  完成"读 230MB rawfile + 建 onnxruntime session + 初始化 Silero VAD"，
  超时对用户表现为"识别超时" —— **必然发生，不是概率问题**。
- **为什么 `warmUp()` 先 `setTimeout(0)` 让出一次**：ArkTS 主线程上做长同步
  加载会卡住 UI，本项目已吃过同类亏（`docs/70` E45：`LIFECYCLE_TIMEOUT` + `SYS_FREEZE`）。
  让出一次让首帧先渲染。
- **为什么失败不抛**：预热失败只在心跳里记一笔；真正的错误留到 `recognize()`
  如实抛出，那时用户能看到原因，而不是在启动阶段静默失败。
- **桥的调用点刻意不 `await`**：桥必须立刻开始轮询，否则请求堆在队列里。

**待真机确认项**：首次预热耗时（心跳会写 `预热成功 模型已就绪=true`）
与首次识别的实际延迟。若预热本身超过 ~20 秒，需要重新考虑
（2026-09-27 设备离线，未能实测）。

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| **E-DH1** | `check-dead-handlers` 报 **180 处**空实现，其中 **177 处是误报**（回调 prop 的**必需默认值** `onX: (a: T) => void = () => {}` —— ArkTS 组件若回调 prop 无默认值，父组件不传就**编译失败**），**2 处是真·死按钮** | 旧判据报"所有跨行空箭头"，无法区分"声明默认值"与"调用处内联空实现"。180 处的报告量让门禁**彻底失去信号** | 收紧判据：只看**调用处**（组件构造参数里的 `onX: () => { },`）—— 那才是"子组件一调就无反应"。**结果：180 → 2 → 0** |

**两个真 bug 的最终处置**（都**是有意的空实现**，但**原先没有任何文字说明** ⇒ 门禁报得对）：

**收紧过程中修的两个自身缺陷**：
1. **跨行声明形态漏判**：`MessageRow.ets` 写成 `onX: (…) => void =` 换行 `(…) => {` ⇒ 判据只看单行会误判成"调用处空实现"。改为**同时看本行与上一行**。
2. **只看"声明行之后"导致 6 处误报**：ArkTS 组件里 `build()` 常写在成员声明**之前**（`this.onCoreAction(id)` 在 202 行、声明在 322 行）⇒ 判成"无人使用"。改为**扫全文件、只排除声明那一行**。

### 12.6 本节可复用的三条方法

1. **门禁必须在已知坏版本上红过一次**，否则不知道它能不能拦住东西（E-RV4 用"注入 bug 的脚本副本"验证）。
2. **假阳性比漏报更糟**：它会让人不再逐条看，真问题就淹在里面（E-DH1 的 180→2→0 是最直接的证据）。
3. **"只 print 不校验"是假门禁**（E-RV4 的第三条），"文档说了、配置没做"同理。

## 13. 冷启动 62 s 全静默的真根因：平台门放行后的 `process.report.getReport()`（E388）

> 这一条按主题属于 §1（平台与进程模型），放在文末是为了**不移动任何既有行号**——
> 本仓的文档交叉引用是 `file:line` 形式，中间插一节会把后面所有引用点顶偏（`tools/check-doc-refs.mjs` 会当场报错）。

这是 §1.6（E103 自建 flock）的**回声**：加载问题修好了，却在**平台判断**这一步留下一个 56 秒的同步调用。

- **现象**：冷启动后 8–70 s 内宿主**完全静默**：3120 端口 TCP 三次握手成功，但**一个请求都不 accept**，
  WebView 侧刷出成片 `[WebNetwork] NetworkTransactionTimeout`。用户体感是「点登录转圈半天不跳浏览器、
  模型选择一直加载中、插件市场与预览一起卡」——三个看起来无关的 bug，其实是同一行代码。
  恢复后积压请求一次性涌出，登录 2.2 s 就跑完。
- **取证链**（三个自证读数器 + 一次 `.cpuprofile`）：
  ① 心跳线程连续（`dshm-hb.log` 每秒一行、`cpu=` 单调增）⇒ **进程没被冻**，是 JS 主线程被**同步**调用挡住；
  ② `LOOP-GAP 62915ms`，而同段 `SYNC-COUNT 同步调用总耗时 425ms`（我们包装过的 fs 只占 0.4 s）
  ⇒ **大头在包装面之外的 native**，只看 fs 记账会得出「没有同步调用」的错结论；
  ③ `.cpuprofile`（61,621 样本）判决 A：**最长连续非空转同栈 55,829 样本（≈55.8 s，自耗时占 90.6%）**，整条链是
  `getReport @node:internal/process/report ← loadBinding @…/node-addon-system/lib/flock.js:6 ← errno ← tryLockExclusive ← SessionWriteLease.acquire`。
- **根因**：`flock.js` 判断 libc 用的是 `process.report.getReport()`——它是「全进程诊断报告」，
  会枚举 CPU 并逐个打开 sysfs `cpufreq` 做**实时频率查询**（同族包 `node-addon-native-custom-loader` 的注释里写着
  "its CPU enumeration opens every sysfs cpufreq entry with a live frequency query, which takes seconds on many-CPU hosts"）。
  端侧实测 **55.8 s**，且是**同步**调用，正好落在会话写租约（`SessionWriteLease.acquire → tryLockExclusive`）的热路径上。
- **为什么是我们的回归**：上游在 openharmony 上直接抛 `ERR_FLOCK_UNSUPPORTED_PLATFORM`（**快失败**）；
  是 `tools/pack-core.mjs` 的 E103 平台门（`platformRaw === 'win32' || 'darwin'` 之外一律当 `linux`）**放行了**这条路，
  把「立刻失败」变成「静默挡住 56 s」。
- **为什么本机复现不出来**：PC 上 `process.platform === 'win32'`，走的不是这条分支
  （4-bundle 实验与 `_bootprobe.mjs` 全是负结果，都源于此）。
  **教训**：「本机复现不出」不等于「设备上不是这个原因」——平台的**分支差异**能把 bug 整段藏住。
- **修法**：`tools/pack-core.mjs` 里重写 `flock.js` 的那段模板不再调 `getReport()`，改为读 `/proc/self/maps`
  判 glibc/musl（`node-addon-native-custom-loader` 同款；读不到 maps 就按 musl）。安全性依据：两个 libc 变体本来
  都是**同一份占位文件**、由 `.node` 处理器按 **basename** 重定向到 HAP `libs/arm64/libsystem.so`
  ⇒ 判 glibc 还是 musl **完全不影响加载**。
- **真机复验（同一台设备、同一个冷启动窗口）**：修复后 `LOOP-GAP` **0 条**、`.cpuprofile` 转储 **0 次**、
  `session/modelCatalog` 首次 **66,503 ms → 4,535 ms**（随后 58–222 ms）、最慢请求 4.5 s、无 ≥10 s 请求；
  预热后第二次冷启动同样 `LOOP-GAP` 0 条。

## 14. 三处"随包但没进坑库"的端侧补丁（E-RES / E-PDF / E-TERM）

> 同样按本节规矩追加在文末（中间插入会顶偏既有 `file:line` 引用）。这三条是 2026-10-03 随文件能力
> 一起进的构建期补丁，**2026-10-05 审计**发现它们在 `dist/sideload/README.md` 与 release notes 里
> **完全没被记录**（包里有、文档里没有），且坑库零命中 —— 本节补齐，避免下一个维护者重踩。

### 14.1 E-RES：ArkWeb 把 `dsh-resource://…` 解析成 opaque URL

- **现象**：右侧栏**所有**资源预览报「文件资源服务不可用」（GitCode #1）。
- **根因**：客户端用 `new URL(address)` 取 `hostname`/`pathname` 来解析自定义协议，而 ArkWeb 对该协议
  返回 **opaque URL**（`URL.hostname === ""`）⇒ 取不到主机与路径。
- **修法**（构建期补丁，`tools/pack-core.mjs:2432-2540`）：`protocolOf` 在 `hostname === ""` 时**用正则
  从原串重新取**协议/主机/路径；同样修侧栏 `pathOf` 与 subagent 的 host/path/query 解析。
  落地处：`dsh-client-resources/lib/client.js:23-31`、`dsh-client-ui-sidebar-right/lib/client.js:8647-8650`、
  `dsh-client-ui-subagent/lib/client.js:722-731`。
- **教训**：**自定义协议在 WebView 里不等于标准 URL 语义**；凡是要拆 URL 的地方，都要先确认"这个协议在
  目标 WebView 里是不是 opaque"。

### 14.2 E-PDF：同进程里的"第二个 realm"让 `Map.getOrInsert` 补丁只装了一半

- **现象**：侧栏 PDF 预览在新版内核上崩溃/白屏。
- **根因**：PDF worker 由 **Blob URL** 起，**不继承页面启动期的注入** ⇒ 页面里装了 `Map.getOrInsert`
  兼容，worker 那个 realm 里没有（同一个进程、不同的 JS realm）。
- **修法**（`tools/pack-core.mjs:2604-2637`）：**两处各装一次**（chunk 工厂 `lib/client.pdf.js:980` +
  内联 worker Blob `:24740`），并留下 `DSHM_MAP_COMPAT` 标记（实测出现 2 次、`install(Map.prototype` 4 次）。
- **教训**：**"进程内"不等于"同一个全局环境"**——Blob worker / iframe / 二次编译的脚本都是新 realm，
  与 worker 线程那条坑（本文件 §7）同源但更隐蔽。

### 14.3 E-TERM：平台白名单漏了 openharmony ⇒ 终端整条不可用

- **现象**：端侧终端打不开（GitCode #2 主因），真机报
  `subprocess-local: terminal inspection is unsupported on platform openharmony`。
- **根因**：上游 `createProcessInspector()` 按 `platform === "linux"` 枚举，openharmony 落到末尾 `throw`。
- **修法**（`tools/pack-core.mjs:2639-2687`）：鸿蒙 `/proc` 与 Linux 同构（`readdir(/proc)`、
  `/proc/<pid>/stat` 的 `tpgid`/`starttime`、`/proc/<pid>/fd/0` 均可用；缺 `syscall` 但上游本就 try/catch 降级）
  ⇒ **复用 `LinuxProcessInspector`**；同时把 `shellActivity` 注入在鸿蒙上**短路**（它给 bash 注 `--rcfile`、
  给 zsh 注 `ZDOTDIR` + `add-zle-hook-widget`，而端侧那条链现在是系统 `/usr/bin/zsh`）。
  落地处：`dsh-subprocess-local/lib/runner-launch-B2zsQ1Dz.js:670`、`lib/index.js:1164`、`:856`。
- **真机证据**：`docs/HANDOFF.md:631` —— `ps` 见 `/usr/bin/zsh -i`、PPID=Host、fd→`/dev/pts/0`，
  PTY 回显 `ZSH=5.9`（同时证明白名单补丁生效，否则 `index.js:1419` 先抛）。
- **残留边界**：终端 activity 读数在该平台恒 `unknown`（`shellActivity` 被短路），功能不受影响。
- **教训**：**"换个平台就把枚举漏一个"** 是上游适配的常态；我们的做法是"发现即补 + 门禁化"——

## 15. `emitter.off` 与 `on`/`emit` 的 API 不对称（E-EMIT）

- **现象**：`emitter.off({ eventId: X }, cb)` 编译失败 ——
  `Argument of type '{ eventId: any; }' is not assignable to parameter of type 'string'`。
  而且**9 个级联错误只定位到这一行**，容易误判成"别处写坏了"。
- **根因**：SDK 声明本身就是不对称的（`@ohos.events.emitter.d.ts`）：
  `on(event: InnerEvent, cb)` 与 `emit(event: InnerEvent, data?)` 收 `InnerEvent`（`{ eventId }`），
  而 `off` 的四个重载是 `off(eventId: number)` / `off(eventId: string)` /
  `off(eventId: number, cb)` / `off(eventId: string, cb)` —— **一个都不收 `InnerEvent`**。
- **修法**：退订写 `emitter.off(EVENT_X, cb)`（传**裸 number/string**）。
  另一个坑：`emitter.on` 不返回句柄 ⇒ 想退订必须**自己保存回调引用**（本项目照 `unwatchInput` 的写法：
  私有字段 + `aboutToDisappear` 里 `off` 后置 `undefined`）。
- **纪律**：写"订阅 + 退订"成对代码时，**两端都要对着 SDK 声明各核一遍**，不要只核注册端就照抄形状；
  这类"同一 API 家族里签名不一致"的坑不会在注册端暴露。
