# 103 · 手持档工作区路径的采纳判据：ArkTS 探写会撒谎，宿主才是判官

> 2026-10-06（第五轮，真机 HUAWEI Mate 80 / `VYG-AL00`，`deviceType=phone`）。
> 用户报障原话：「设置各类基本的基本都正常，但是工具调用、侧边栏、终端这些都异常，主要看这些」。
> 本篇记录复现、两条对立读数、根因、判据改法，以及「为什么 2in1 / PC 不受影响」。

## 1. 现象（真机复现，非偶发）

`uitest dumpLayout` 拿到的原文（右侧边栏「文件」页签）：

```
读取失败：cannot list "/storage/Users/currentUser/Download/harness": permission denied
```

`harness` 就是**新会话的默认工作区**（首页工作区 chip 显示 `harness`）⇒ 每个新会话的文件页都读不出来。

## 2. 两条互相矛盾的读数（同一路径、同一台机）

| 侧 | 操作 | 读数 |
|---|---|---|
| ArkTS | `probePathWritable()`（`fileIo` 的 create+write+unlink） | **通过** |
| 宿主（node） | `workspaceFiles/list`（`readdir`） | `cannot list "…/Download/harness": permission denied` |

ArkTS 侧「通过」的落盘证据是 `diag-resolve-dispatched`（设备 `…/haps/entry/files/`）：

```
2026-09-27T12:26:14.805Z path=/storage/Users/currentUser/Download/harness
2026-10-06T03:55:19.577Z path=/storage/Users/currentUser/Download/harness
```

同一台机上宿主**自己认领的目录**是好的（`dshm-host.log` 原文）：

```
默认工作区：/storage/Users/currentUser/Download/com.dshm.dshclient（来源=DSHM_PUBLIC_DOWNLOAD，
            即 ArkTS 经 DOWNLOAD 模式认领的 Download/<包名>/，用户可见；
            选择理由=lstat 判为目录且 create+write+unlink 全部通过）
[dshm-workspace-claim] 默认工作区已登记：/storage/Users/currentUser/Download/com.dshm.dshclient
                       （workspaceId=2f2ae667-9f89-4da7-93e5-adbf82b04c19）
```

## 3. 根因：两侧走的不是同一条文件通路

* **ArkTS**：`fileIo` 对沙箱外路径由 `file_access_service` **代理**，picker 授权的那条 URI
  在服务侧认得 ⇒ create+write+unlink 全过；
* **宿主**：`dsh-fs-local` 直接 `import node:fs`，是**裸 syscall**，不认 URI 授权 ⇒ 连 `readdir` 都被拒。

⇒ 手持档上「ArkTS 探写通过」**推不出**「宿主能用」。旧判据把这两件事当成了同一件
（2026-10-03 的注释里写着「Host 能『读』」——那是在 2in1 上量的），于是：

1. 采纳了宿主读不到的路径；
2. 该路径被持久化成会话默认工作区（el2 注册表，覆盖安装不清）；
3. 文件页每次必失败。错误文案由**官方 Web 界面**渲染（我们改不了它）⇒ 只能从源头不采纳。

## 4. 判据改法（落点）

原则：**只接受落在「宿主自己验过的目录」里的路径**；那份目录就是启动期
`claimPublicDownloadFolder()` 对 `Download/<包名>/` 跑的那次 create+write+unlink。

| 文件 | 改动 |
|---|---|
| `platform/src/main/ets/system/FilePicker.ets` | 新增 `isHandheldForm()` / `isPathWithin()`（含上述两条读数与理由）；`pickFolder()` 的采纳判据分两支 |
| `platform/src/main/ets/Index.ets` | 导出上面两个判据 |
| `entry/src/main/ets/pages/WebApp.ets` | `doPick()`（官方 Web 的「添加工作区」走这条）用同一分支，并把 `handheld` 写进 `diag-picker-public-fallback` 标记 |

替换提示文案按档分开：手持档说「宿主读不到（系统只把目录授权给了本应用的 fileIo 代理）」，
其它档保留原文（「Host 只能读、不能写入/删除」）。

## 5. 为什么 2in1 / PC 不受影响（构造上）

| 约束 | 做法 |
|---|---|
| PC 那条路不改 | `handheld === false` 时逐字走原来的 `probePathWritable(realPath)`，**不**调用 `publicDownloadFolder()`（不新增任何动作） |
| 读不到形态时不误伤 | `readDeviceFacts()` 抛错 ⇒ `isHandheldForm()` 返回 `false` ⇒ 退回 PC 旧行为（保守方向） |
| 手持档兜底也拿不到时 | 保持旧行为（返回用户选的路径），不发明第二种失败形态 |
| 不碰宿主与核心树 | 本轮**只动 ArkTS 侧**（platform + entry）：`hostcore/**`、核心树补丁、resfile 容器均未变 |

## 6. 未做 / 待决

* **已存在的那条坏登记（`harness`）没有被删** —— 它属于用户数据（el2 注册表）。
  出路：在 UI 的工作区管理里删掉它，或直接改用应用专属目录；两条都不需要卸载/清数据。
  本轮改动只保证**不再产生新的坏登记**。
* 手机上「添加工作区」从此只能落在应用专属目录内 —— 这是平台边界，不是本轮的取舍：
  宿主（node）在手持档对 picker 目录没有路径级访问。若将来要让用户选中的**任意**目录可用，
  需要另开一条通路（ArkTS 侧中转的读写 API，或让宿主走 URI），属独立课题。
* 平板档（`deviceType=tablet`）与手机同归手持、判据一致，但没有单独的真机读数。
