# 102 · 手持形态（手机 / 平板）朝向：改为**跟随屏幕旋转**

> 2026-10-06（第四轮，真机 HUAWEI Mate 80 / `VYG-AL00`，`deviceType=phone`）。用户报障与口径：
>
> ① 「这是宽度不够，可以考虑手机、平板设备可以横屏使用」→ 先按**横屏**做（`AUTO_ROTATION_LANDSCAPE`）；
> ② 同轮追加「手机平板的设备设置可以跟随屏幕旋转…**首次安装初始化的时候横屏就可以完整设置了，
> 然后平时用的时候可以竖屏，就跟随屏幕旋转**」⇒ 改为 `AUTO_ROTATION`（=5）；
> ③ 随后再追加定案：「**跟随系统旋转锁定，锁定的话就不能转，解锁就可以旋转**」（=5 真机实测
> 「开着旋转锁定照样能转」，口径不对）⇒ 最终 **`AUTO_ROTATION_RESTRICTED`（=8）**。
>
> 本篇记录判据、落点与真机读数；顺带把这一轮取到的**手机档能力边界**读数一并归档（§5）。

## 1. 现象与判据：为什么必须「能横过来」

真机读数（手机档，Mate 80）：

| 项 | 读数 |
|---|---|
| 屏 | 1280×2832 px，density ≈ 3 ⇒ **427×944 vp** |
| 系统 | OpenHarmony-7.0.0.105 / API 26（应用 `build.default.sdk 6.1.1(24)` 不变） |
| 竖屏「设置」对话框 | 宽 1113 px，左侧页签可见（通用设置 / 模型 / 内置插件 / Agent 预设），**右侧内容被裁到屏外** |
| 横屏同一对话框 | `[84,217]–[2751,1099]`，右栏 `权限 / 语言 / 外观` 与 `打开配置文件` 都在屏内 |

判据出处（仓库既有设计，本轮**没有**改布局代码）：

- `appstate/src/main/ets/ui/LayoutController.ets`：把**手机横屏**归为双栏形态
  （`landscape: input.widthVp > input.heightVp`）；
- `appstate/src/main/ets/ui/Breakpoints.ets`：双栏 ≤840 vp / 三栏 ≥840 vp。

⇒ 竖屏 427 vp 落在**单栏**，官方 Web 客户端的两栏「设置」放不下；横屏 ≈944 vp 才进双栏/三栏。
**这不是布局 bug，是物理宽度**：能横过来就完整，横不过来就只能裁。

## 2. 决定：`AUTO_ROTATION_RESTRICTED`（=8）

SDK 原文（`@ohos.window.d.ts` 的 `window.Orientation` 枚举）：

| 枚举 | 值 | SDK 原文要点 |
|---|---|---|
| `LANDSCAPE` | 2 | 锁死单一横屏方向，翻面会看到**倒置**界面 |
| `AUTO_ROTATION` | 5 | 随传感器覆盖**四个方向**；「**不受**控制中心旋转开关管辖」⇒ 锁定状态下照样能转 |
| `AUTO_ROTATION_LANDSCAPE` | 7 | 只在横/反向横两向跟随；同样不受旋转开关管辖（竖屏手感全丢） |
| **`AUTO_ROTATION_RESTRICTED`** | **8** | 方向集合与 5 **完全相同**（竖/横/反向竖/反向横），但「**受**控制中心旋转开关管辖」 |
| `AUTO_ROTATION_UNSPECIFIED` | 12 | 受旋转开关管辖，方向集合「**由系统决定**」；属 SessionManager、`@since 12` |

**先按 5 做过一版，真机实测口径不对**：用户开着「旋转锁定」时它**照样能转**，与系统里其它应用
的行为不一致 ⇒ 定案 **8**。三条理由：

1. **跟系统开关走**——用户第二轮口径原文：「手机、平板 屏幕旋转跟随系统旋转锁定，**锁定的话就
   不能转，解锁就可以旋转**」；8 是唯一「保留四向跟随 + 把决定权交回旋转开关」的取值；
2. **不选 5**：它「不受控制中心旋转开关管辖」，真机实测锁定状态下仍能转 ⇒ 等于让「旋转锁定」
   这个开关在本应用上失效；
3. **不选 2 / 7 / 12**：2 锁死单方向（翻面倒置）、7 只横屏两向（竖屏手感全丢）；12 语义相同但
   方向集合由系统决定、且属 `SystemCapability.Window.SessionManager`（`@since 12`）——
   本工程要的是**明确**语义，故选 8。

**代价（主动取舍，如实登记）**：锁定状态下本应用保持竖屏 ⇒ 官方 Web 界面的两栏「设置」会重新
被裁（§1 的物理宽度问题依旧）。用户口径就是「想横过来就解锁，平时按系统开关走」。

## 3. 落点与分层理由

- **机制层**（`platform/src/main/ets/window/WindowRegistry.ets`）：新函数
  `followScreenRotationOnHandheld(windowStage)`。`platform` HAR 的对外口径是「只提供**机制**、
  不含产品策略、不认识 DSH 上游」，朝向是纯系统能力，放这里合规。
- **门面**（`platform/src/main/ets/Index.ets`）：与既有 `currentWindowId` / `openSessionWindow` 同一块导出。
- **装配层**（`entry/src/main/ets/entryability/EntryAbility.ets`）：`onWindowStageCreate` 里、
  `windowStage.loadContent('pages/WebApp', …)` **之前**调用。

两条设计取舍，写在代码注释里：

1. **为什么在 `onWindowStageCreate`**：会话窗是**独立 `EntryAbility` 实例**（各有自己的
   `onWindowStageCreate`）⇒ 一处调用等于所有窗口一起生效；`BackGroundAbility` 没有窗口，不受影响。
2. **为什么不用 `module.json5` 的 `orientation` 字段**：manifest 一收严就难回退，
   且**无法只对手机/平板分档**——本工程资源目录只有 `base / dark / en_US / rawfile / resfile`，
   没有按形态分档的位置；用运行时调用则「读不到形态就降级为系统默认」，不会把 PC 档搭进去。

失败只记日志（`setPreferredOrientation` 的 `catch` + 外层 `try`）：拿不到朝向不影响启动。

## 5. 顺带归档：手机档能力边界（读数，非本轮回退）

同一轮真机读数（`node-output.log` / `dshm-host.log` 原文）：

```
[2026-10-06T03:54:24.506Z] exec 探测：python3.12=缺，git=缺，git-core/git=缺，git-remote-http=缺，
                            rg=denied，ash=denied，bash=denied，git-ls-remote=缺
[2026-10-06T03:54:24.081Z] bash 垫片：bash/hush 已布置（解释器 …/files/bin/ash；busybox 无 bash applet）
[2026-10-06T03:54:24.231Z] 工具链：解包子进程异常：Error: spawn …/files/bin/busybox EACCES
```

判据出处：`hostcore/profile/ondevice/cordis.patch.yml`（「**手机档内不生效**：`ash` 副本在本档
同样 `denied`」；PC/2in1 档实测 `exec 探测 8/8` 含 `ash=ok`）、`hostcore/app/main.js`
（`ensureBashShim` 与 exec 探测的注释：随包自签名 ELF 的 `execve` 被**签名域 / MAC 策略**拒绝，
与 inode / 执行位无关）。

⇒ 手机档上：**终端（PTY 走 `shellPath`）与 `rg` / `git` / `python` 这类 exec 型工具不可用**；
对话本身、`bash` 工具的**单条平凡命令**（真机实测 `pwd` 返回一行）与全部 HTTP 面能力正常。

## 6. 未做 / 待决

- **平板档**：`followScreenRotationOnHandheld` 对 `FormFactor.TABLET` 同样生效，但本轮**没有平板真机**，
  未取读数（平板横屏在仓库里是「三栏」，方向策略相同、收益更大）。

  会话正文可见高度偏小（输入框会浮在正文之上）。属**观感**问题，本轮未改，登记在此。

  属鸿蒙软键盘与 Web 输入框的一般交互，非本轮引入。
