## 0. 验证总则

1. **顺序纪律**：POC-1 是全方案的生死门，未通过前**不得**投入 P1 之后的功能开发；其余可并行。

4. **回写纪律**：任何与 D1/D2 不符的结论，必须在结论落地的同一次提交中修订对应文档。

## POC-1 原生协议往返（**生死门**）

| 项 | 内容 |
|---|---|
| **目标** | 证明 ArkTS 原生客户端能完成 dsh 协议的完整往返：认证 → 一元 RPC → 逻辑流 → 事件流 |
| **为什么是门** | 若原生 ArkTS 无法满足该协议（cookie/WS 心跳/取消/信封校验），整个「原生客户端」架构不成立 |
| **前置** | 可访问的 dsh Host（本机 loopback 或已配对地址）；可部署的最简 ArkTS 工程；`tools/protocol-suite` 的 token 交换能力 |
| **步骤** | 1. 用 `@ohos.net.http` 请求 `GET /?token=<token>`，捕获 `303` 与 `Set-Cookie`；<br>2. 开启 `enableAutoCookie(true)`（或手动管理 cookie），请求任意已确认端点 `POST /api/<endpoint>`，校验 `{type:"server-response", rpcId, result}`；<br>3. 用 `@ohos.net.webSocket` 打开 `wss/ws://<authority>/api/remote.mux`，发送 `{type:"open", streamId, endpoint:"$events", payload:{}}`——**注意 mux 的上行 open 帧实参是 `payload` 本身且 `$events` 要求空对象**，不要照一元 RPC 的 `payload:{args:{…}}` 包装（D2 §8.7.9 实测：写成 `args` 会被服务端以 `1008` 关闭）；<br>4. 记录帧序列，确认首帧为 `ready`（含 `clientId`、`host.home`），随后收到增量事件；<br>5. 保持连接 ≥ 5 分钟，确认不被 2 s 心跳断开；<br>6. 主动发 `{type:"cancel", streamId}` 并确认流终止 |
| **判定（全部满足）** | ① `303` + cookie 落盘成功；② 至少一次一元调用返回 `ok:true`（用 `session.create` 或等效只读端点）；③ `ready` 首帧到达；④ ≥ 1 条增量事件到达且可解析；⑤ 5 分钟心跳存活（无服务端主动断开）；⑥ `cancel` 生效 |
| **必须记录的抓包事实** | `item` 帧完整字段；`error` 帧完整字段；ArkTS WS 是否自动回 Pong；事件项结构 |
| **失败处置** | **立即评估架构 C**（ArkWeb + 官方 dist + 合法暴露方案），暂停 M2 之后的一切开发，回写 D1 §6.2 与 D2 §7（A-1/A-2/A-5） |
| **产出** | `specs/poc/poc-01-*.md` + `tools/protocol-suite/fixtures/mux/*.jsonl` + `fixtures/events/catalog.md` 首版 |
| **回写** | D2 §1.2、§1.3、§7（A-1/A-2/A-5） |

## POC-2 loopback 直连可行性

| 项 | 内容 |
|---|---|
| **目标** | 确认端侧应用（同机跑 Host 的 2in1/PC 场景）能直连 `127.0.0.1:<port>` |

## POC-4 长连接稳定性与恢复（不重不漏）

| 项 | 内容 |
|---|---|
| **目标** | 弱网、切网、前后台切换各 10 分钟，重连后事件流**不重、不漏** |
| **步骤** | 1. Host 侧记录事件序列（含序号/时间）；<br>2. 端侧订阅 `$events` 并本地落盘收到的序列；<br>3. 依次执行：断 Wi-Fi 60 s → 恢复；切 4G ↔ Wi-Fi；App 切后台 10 分钟 → 回前台；Host 进程重启；<br>4. 每次恢复后按 D2 §3 的退避表核对重试档位；<br>5. 用工具对账两侧序列，输出差异报告 |

### 已实施部分（2026-09-11）

`platform/src/main/ets/system/SecretStore.ets` 用 **Asset Store Kit**
（`@ohos.security.asset`，系统在 HUKS 之上的封装）保存 token；
`HostStore.ets` 把**非敏感**的 Host 地址走 `preferences`、token 走前者。
分开两个 store 是刻意的：让「哪些字段是敏感的」在代码结构上成立，
而不是靠约定。

实测得到的、写在这里以免重踩的三个系统事实：

| 事实 | 后果 |
|---|---|
| `Tag.IS_PERSISTENT` 需要 `ohos.permission.STORE_PERSISTENT_DATA`（仅系统应用） | 带上它 → `201 The caller doesn't have the permission`，**保存静默失败** |
| 失败时**绝不降级为明文**（本实现的选择） | 失败只影响「下次能否自动重连」，本次连接不受影响 |
| `SessionHub.configure(address, name)` 的第二参是**显示名，不是 token**；token 从地址串解析 | 自动重连时若只传裸 baseUrl，会拿空 token 去认证，界面显示「连接失败（HTTP 0）」——看起来像网络问题 |

**仍待完成**：卸载/清数据残留检查、日志全文审查的第三方签署、
以及把签名 cookie 也纳入加密存储（当前 cookie 每次启动重新兑换，不落盘）。

### 待收口（2026-09-11 记录，按影响排序）

> **本轮结论：两处缺口都已补上，恢复链现在完整可见。**
>
> 修了两件事：
> 1. `Connection.handleMuxDead` 过去**只改状态、不驱动重连**——`scheduleReconnect`
>    仅由 `start()` 与事件流 `onEnd` 调用，于是「探活发现失效了，但连接永不恢复」。
>    现在它用 `start()` 时记下的 `startSink` 重新进入重连循环（策略仍集中在
>    `ReconnectController`，不自己实现退避）。
> 2. `SessionHub` 过去**只**通过事件流 `onEnd` 感知失败，**从不订阅连接状态**——
>    所以底层降级对本层不可见，横幅仍显示「连接 live」。
>    现在 `connect()` 里 `conn.onStateChange(...)` 把载体事实映射到中枢阶段
>    （映射而非照抄：底层 `CONNECTING` 在中枢是「降级」，不是「首次连接中」）。
>
> **设备实测的恢复链（trace 原文）**：
> ```
> connection degraded: 第 1 次重试将在 264ms 后进行（档位 500ms）
> connection disconnected: 重试已耗尽：探活发送失败 code=-1
> events end 重试已耗尽：探活发送失败 code=-1
> ```
> 横幅显示 **`连接 degraded`**（不再是与事实相反的 `live`）。
>
> **剩下的阻塞点在传输通道**：这台设备上 `hdc rport` 的转发会失效，
> 失效后**所有重试都失败**（因为重试也走同一条已死的转发）。
> 因此**「恢复」无法在 rport 通道上验证**——需要在一条可靠通道上验证
> （D1 §6.5 的 hostkit 加密隧道，或真机 + 局域网直连）。

### `$events` 载体问题（2026-09-11 **已定位并修复**）

**症状**：设备上 `$events` 逻辑流在 `open` 后约 27 ms 内被关，
错误统一是 `carrier/closed: ws error code=200 message=undefined`；
一元 HTTP RPC 同时全部正常。它阻塞了审批/提问推送、通知、设置页外部改动刷新。

**根因（设备内部实测，D2 §8.7.10）**：ArkTS 的 `WebSocket` 会在**链路健康**时
抛出 `code=200 message=undefined` 的 `error` 事件，且**不伴随 `close` 事件**；
而 `RemoteMux` 旧实现把这个 `error` 当成「连接已断」，直接终止了全部逻辑流。

设备内部探测（`entry/src/ohosTest/ets/test/MuxProbe.test.ets`）的关键读数：

| 观察 | 数值 |
|---|---|
| 升级 | `connected=true` |
| 窗口内是否收到 `close` | **`closed=false`（从未收到）** |
| `error` 到达时间 | **73–198 ms** |
| 连接是否存活整个 8 s 观察窗口 | **是** |
| 有无客户端心跳配置的差异 | **无** |

**因此 `hdc rport` 转发与 ArkTS 实现都不是问题**——连接实际是好的。
（先前文档里「转发通道不可靠」的结论是**错的**，已被这条实测推翻。）

**修法（最终版）**：不再围绕 `error` 做任何判定——它只记入 `lastError` 供诊断展示；
判死只认 WebSocket 层的 `close`（权威信号）+ 库自身的心跳。
（中间那版「6 s 活性宽限期」也是错的：计时器是**连接级**的，而 `session/control`
空闲时不推数据帧，于是被 `$events` 的计时器一起误杀。详见 D2 §8.7.10。）

**修复效果（设备实测）**：启动后 30 秒以上窗口内不再出现 control error carrier/closed、
不再出现 events end 重试已耗尽，会话列表顶部也不再出现错误横幅（修复前 3–6 秒必现）；
诊断页「协议」判定为 **「WebSocket 已建立；事件流 live」**。

**仍未解决**：`session/control` 仍报一次 `carrier/closed`。按同一机制，
最可能是该流空闲时确实不推送任何帧。下一轮应确认「开流成功但长期静默」
是否应**不算**断开（若是，判死只应依赖服务端 Ping 的存活信号）。
**设置页外部改动自动刷新**：接线正确但**本机无法验证**——实测该 Host 用直接 RPC
改设置后**不产生** settings/document-updated（ 本身工作正常：建会话即收到
emit:api-session/added）。详见 D2 §8.7.11。

### 设备 ↔ Host 端到端验证（2026-09-10，**一元链路已通过；长连接仍受限**）

在模拟器内让应用真的连上宿主上的 `0.1.5-rc.1` Host，用来验收真实的协议往返。
做法：宿主起一个隔离 DSH_HOME 的 Host（端口 3115），用 `hdc rport tcp:3116 tcp:3115`
把设备侧的 3116 反向转发到宿主，然后在应用里「添加 Host」粘贴带令牌的启动链接。

| 环节 | 结果 | 证据 |
|---|---|---|
| 设备侧发起 HTTP 到宿主 | ✅ | 首次用错方向（`fport` 是宿主→设备）时，界面如实报 `code=2300007 Failed to connect`；换成 `rport` 后即连通 |
| token → 签名 cookie 认证 | ✅ | 界面显示「已连接」，说明 303 + Set-Cookie 流程在设备上走通 |
| mux 物理连接 + 打开 `$events` / `session/control` | ✅ | 旁路日志 `control open ok` |
| **`session/list` 一元调用** | ✅ | 旁路日志 **`list ok 4 条`**；界面「收到 4 个会话」 |
| **真实列表渲染（标题兜底 / 副信息 / 相对时间）** | ✅ | 4 条真实会话显示 `deepseek-harness-desktop-HarmonyOS`（`title` 实测为 `null`，走 cwd 末段兜底）+ 完整 cwd + 「29 分钟前」 |
| **状态徽标基于真实事实** | ✅ | 全部 `新会话`（真实 `blank:true, running:false`、无待决），不再凭空出现「待审核 2 / 失败」 |
| `$events` / `session/control` 长连接存活 | ❌ | 旁路日志 `control error carrier/closed`（约 30 ms 后）与 `events end … ws error code=200`（约 18 s 后） |

#### 结论修正记录（一次被推翻的归因，留档为教训）

第一轮验证时 `session/list` 报 `carrier/parse`，据此判断「根因是 `hdc rport` 扛不住并发」
并写进了本文档与提交说明。**该结论是错的**，被第二轮验证推翻：

- 真正的根因是 `connection` 的 `checkTarget()` 把 `/api` 当成「被保留、调用方不得使用」的
  channel 拒绝，而 `Connection.call()` 正是用 `surface.apiChannel`（= `/api`）调它——
  于是**每一次一元 RPC 都被守卫拦下**，且失败码伪装成 `carrier/parse`（看着像网络问题）。
- 修掉守卫后，**同一个 `hdc rport` 通道上 `list ok 4 条`**——直接证伪了「通道不行」的归因。
- 为什么会误判：认证走 `AuthSession` 直连 HTTP、流走 `RemoteMux`，都不经过该守卫，
  所以「能认证、能开流」造成了「连接正常」的错觉；而 `carrier/parse` 这个码同时覆盖
  「响应确实解析不了」与「我们自己拼错了 endpoint」两种完全不同的原因。
  **已给调用方错误单列 `client/endpoint-invalid`**，避免再次把排查引向网络方向。

**这条教训比结论本身重要**：错误码一旦复用了语义相近的类别，
每一次归因都建立在猜测上。错误码必须能区分「谁的错」。

#### 仍然成立的部分

长连接的失败（`control error` / `events end`）在修掉守卫后**依然存在**，因此独立于上述 bug。

现有证据指向**转发通道**，而不是 Host 的心跳超时：

| 观测 | 数值 | 说明 |
|---|---|---|
| Host 心跳阈值 | 每 2 s Ping，`MAX_MISSED_HEARTBEATS = 2` → 约 **4–6 s** | 已读上游代码确证（D2 §8.2），非文档推测 |
| 实测关闭时刻 | 第二条逻辑流打开后约 **27 ms** | `control open ok` → 27 ms 后 `control error carrier/closed` |
| 同一时刻的 HTTP | **成功**（`list ok 4 条`，紧随其后 31 ms） | 短请求可用、长连接不可用 |

27 ms 比 4–6 s 快两个数量级，**心跳超时不足以解释它**；而「短请求成功、长连接随即断开」
更像转发通道无法同时承载两条长连接。

**仍未验证**：ArkTS 是否自动回 Pong（D2 §8.2 的未决风险）。要单独验证它，
需要一个不经转发通道、只维持**一条** WebSocket 的对照实验。

**尚未验证**：轨迹（`session/follow`）与待决（waterfall）在设备上的真实渲染——
它们依赖那条不稳定的长连接。要关闭它，最小实验是**把 ArkTS 客户端接到 `hostkit` 的
加密隧道**（隧道已建成，`node --test` 295 项通过，含端到端隧道测试），
而不是继续在 `hdc rport` 上调试。

### 第三轮设备验收（2026-09-11，清理桩数据之后）

本轮的目标不是新功能，而是**「界面是否在说实话」**：此前工作区、文件树/预览、
斜杠命令、`@` 引用、设备页 Host 列表、详情栏分区六块是编造的示例数据，
桩数据不报错，所以「没接上」与「正常」在界面上完全一样。

| 环节 | 结果 | 证据 |
|---|---|---|
| 未连接时为空态（不是假会话） | ✅ | 布局原文：`还没有会话` / `在 Host 上新建会话后会自动出现在这里` |
| 连接失败如实报错（不是 `live`） | ✅ | `连接失败（HTTP 0）：无法连接到 127.0.0.1:3120：code=2300028 Operation timeout` + `连接 degraded · 逻辑流 0` |
| 横幅提供「手动重连」（D3 §4 必需动作） | ✅ | 布局原文 `重连`（`clickable`）与 `诊断` 并列；`degraded` 时才出现 |
| 手动重连真的重新认证 | ✅ | 点击后旁路日志：`pluginInventory ok 156 个条目`、`settings/describe ok, 1 个凭据引用, 48 个设置项`、`credentials ok 1 条`，并拉回真实会话列表 |

| 设置/凭据/插件为真实计数 | ✅ | `48 个设置项` / `1 条凭据` / `156 个插件条目`（均为 Host 实际返回） |
| 目录展开 / 文件预览 / 命令与引用候选 | ⛔ **未能验收** | `hdc rport` 转发在数秒内失效：每次加载完成后即 `control error carrier/closed`，随后的交互调用全部落空。属环境限制，不是实现缺陷 |

**本轮发现并修复的一个「界面说谎」型缺陷**（详见 D2 §8.7.16）：
`workspaceFiles/list` 的根目录必须传 `"."`，传空串被 Host 拒绝
（`gateway/bad-request: path is required`）。客户端把失败当成空目录，
于是界面显示「该目录暂无文件」——一个完全合理的状态，与真相相反。
**它不会报错，只会显示一个看起来正常但错误的结果**，正是本项目最需要防的那一类。

**本轮同时修掉的**：诊断页把受支持版本矩阵字符串塞进 `versionVerdict`，
而视图按三态分支渲染，导致三个分支**全部落空**（该区域无图标无文案）；
`SessionHub` 每次 `connect()` 都 `onStateChange` 一次，重连 N 次就有 N 个监听者
（同一份降级被处理 N 次）。

**给下一轮的最小实验**（顺序即优先级）：
1. 把设备接到 `hostkit` 隧道（或真机 USB 直连）后复跑「目录展开 → 文件预览 →
   输入 `/` 看命令目录 → 输入 `@` 看引用候选 → 详情栏分区」这条链，
   它们共用同一个前提：一次能活过 10 秒的连接。
2. 完整「失效 → 恢复」闭环：在可靠通道上断开（如停 Host 进程）→ 确认横幅为 `degraded`
   → 重启 Host → 点「手动重连」→ 确认回到 `live` 且数据重新拉取。
3. 附件上传：端侧文件选择（相册/文件选择器）+ 调 `fileUploads/upload`
   （载荷构造与回执投影已在 `Wire.ets` 中并有单测）。
