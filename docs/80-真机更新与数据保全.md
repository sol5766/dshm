# 真机更新与数据保全（事故复盘 + 强制流程）

> **本文档的起因是一次真实的数据丢失事故。**
> 如果你只读一段，读 §1 和 §2。

---

## 1. 事故：我把真机环境清掉了

**时间**：2026-09-25
**操作**：为"清理环境准备重装"，执行了

```powershell
hdc uninstall com.dshm.dshclient     # ← 裸卸载，默认连数据一起删
```

**损失**（真机实测）：

| 内容 | 结果 |
|---|---|
| 历史会话 | **6/6 全丢** |
| 已装插件 | **丢 7/8**（仅剩"智能体团队"） |
| 工作区 | **丢 2/3**（`test`、`data` 没了） |
| `.backup` 系统备份 | **空**，不可恢复 |
| `preferences` | **空** |

**这是不可逆的。** 没有备份可回滚。

### 更要命的是第二层错误

事故之后，我在汇报里把它写成了正常步骤：

> "清理 | 卸载旧应用（**连数据一起清**）、清设备临时文件、删 build/.cxx/.hvigor …"

**这等于把破坏性操作固化进了流程** —— 下一次照做，就会再丢一次。
比单次误操作更危险的是"误操作被文档正当化"。

### 根因

不是"不知道 `-r`"，而是：

1. **把卸载当成了清理的常规动作**，没有意识到它默认删数据
2. **没有向用户确认**就执行了不可逆操作
3. **事后没有把它标记为事故**，反而写进流程

## 2. 强制规则（唯一正确做法）

### 2.1 永远覆盖安装，永不卸载

```powershell
hdc install -r <hap>
```

`-r` = replace。同签名的覆盖安装：

| 路径 | 内容 | 覆盖安装后 |
|---|---|---|
| `/data/app/el1/bundle/public/<bundle>/` | 代码 + 资源 | **被替换**（这是我们要更新的） |
| `/data/app/el2/100/base/<bundle>/haps/entry/files/dsh/home/` | **会话 + 插件 + 配置** | **保留** |
| `.../files/dsh/cores/` | 核心树 | 保留（新版本解到新目录，旧的不动） |
| `.../files/toolchain/` | python / git | 保留 |
| `.../files/workspace/` | 工作区 | 保留 |
| `.../files/bin/` | busybox + wrapper | 保留 |

**判据**：`el1` = 代码（可换），`el2` = 用户数据（不可删）。

### 2.2 禁止清单

除非用户**明确说**"全部清掉"：

```
✗ hdc uninstall <bundle>
✗ hdc shell bm uninstall -n <bundle>
✗ rm -rf /data/app/el2/100/base/<bundle>/...
```

### 2.3 唯一例外（且必须先问）

| 情形 | 做法 |
|---|---|
| 用户明确要求清空/重装 | 先复述确认，再执行 |
| 换签名导致覆盖安装失败 | `hdc uninstall -k <bundle>`，**卸载后立即验证数据仍在**，不可假定 `-k` 生效 |

`-k`（`--keep-data`）确实存在（`hdc uninstall -h` 可见），但**未在真机上验证过**，
所以不能假定它一定保留成功。

### 2.4 唯一允许的装机入口

```
tools/update-device.ps1
```

它把上面所有规则做成了代码约束：

- 第 0 步**自检脚本自身**不含卸载调用（避免以后有人改坏它）
- 只用 `hdc install -r`
- 装前记录 `home` 条目数，装后比对，**减少就判 FAIL**
- exec 七项 + HTTP 就绪校验
- 任一步失败即停，不静默继续

用法：

```powershell
# 完整（构建 + 覆盖安装 + 验证）
.\tools\update-device.ps1

# 只装现有产物
.\tools\update-device.ps1 -SkipRebuild
```

> **诚实说明**：第 7 步的"数据保留"检查有个盲点 —— 如果安装前 `home` 就是空的
> （就像现在这台设备），前后都是 0，**检查无法发现丢失**，会打印 SKIP 而不是 OK。
> 脚本已如实标注"未能验证"，不会假通过。要在有数据的设备上才能真正验证它。

## 4. 插件与 DSH 版本的兼容边界

"保留会话与插件"的前提是**插件与核心版本不冲突**。

| 情形 | 可否直接覆盖安装 |
|---|---|
| 核心不变，只改 ArkTS / 宿主 | ✅ 可以 |
| 核心小版本升级（rc.2 → rc.3），插件只用公开 API | ✅ 可以（装后跑一遍插件面板） |
| 核心大版本升级，插件用了变更的 API | ⚠ 需评估插件能否加载 |
| 插件声明了核心版本约束 | ⚠ 先看插件 `peerDependencies` |

**结构性保障**：核心树按版本解到 `cores/<ver>/`，**旧版本目录不删**（可回退）；
插件在 `home/` 下，与核心版本目录**相互独立** ⇒ 核心升级本身不会动插件。

## 5. 回归反复（"修好后面、前面又坏"）

你提的第二个问题。本次确实发生过：修 javaScriptProxy 双桥覆盖时，
为定位原因交换过注册顺序，差点留下实验残留。

**三条纪律：**

1. **改前先跑基线**，记录结果
2. **改后跑同一批**，逐项对比；任何 ok → fail **当场修**，不许延后
3. **临时实验在同一次改动内还原**，把结论写进注释，不留实验代码

回归门禁：

```powershell
node tools/assert-cli-shim.mjs
node tools/assert-resfile-sync.mjs
node tools/check-parity.mjs
node tools/compat-drift.mjs
node tools/assert-exec-fix.mjs
node tools/assert-python-bridge.mjs
node tools/assert-fs-search-fallback.mjs
.\tools\device-acceptance.ps1
```

**为什么这条重要**：本项目有过"断言绿了但测错了对象"的先例
（如 `[bool]([regex]::Match(...))` 恒为真，掩盖了 5 个章节页缺背景的真 bug）。
"跑过了"不等于"修对了"，所以**门禁必须跑，但结论要人看**。
