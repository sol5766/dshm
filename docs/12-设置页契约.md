## 1. 回复顶层

```jsonc
{
  "writable": true,        // Host 是否接受写；false 时**所有**写控件都必须禁用
  "hasDocument": true,     // 是否有本地设置文档（不暴露 Host 路径）
  "namespaces": [ /* 每个已注册命名空间一项 */ ]
}
```

实测规模：`namespaces = 14` 个，`writable = true`，`hasDocument = true`。

## 2. 命名空间视图

```jsonc
{
  "ns": "ui-theme",
  "schema": { /* schemastery toJSON，见 §3 */ },
  "value": { /* 已脱敏的**解析后**值：schema 默认 → 组合基线 → 用户层 */ },
  "base":  { /* 可选：组合基线层 */ },
  "user":  { /* 可选：用户层原文；**字段出现在这里 = 被用户覆盖** */ },
  "applies": "live",       // 'live' | 'restart'
  "secrets": [ { "path": ["apiKey"], "set": false } ],
  "revision": 0            // 写回时必须带上（expectedRevision），否则并发写会互相覆盖
}
```

**关键事实（都由实测确认）**：

1. `value` 是**三层合并后的结果**，不是用户层。想表达「此项已被用户覆盖」必须看
   `user` 里有没有该字段——只看 `value` 无法区分「默认值」与「用户显式设成同一个值」。
2. `secrets[].path` 是**数组**，`ref = path.join('.')` 且**不带命名空间前缀**
   （与 D2 §8.7.2 第 18 条一致）。`set` 表示该槽位当前是否有值，**值本身永不上线**。
3. `revision` 是**写操作的并发令牌**，不是展示字段。上游对过期写返回
   `settings/conflict{ns, expected, actual}`，客户端必须重新读取后再写。
4. `applies: 'restart'` 的命名空间，改动后需要重启 Host 才生效——界面必须如实提示，
   不能让用户以为已经生效。实测 14 个命名空间**全部是 `live`**。

## 3. `schema` 的序列化格式（schemastery `toJSON()`）

**这是必须看实测才能写对的部分。** schema 不是一个嵌套树，而是一张
**以 `uid` 为键的扁平表** + 一个根 uid：

```jsonc
{
  "uid": 231,
  "refs": {
    "220": { "type": "const", "meta": {"required": true}, "value": "light" },
    "225": { "type": "union", "meta": {"default": "system"}, "list": [220, 222, 224] },
    "230": { "type": "number", "meta": {"step": 1, "min": 12, "max": 17, "default": 14} },
    "231": { "type": "object", "meta": {"default": {}}, "dict": {"preference": 225, "fontSize": 230} }
  }
}
```

要点：

- **`dict`**：对象字段名 → 子节点 uid。**设置项就来自这里**，且它通常只在根上有；
  嵌套对象（如 `llm-deepseek` 的 `retryPolicy`、`models[]` 的元素）也是 `dict`。
- **`union`**：`list` 是候选 uid；枚举选择项在实测里普遍是
  `union(list: const…, const…)`。**枚举的显示名在 `const.value` 里**（就是取值本身），
  上游没有单独的 label 字段。
- **`array`**：`inner` 是元素 uid。列表型设置（`models[]`）需要「编辑列表」，
  第一版可只读展示。
- **`meta`** 是字段级约束的**唯一**来源：`required`、`default`、`min`/`max`/`step`
  （数字）、`pattern`（字符串，形如 `{source, flags}`）、`role`。
  实测 `role: 'credential-ref'` 出现在 `llm-deepseek.apiKeyEnv` 上——
  这正是「这个设置项其实是一个凭据引用」的机器可读标记，设置页应把它渲染成凭据选择/链接，
  而不是一个普通文本框。
- **`const`**：常量字段（枚举分支）。根级 `dict` 里一般不会直接出现，只在 `union.list` 里。

### 5.2 写路径（已完成，2026-09-11）

实测 `settings/mutate` 的回复形状（`.research/protocol/probe-mutate.mjs`）：

```json
{"result":{"ok":true,"value":{"ns":"ui-theme","schema":{…},"value":{"preference":"system","fontSize":15},
 "user":{"fontSize":15},"applies":"live","secrets":[],"revision":1}}}
```

要点：

| 事实 | 含义 |
|---|---|
| 回复是**整个命名空间视图**（`ns,schema,value,user,applies,secrets,revision`） | 与 `describe` 里的一项同构 |
| `value` 是**合并后**的新值，`user` 出现该字段 | 写成功后 `userSet` 会变 true |
| `revision` 自增（0 → 1 → 2） | 并发令牌按预期工作 |

**实现选择**：写成功后**整页重拉** `describe`，而不是用回复里的视图局部替换。
理由是一条实测到的静默失效：局部替换只在「界面当前持有的视图确实来自 Host」时才是安全的；
写操作前后可能已被其它刷新改过分组，此时局部替换会**把旧分组原样保留**，
表现就是「Host 说写入成功、界面值却没变」——而且不报错。
整页重拉多花一次 RPC，换来「界面一定等于 Host 当前状态」这个不变量。

**另一个必须记住的坑**：写完之后**不要**再在界面层套一次 `applyHubSnapshot(hub.snapshot())`。
中枢在写成功时已经 `notify()` 过，订阅回调带着**已与本地偏好合并**的视图刷新界面；
再套一层快照会在「快照比 notify 更旧」时把刚刷新的值盖回旧值。这一层是多余且有害的。

**已实测的端到端链路**（模拟器 + 真实 0.1.5-rc.1 Host）：
> **版本说明（E239）**：本文件实测于 `0.1.5-rc.1`；当前端侧核心为 `0.1.5-rc.2`（并在真机上验证过切到 `rc.3`）。
> 上游面是否一致**不靠本文件的日期判断**，而由 `node tools/compat-drift.mjs` 判定（当前：84/84 无漂移）——见 `docs/40-上游升级手册.md`。

1. 设置页显示 `ui-conversation.busyEnter = queue`（revision 0）；
2. 点开选择浮层（显示 `queue` / `steer`，当前项标「当前」）；
3. 选 `steer` → 界面提示「已写入 ui-conversation.busyEnter。」；
4. 回读 Host：`value.busyEnter = "steer"`、`user.busyEnter = "steer"`、`revision = 1`；
5. 再选回 `queue` → 回读 Host：`revision = 2`、`value = "queue"`。

**写端点的选型**：用 `settings/mutate`（按路径 `set`），**不用** `update` / `replace`。
`update` 的 `patch` 是**浅覆盖**（改 `retryPolicy.maxRetries` 会整块替换 `retryPolicy`）；
`replace` **整体替换**用户 section（未出现的键被删除，用它改一个开关会误删其它设置）。
选错会**静默删掉用户的其他设置**。

**控件与本地偏好的区分**：点击时先查这个 key 是否在 Host 设置分组里。
不在 → 是本机偏好，如实说明「只在本机生效」；
在但不是枚举 → 说明「需要输入值，本客户端暂未提供该编辑器」，并指出可在 Host 设置文档里改。
两种情况都不发 RPC（否则会对不存在的命名空间发请求）。

### 5.3 凭据写路径（已完成，2026-09-11）

`credentials/set` / `credentials/unset` 已接通。实测得到的四条事实：

| 事实 | 含义 |
|---|---|
| `credentials/set` 的成功回复是 `{"ok":true}`，**没有 `value` 键** | 不能用「有没有 value」判成败——那会把每一次成功都判为畸形响应（D2b §4.1） |
| `credentials/unset` 同样回 `{"ok":true}` | 同上 |
| 写入成功且**跨重启持久** | 实测 `credentials/describe` 稳定回 `{configured:true, source:"file", writable:true}` |
| `credentials/describe` 是配置状态的**唯一权威** | 见下 |

**⚠️ 一个会撒谎的字段**：`settings/describe` 里 `secrets[].set` **不是**配置状态。
实测对同一个 Host 连续做 `set`（→ `credentials/describe` 回 `configured:true`）
与 `unset`（→ 回 `configured:false`），而 `settings/describe` 的
`secrets[].set` **始终是 `false`**。它表达的是「这个 secret 槽位**是否存在**」。
拿它当配置状态用，界面会**永远显示未配置**。因此 `projectCredentialRefs()`
只读 `path`，状态一律取自 `credentials/describe`。

**本客户端不保存明文**：值只在一次 `set` 调用里存在，随后立刻从内存消失
（D1 §11.5 S3/S4）。输入框用 `InputType.Password` 并关掉自动填充联想。

### 5.4 文本 / 数字编辑器（已完成，2026-09-11）

`TEXT` 类设置项（schema 的 `string` 与 `number`）已可编辑。

**为什么必须按类型发值**：实测 `ui-theme.fontSize` 的 schema 是
`{"type":"number"}`。把 `"16"` 当字符串发过去会被 Host 的 schema 校验拒绝，
而错误只说「不符合 schema」——用户看到一个自己按提示填的数字被拒，无从下手。
因此 `SettingItem.valueType` 记录线上类型，`parseSettingInput()` 负责转换。

**客户端先校验，Host 仍是权威**：`parseSettingInput()` 用实测取到的
`meta.min/max/step/pattern/required` 先在本地判一次，给出**具体**原因
（「不能大于 17」而不是「不符合 schema」），省一次往返；
Host 的拒绝走 `settings/rejected` 分支如实呈现，不被本地校验替代。

**一个刻意的边界**：schema 里的正则若**本身非法**（上游 schema 写错），
本地**放行**而不是拦下——否则一个坏 schema 会让这一项永远改不了。
交给 Host 判定。

**为什么用文本输入而不是数字步进器**：实测数字项跨度极大
（`llm-deepseek.maxTokens` 默认 256000，上界 9007199254740991），
步进器要点几万次，而不同项又需要不同步进。

**端到端实测**（模拟器 + 真实 Host）：设置页点 `llm-deepseek.maxTokens`
→ 浮层显示「编辑「Max tokens」/ 请输入数字；范围 1 – 9007199254740991」，
输入框**预填当前值 256000** → 改成 2560000 → 「写入 Host」→
提示「已写入 llm-deepseek.maxTokens。」→ 回读 Host
`value.maxTokens = 2560000`（**JSON 数字**，不是字符串）。探测后已复位为 256000。

**同时修掉一处「功能只存在于代码里」**：`SettingsPane` 的 `TEXT` 分支原本只是
一个带 `.maxLines(1)` 的静态 `Text`，**没有任何点击处理**。
数据与 `kind` 都对，但界面上完全看不出可以点（UI 导出里该节点没有
`clickable` 标记）——一个不可点的控件等于没有这个功能。
现在该分支有 `onClick` → `onEditText`。

### 5.5 结构化值（数组 / 对象）整值编辑（已完成，2026-09-11）

**先说结论：数组元素无法按路径寻址，只有整值写回一条路。** 实测
（`.research/protocol/probe-deep-path.mjs`）：

| 写法 | 结果 |
|---|---|
| `path: ['models','0','maxTokens']`（字符串下标） | `settings/rejected`：`$.models expected array but got [object Object]`——字符串段被当成**对象属性名**，于是往数组里加了个属性，数组就坏了 |
| `path: ['models',0,'maxTokens']`（数字下标） | `gateway/input-invalid`：连**线上边界校验**都过不去（`ops` 不接受数字段） |
| `path: ['models']` + 完整数组 | ✅ 成功 |
| `path: ['retryPolicy']` + 完整对象 | ✅ 成功 |
| `{op:'unset', path:['retryPolicy','maxRetries']}` | ✅ 成功（该键的用户层被移除，值回落到 schema 默认） |

因此编辑器是**整值编辑**（`SettingKind.STRUCT` + 多行 `TextArea`，
打开时把当前值缩进美化、写回时用紧凑 JSON）。

**写回语义按外层类型不同（这是最容易猜错的地方）**：

| 外层类型 | 写回语义 | 证据 |
|---|---|---|
| **对象** | **逐键合并**，未提到的键**保留** | 把 `retryPolicy` 写成 `{mode,maxRetries:9}`（故意省略 `retryableCodes`、`backoff`）后回读，缺失的键**原样保留** |
| **数组** | **整体替换**，未列出的元素**被删除** | 写成 `[]` 后 `models.length` 变 0 |

> **本项目的初版文案写的是「写回会整体替换」（对所有类型），实测后发现对对象是错的**——
> 它会让用户以为遗漏的键会被清掉。**文案错了也是一种撒谎**，已改正，
> 并写成断言（`states the correct write semantics per outer type`）防止回退。

**删除单个键**：实测 `unset` 在顶层与嵌套路径**都可用**，但本客户端当前**没有暴露**
该入口，界面上如实写明「暂不提供」，而不是提供一个半真的替代（例如「把值设为 null」——
那只是把值设成 null，并不会删掉键）。

**端到端实测**（模拟器 + 真实 Host）：`llm-deepseek.retryPolicy` 行显示
`union · 182 字符` 且可点 → 打开后 `TextArea` 里是缩进美化后的当前值
→ 「写入 Host」→ 提示「已写入 llm-deepseek.retryPolicy。」→ 回读 Host
得到完整对象（含嵌套 `backoff` 与数组 `retryableCodes`）。
数组行 `subagent-model-selection.allowedModels` 显示
「写回为整体替换（未列出的元素会被删除）」。

### 5.6 外部改动与「恢复默认」（已完成，2026-09-11）

**外部改动可见性**：接了 `settings/document-updated` 与
`credentials/reference-updated` 两条转发事件（两者都已在 `FORWARDED_EVENTS`
白名单里），触发一次**节流后**的设置重读。

- 为什么必须接：`settings/describe` 是**读一次就冻结**的快照。不接事件时，
  另一个窗口或另一台设备改了设置，本端会一直显示旧值，而且**手上的 revision
  已经过期**——用户改一次撞一次 `settings/conflict`，却看不出为什么。
- 为什么节流 1200 ms（比列表刷新的 800 ms 长）：实测 `document-updated`
  在**每次**提交后都会发，**包括本端自己写的那次**；太短会与写操作自身的重拉叠加。
- 为什么用**独立**的计时器与时间戳：共用会让「刚刷过会话列表」把设置刷新一起压掉，
  表现为别人改了设置而本端半天不动。

> ⚠️ **仍未完成端到端验证（2026-09-11 修正）**：上一轮曾判定「本机无法验证」，
> 那是**错的**——实测（`.research/protocol/probe-events.mjs`）：
>
> | 验证项 | 结果 |
> |---|---|
> | `$events` 帧形态 | ✅ 客户端正确（`eventsPayloadJson = {"args":{}}`） |
> | `$events` 是否投递事件 | ✅ 会——建一个会话即收到 `emit:api-session/added` |
> | 是否需要客户端先订阅 | ✅ 不需要 |
> | 一次 Host 侧 **RPC** `settings/mutate` 后 | ❌ 14 秒窗口内只收到 `ready` |
> | 在 Host 上**直接改设置文档**（`settings.yaml`）后 | ✅ 立即收到 `emit:"settings/document-updated",args:["ui-theme",9]` |
>
> 也就是说**验证路径是存在的**：「在 Host 上直接改设置文档」。
> 上一轮把「RPC 写入不触发」误当成「该 Host 不产生该事件」。
>
> 本轮按这条路径试了一次端到端（改文档 → 看界面），**未观察到界面自动更新**，
> 但**尚未取到 App 侧是否收到该 emit 的证据**，因此不能断言接线失效。
> 下一轮的判据：先在 App 诊断页确认 trace 里出现 `emit settings/document-updated`——
> 把「事件到没到」与「到了之后刷没刷」**分开**看。详见 D2 §8.7.11。

**「恢复默认」**：结构化编辑器新增该入口，走 `settings/mutate` 的
`{op:'unset', path}`。实测语义是**移除用户层取值、值回落到 schema 默认**，
因此文案写「恢复默认（移除这里的设置）」而**不是**「清空」——
`null` 在若干 schema 里是合法取值，`set null` 与 `unset` **不是一回事**。
入口只在 `userSet` 为真时出现：对继承默认的项执行 unset 是无操作，
给它一个按钮等于让用户白点一次。
