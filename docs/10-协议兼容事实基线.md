## 1. 载体与端点

### 1.1 一元 RPC（HTTP）

| 项 | 事实 | 来源 |
|---|---|---|
| 方法/路径 | `POST /api/<endpoint>` | 代码 |
| endpoint 构成 | descriptor 的 `namespace` + `method`，以 `/` 连接 | 代码 |
| endpoint 段字符集 | `^[A-Za-z0-9_$.-]+$`，禁止空段、`.`、`..` | 代码（`ENDPOINT_SEGMENT_PATTERN`） |
| channel 约束 | channel 必须匹配 `^/[A-Za-z0-9._~-]+$` 且不得为保留值 `/api`（`/api` 由 Gateway 认领） | 代码 |
| 请求头 | `content-type: application/json` | 代码 |
| 请求体 | `{ "type": "client-request", "rpcId": "<uuid>", "method": "<endpoint>", "payload": { "args": { ... } } }` | 代码 |
| 响应体（成功） | `{ "type": "server-response", "rpcId": "<同请求>", "result": { "ok": true, "value": <T> } }` | 代码 |
| 响应体（业务失败） | `{ "type": "server-response", "rpcId": "<同请求>", "result": { "ok": false, "error": { "code": "<string>", "message": "<string>", "details": { ... } } } }` | 代码 |
| 传输失败 | HTTP 非 2xx ⇒ 客户端侧抛 `transport failure for <channel>/<endpoint>: HTTP <status>` | 代码 |
| 信封校验 | `type` 必须为 `server-response`；`rpcId` 必须为字符串且等于请求；`result` 必须为对象；`ok=true` 时 **`value` 键可以不存在**（那是 `void` 端点的合法成功形态，上游有 4 个这样的端点，其中包含审批答复通道 `$events/result`）；`ok=false` 时 `error.code`/`error.message` 为字符串、`error.details` 为对象 | 代码（`parseConnectionResponse`）+ **2026-09-10 修正**（原记录为「`ok=true` 时须有 `value`」，已在 D2 §8.7.6 记录修正经过） |
| 取消 | 通过 `AbortSignal` 中止 HTTP 请求；Host 按 descriptor 的 signal 元数据支持取消 | 代码 + 官方文档 |

**待实测**：

- [ ] 超大 payload（图片）时的分块与 `maxRequestBodyBytes` 边界（默认 300 MiB）

## 2. 认证与信任

### 2.1 认证流程

| 步骤 | 事实 | 来源 |
|---|---|---|
| 1 | 进程启动生成**随机启动 token**（每进程一个） | 官方文档 |
| 2 | `dsh web` 打印并打开 `http://<authority>/?token=<token>` | 官方文档 |
| 3 | 仅 `GET /` 接受该 token：校验通过 → 写入**绑定 authority 的签名 cookie** → **303 重定向到干净的 `/`** | 官方文档 |
| 4 | 静态资源保持公开；`/api` 全部方法与全部 WS 流要求同一 cookie | 官方文档 |
| 5 | 缺失/过期/畸形/authority 不匹配的 cookie ⇒ RPC 分发前 **401** | 官方文档 |
| 6 | HTTP 载体**不接受** query token（除根路径交换）与 `Authorization` header token | 官方文档 |

**签名 cookie 属性**：

| 属性 | 值 |
|---|---|
| 密钥 | `ctx.credentials` 中由 `client-connection/browser-session` 拥有的 grant 记录；本地提供方持久化到 `$DSH_HOME/.credentials.yaml` |
| 名称与载荷 | 确定性名称；payload 同时绑定**规范化 hostname 与 port** |
| 绑定 | host-only；`Path=/` |
| 标志 | `HttpOnly`、`SameSite=Strict`；**刻意不设 `Secure`**（载体是 loopback HTTP） |
| 有效期 | 绝对签发/过期区间；`cookieMaxAgeDays` 默认 **30 天** |
| 撤销 | 无 logout 操作；清除客户端 cookie 结束单个会话；删除 owner 凭据记录并重启 dsh 撤销全部会话 |

### 2.2 信任栅栏（`src/api-request-trust.ts`）

| 规则 | 结果 |
|---|---|
| `Host` 为 loopback（`localhost` / IPv6 loopback / `127.0.0.0/8`），或匹配 `trustedHosts` 条目 | 通过 |
| `trustedHosts` 匹配语义：带端口条目按 `host:port` **精确**匹配；不带端口条目匹配**任意端口**；两侧经 WHATWG 归一化 | 通过 |
| 附带 `Origin` 时必须**等于**该 `Host` | 否则 403 |
| `sec-fetch-site: cross-site` | 一律拒绝 |
| 畸形配置 authority | 插件**加载失败** |
| 校验失败 | **403** |
| Host 可信但未认证 | **401** |

> 这些检查**防御 DNS rebinding 与跨站请求，绝不建立身份**——身份由 2.1 的 cookie 承担。

### 2.3 绑定姿态

| 配置 | 行为 | 来源 |
|---|---|---|
| `host` 取值 | 只接受 `127.0.0.1`（默认，仅回环）与 `0.0.0.0`（有意向网络开放；服务器自身**不携带 TLS、认证或来源策略**） | 官方文档（webserver） |
| CLI 姿态 | `dsh web --host 0.0.0.0` **在启动时被拒绝**（安全考虑）；`--trusted-host` 可追加权威 | 官方文档（web-app） |
| LAN 信任采样 | `resolveLanTrust` 启动时采样一次：loopback 绑定不派生 LAN 地址；`0.0.0.0` 绑定加入每个非 internal IPv4 字面量 | 官方文档 |

**结论（本项目的部署红线）**：端侧**永不**依赖 `0.0.0.0` 绑定，也**永不**改写 `Host`/`Origin`。跨设备接入必须让请求在 Host 看来仍来自 loopback（隧道出口回 loopback）或其权威在 `trustedHosts` 中显式登记。

## 3. 连接生命周期

| 状态 | 进入条件 | 来源 |
|---|---|---|
| `connecting` | 浏览器/客户端报告网络可用；或 `reconnect()` 被调用 | 官方文档 |
| `connected` | 收到 `$events` 的 ready 项 | 官方文档 |
| `disconnected`（终态） | 10s 档重试仍失败 | 官方文档 |
| 中断 | `offline` 事件：中断活动工作、发布 `disconnected`、暂停自动尝试 | 官方文档 |
| 恢复 | 下一次 `online`：重置序列，从 **500 ms** 档开始 | 官方文档 |

**退避表（确定性，必须逐档实现）**：

| 档 | 延迟 | 抖动 |
|---|---|---|
| 1 | 500 ms | 50%–100% |
| 2 | 1 s | 50%–100% |
| 3 | 2 s | 50%–100% |
| 4 | 4 s | 50%–100% |
| 5 | 8 s | 50%–100% |
| 6 | 10 s（上限） | 50%–100% |

**generation 失效条件（任一即失效）**：`$events` 结束 / Remote stream error / 收到**非 ready 首项** / 畸形事件项。

**重试前动作**：要求 mux **取消候选或活动 socket**，再重开 `$events`。

**待实测**：
- [ ] 端侧如何在 ArkTS 中获取「网络可用/offline」信号（`@ohos.net.connection` 能力确认）
- [ ] 后台切前后台的连接行为与系统限制（POC-4）

## 5. 备选协议：SDK JSON-RPC（stdio）

| 项 | 事实 | 来源 |
|---|---|---|
| 分帧 | 每个 `\n` 结尾行承载一条 JSON-RPC 2.0 消息 | 官方文档 |
| 帧判别 | 同时含 `id` + `method` ⇒ 请求；仅 `id` ⇒ 响应；仅 `method` ⇒ 通知；格式错误行**忽略** | 官方文档 |
| 错误码 | 无处理器 ⇒ `-32601`；处理器失败 ⇒ `-32603` | 官方文档 |
| 客户端→服务端 | `initialize`（`InitializeParams` → `InitializeResult`）、`session/prompt`（→ 持久入队回执）、`shutdown` | 官方文档 |
| 服务端→客户端 | `session.event`、`session.status`、`subagent.started`、`subagent.finished` | 官方文档 |
| `prompt` 内容块 | 普通内容 + `SdkEncodedImageBlock { type: "image", data, mimeType }`；服务端入队前转成持久引用 | 官方文档 |
| `serverInfo.name` | 固定 `deepseek-harness-sdk-runtime`（协议稳定值） | 官方文档 |
| 无版本协商 | 握手只带 `serverInfo.version`（`0.0.1`），客户端不校验 | 官方文档 |
| 已知限制 | 无取消方法、无会话关闭方法（客户端放弃轮次 = 关进程）；server→client 请求未使用 | 官方文档 |
| 服务端插件 | `@deepseek-ai/dsh-sdk-jsonrpc-server`，应用组合包 `dsh --profile sdk` | 官方文档 |

**本项目用途**：仅 POC-11（端侧 Host 可行性）与「无 webserver 场景」备选。**不得**作为 v1 主载体——它缺少取消/会话关闭，且 stdio 载体在移动端反而更难（需进程内管道）。

### 8.2 ArkTS 心跳对策（关闭 A-2 的设计侧）

**新事实（ArkTS SDK，API 21+）**：`@ohos.net.webSocket` 的 `WebSocketRequestOptions` 提供
`pingInterval`（默认 30s，0 = 关闭）与 `pongTimeout`（默认 30s，须 ≤ `pingInterval`），
即**客户端可主动发起心跳**，但 SDK **不暴露** `pong()` 之类的控制帧 API。

**风险**：Host 每 2s 发 Ping 并「若下一周期前未收到 Pong 则主动终止」。若 ArkTS 客户端不自动回 Pong
（无法在 ArkTS 层验证），连接会在 ~4s 内被 Host 断开。

**服务端常量已实地确认（2026-09-10，读上游代码）**：
`@deepseek-ai/dsh-api-gateway` 的 `RemoteStreamMuxServer`：

```js
const MAX_MISSED_HEARTBEATS = 2;     // 连续漏 2 次 Pong 即终止
websocket.on("pong", () => { this.missedHeartbeats.set(websocket, 0); });
```

配合配置项 `websocketHeartbeatIntervalMs`（**默认 2000**），即：**Host 每 2 s Ping 一次，
连续 2 次未收到 Pong（约 4–6 s）就主动终止该连接**。
这条常量此前只有文档级描述，现在是代码级确证——它决定了「不做 Pong 也能长期存活」是不可能的。

**本项目对策**：不假设自动 Pong，改为**显式开启客户端双向心跳** `pingInterval=5000ms, pongTimeout=4000ms`。
链路上因此始终存在双向流量；即使对端把「有流量」视为保活，也不会在 2s 判定窗口内被判静默。
该决策已实现于 `connection/src/main/ets/protocol/RemoteMux.ets`。

**⚠️ 真机观测与上述 4–6 s 阈值不一致（未决）**：
设备侧实测的关闭**发生在第二条逻辑流打开后约 27 ms**（`control open ok` → 27 ms 后
`control error carrier/closed`），而同一次会话里的 HTTP 一元调用在紧接着的 31 ms 后仍然成功
（`list ok 4 条`）。27 ms 比 4–6 s 的心跳阈值快两个数量级，因此**心跳超时不足以解释它**；
更可能是所用转发通道（`hdc rport`）无法同时承载两条长连接。
但「ArkTS 是否自动回 Pong」这一项**仍未验证**——要单独验证它，需要一个不经转发通道、
只维持**一条** WebSocket 的对照实验（见 D4 POC-1 步骤⑤与「设备 ↔ Host 端到端验证」）。

> **对 §6.4（设备接入与安全设计）的直接支撑**：该实验证明「伪造 `Host` 头」这条路**必然 403**——
> 这正是社区方案需要打 patch 才能绕过的围栏。本项目的 L1/L2 走**隧道出口回 loopback**，
> 因此无需伪造任何头即可满足该围栏；反之，任何试图直接连 Host 对外地址的做法都会被 403 拒绝。

**由此确立的三条实现纪律**

1. **404 与业务失败必须分开处理**：404 意味着「该 endpoint 在本 Host 上不存在」⇒ 上层应做**能力探测与入口置灰**（D1 7.9.2），而不是当作网络错误重试。
2. **错误码前缀是分层信号**：`gateway/*` = 调用契约错误（我方 bug，不应重试）；其他前缀 = 域内业务结果（应呈现给用户）。`Connection.call` 的 `RemoteFailure.code` 因此必须原样保留。
3. **参数包装名必须逐端点查描述符**：`session/list` 用 **`_request`**（带下划线），其余多数用 `request`，还有多个是扁平具名参数（`refs` / `id` / `namespace` 等）。**禁止按方法名猜参数形状**——这是本项目 v1 枚举阶段踩到的真实错误（首版假设 `workspace/list` 存在，实测 404）。

#### 8.7.6 本次整合中发现并修正的**仓库自身缺陷**（不是上游变化）

这些不是上游改了什么，而是**我们自己的工具与解析层错了**。它们共同的特征是：
编译通过、运行时也不报错，只在特定调用路径上静默给出错误结论。

| # | 缺陷 | 症状 | 修正 | 为什么长期没被发现 |
|---|---|---|---|---|
| 1 | 端点上表的 `params` 存的是上游 **TypeScript 形参名**（`name`），不是**线上名**（`wire`） | **30 个端点**的参数名是错的：所有 Agent 作用域端点记成 `agent`（线上必须发 `agentId`），`workspaceFiles/*` 记成 `workspaceFileScope`（线上 `workspaceFileScopeId`） | `tools/gen-compat-endpoints.mjs` 与 `tools/compat-drift.mjs` 一律改用 `p.wire`（含 `shapeOf` 的包装名判定）；重新生成上表 | 仓库里**没有任何代码读上表的 `params`**（`buildArgs` 只按 `shape` 装配），所以错值从未被使用过——纯粹是「等着将来有人用」的陷阱 |
| 2 | `connection/Envelope.ets` 要求 `ok:true` 响应**必须**带 `value` 字段 | 上游 **4 个 `void` 端点**的成功响应是 `{ok:true}`（没有 `value` 键，`JSON.stringify` 丢弃 `undefined`），会被解析层判为「畸形响应」而失败。**其中包含审批与提问的答复通道 `$events/result`**——即「用户点了允许、客户端认为调用失败」 | 新增 `rpcOkVoid()`；解析时**先用键存在性判断**再取值（区分「没有 value 键」与「有 value 键但值为 null」） | 之前的实测只覆盖了有返回值的只读端点，而 `$events/result` 需要真实审批才能触发，设备未到位就一直没跑到 |
| 3 | `connection/RpcTypes.checkTarget()` 把 `/api` 当成「被 Gateway 保留、调用方不得使用」的 channel **拒绝**它 | 而 `Connection.call()` 正是用 `surface.apiChannel`（= `/api`）调它 → **每一次一元 RPC 全被守卫拦下**，返回 `carrier/parse`（伪装成网络问题）。会话列表 / 发送提示词 / 取消轮次 / **审批答复**全都是死的；只有认证（直连 `HttpClient`）与流（走 `RemoteMux`）是活的 | `checkTarget` 不再拒绝 `/api`（它就是 Gateway 服务的 channel，也是本客户端唯一使用的）；调用方错误单列 `client/endpoint-invalid`，**不再伪装成载体失败** | 认证与流都不经过该守卫，「能认证、能开流」造成了「连接正常」的错觉。单元测试里那条 `checkTarget(API_CHANNEL, 'session/list').ok === true` **一直在指着它**，但旁边一条自相矛盾的 `it('rejects the reserved /api channel')`（`API_CHANNEL` 就是 `/api`）把错误行为写成了预期——两条测试不可能同时通过，直到**把测试真正跑起来**才暴露 |

> 缺陷 2 的上游代码实证：网关对 `$events/result` 的成功分支直接写
> `return { ok: true, value: undefined };`（`dsh-api-gateway/lib/types/index.js`）。
> 这是**权威证据**，不是推断。

**一次被推翻的「推翻」（方法论教训，值得留档）**

升级过程中有一位复核者提出：先前记录的「`commands/execute` 的 `images` → `submittedAttachments`
是破坏性线上改名」属于**假阳性**。**该结论本身是错的**，错因比结论更值得记住：

- 它拿**已提交上表里的 `name`**（受缺陷 1 影响，存的是形参名）去比**契约里的 `wire`**——
  两个字段不对等；
- 而这个端点上 `name` 与 `wire` **恰好同名**，于是比对看起来是「两边都是新名」，
  实则只证明了「新版的 name 等于新版的 wire」。

两端 `wire` 直接比对的结果（证据）：

| 版本 | `commands/execute` 的 params（`wire<-name`） | kind | cancellable |
|---|---|---|---|
| `0.1.2-rc.1` | `[agentId<-agent, line<-line, images<-images]` | `direct` | `true` |
| `0.1.5-rc.1` | `[agentId<-agent, line<-line, submittedAttachments<-submittedAttachments]` | `direct` | `true` |

**结论：这是真实的线上改名**，先前的 `PARAM_ALIASES` 条目是对的，予以保留。

**教训**：跨来源比对必须先确认两边取的是**同一个字段**。否则会得到一个看起来很有说服力的
错误结论——**比没有结论更危险**，因为它会让人主动删掉正确的防护。

#### 8.7.7 会话事件类型的权威清单（关闭 §8.7.5 第 1 项，2026-09-11 复核修订）

> **采集方式（零风险、无需凭据）**：直接读 Host 落盘的会话日志并逐帧解码。
> 日志是**多帧拼接**的 zstd（`.dsh/sessions/<cwd>/<sessionId>/session.v3.jsonl.zstd`），
> 而 `zlib.zstdDecompressSync()` 与 `zlib.createZstdDecompress()` **都只解第一帧**
> （4.2 MB 的文件只得到 223 字符——那是文件头）。
> 正确做法：**扫描 zstd 魔数 `28 B5 2F FD` 逐帧解码再拼接**。
>
> 这一步把前置条件从「需要凭据 + 一次真实对话」降为「只需要磁盘上的既有日志」——
> 后者在任何用过的 Host 上都现成。
>
> **本次复核规模**：5 个 v3 日志、4876 帧、解压 3443 万字符、11013 条记录。
> 复核脚本已入库：`node .research/event-census.mjs <目录> --v3`（清单）
> 与 `node .research/event-sample.mjs <类型>`（内层结构取样）。

**数清单前必须先定口径。** 本次修订暴露了两条**会把清单数错**的陷阱，
都是「按 `type` 字段统计」这种看起来无害的写法导致的：

| 陷阱 | 后果 | 正确做法 |
|---|---|---|
| `assistant/message.data.stream[]` 里的**流式记录**也有 `type` 字段（`text-chunks` / `reasoning-chunks` / `tool-call-chunks` / `chunk`） | 清单被**虚增 4 种**（32 → 36），并且会去「为不存在的事件建形状」 | 只认顶层事件记录；流式记录属于 `assistant/message` 的内部结构 |
| 日志有**两种信封**：v3 裸记录 `{type,seq,time,data}` 与 `session/follow` 帧 `{type:'event',event:{…}}` | 只按 `event.type` 取值会得出「只有 1 种事件类型」的荒谬结论 | 两种信封都要识别（`rec.event ?? rec`，并用 `seq` 是否存在区分文件头） |

> **教训（值得单独记住）**：这两条都不是「少统计」，而是**多统计**与**统计错对象**。
> 多出来的类型看着很像真事件（名字就叫 `text-chunks`），于是会顺手为它们建形状表、
> 写下「实测存在流式事件族」的结论——**一个听起来很有道理的错误结论**。
> 凡是「按某个通用字段名遍历」的统计，都要先确认这个字段名在该层级**唯一**。

#### 8.7.9 `remote.mux` 上行帧的字段名是 `payload`，不是 `args`（2026-09-11 实测）

`.research/protocol/probe-mux.mjs` 用**手工完成 WebSocket 升级**的方式直连
`/api/remote.mux`（Node 内置 `WebSocket` 不能带自定义头，因此用 `http` 模块
自己做握手），把一个含糊的现场——「设备上流总是立刻断」——拆成了两层：

| 观察 | 结论 |
|---|---|
| 升级返回 **101**；10 秒窗口内服务端每 2 s 发一次 `ping`、连接**保持** | 握手与**载体本身没问题** |
| 上行 open 帧写成 `{type:'open',streamId,endpoint,args:{}}` → 立刻 `CLOSE code=1008 reason=invalid Remote stream request` | 上行帧的实参字段名**必须是 `payload`** |
| 改成 `payload:{}` 后连接稳定，但收到一帧 `gateway/arguments-invalid`：`forwarded Remote event stream requires an empty args object` | 服务端接受了帧；但 `$events` 要的是**一个空的 `args` 对象**，即 `payload:{args:{}}`（§8.7.11 补正） |

**两个极易写错的点**（都实测确认）：

1. 上行帧字段是 **`payload`**（`connection/RemoteMux.ets` 文件头记的是对的）。
   写成 `args` 会被服务端以 `1008 invalid Remote stream request` **立刻**关闭——
   这个现象与「心跳没回 Pong 被断开」**看起来一样**（都是快速断开），
   但原因完全不同：一个是**帧格式错**，一个是**心跳超时**。
   排查时必须靠服务端给出的 close code/reason 区分，不能凭「断得快」下结论。
2. **mux 的 open 帧与一元 RPC 的包装不同**：一元是
   `payload:{args:{…}}`，而 open 帧的 `payload` **仍然要装 `args`**
   （`$events` 要求 `payload:{args:{}}`）。完整的实测矩阵见 §8.7.11。

#### 8.7.11 `$events` 的实参是 `{args:{}}`；它确实投递事件；但设置/凭据写入不触发对应事件（2026-09-11 实测）

新增 `.research/protocol/probe-events.mjs`（观察 `$events` 投递，可选在窗口中途做一次外部写）
与 `.research/protocol/probe-event-delivery2.mjs`（建会话以**确定产生**事件）。
两个探测都用同一套手工 WebSocket 握手。

**三条实测结论**：

| # | 结论 | 证据 |
|---|---|---|
| 1 | `$events` 的 open 帧实参必须是 **`{args:{}}`**，不是 `{}` | 传 `{}` → `gateway/arguments-invalid`：「forwarded Remote event stream requires an empty args object」 |
| 2 | `$events` **确实投递事件**，且**不需要客户端先订阅** | 建一个会话即收到 `emit:api-session/added`（完整会话摘要，含 `projections.values`） |
| 3 | **Host 侧 RPC 写入不触发** `settings/document-updated` / `credentials/reference-updated` | 一次 `settings/mutate` 与一次 `credentials/set`+`unset` 之后，`$events` 在 14 秒窗口内**只收到 `ready`** |
| 4 | 但**直接编辑 Host 的设置文档确实会触发**它 | 在 `$settings.yaml` 里把 `fontSize: 14` 改成 `>15` 后立即收到 `emit:"settings/document-updated",args:["ui-theme",9]` |

> 第 3 与第 4 条合起来才是完整事实：该事件**只在文档被外部改动时发出**，
> 不随 Host 自身的 RPC 写发出。因此上一轮「本机无法验证自动刷新」的结论需要修正——
> **验证路径是存在的**，就是「在 Host 上直接改设置文档」。这也说明客户端接线是对的：
> 它订阅的正是这个事件、而事件确实会来。

> 第 1 条说明客户端**做对了**：`dshcompat/Surface.ets` 的
> `eventsPayloadJson: '{"args":{}}'` 就是正确形态，`EventStream.open()` 把它交给
> `RemoteMux.open()` 后装进帧的 `payload` 字段。这条同时解释了为什么
> 「开流看起来成功但收不到任何事件」——**实参错形态时服务端只回一帧 error，
> 而开流调用本身不报错**。

> 第 3 条是**上游行为**，不是客户端缺陷：上游 `API_REMOTE_FORWARDED_EVENTS`
> 里确实声明了 `{ event: 'settings/document-updated', mode: 'emit' }`
> （`packages/api/remotes/src/remote-events.ts`），但在这台 Host 上用直接 RPC
> 改设置**没有**产生该事件；而第 4 条证明**外部改文档会**产生。
>
> **因此**：本客户端的「外部改动自动刷新」**验证路径是「在 Host 上直接改设置文档」**，
> 而不是「用另一个客户端发 RPC」。上一轮把「RPC 写入不触发」误当成
> 「该 Host 不产生该事件」并据此判定「本机无法验证」——**那个判定是错的**。
>
> ⚠️ **仍未完成**：按第 4 条的路径做**端到端**验证（改文档 → 观察 App 界面自动更新）
> 本轮试了一次但**未观察到界面变化**，且尚未取到 App 侧「是否收到该 emit」的证据，
> 因此**不能**断言客户端接线已生效。下一轮应先在 App 诊断页确认 trace 里出现
> `emit settings/document-updated`，再判界面是否刷新——把「事件到没到」与
> 「到了之后刷没刷」分开看。

**方法论收获**：排查「接了事件但界面没变」时，必须把三件事分开验证——
**帧形态对不对**、**流会不会投递**、**上游会不会产生该事件**。
只验其中一项都会得出错误结论：本次先后误判过「客户端帧形态错」与
「转发通道不可靠」，而真因分别是「我自己的探测脚本帧形态错」与
「该 Host 不产生这个特定事件」。

#### 8.7.13 「socket 静默失效」是这台设备上真正的载体问题（2026-09-11 实测收敛）

把 §8.7.10–§8.7.12 的线索拼起来，得到一条**自洽且可复现**的机制：

| 观察 | 结论 |
|---|---|
| 探测侧：`error code=200` 在 73–216 ms 到达，**`close` 永不到来**（`closed=false`） | ArkTS 的 socket 失效时**可能不触发 `close`** |
| 探测侧：连接「存活」整个 8 s 窗口，但期间**只收到 0–1 个数据帧** | 「存活」是假象——载体其实**已经不可用**；先前把它读成「链路健康」是**误判** |
| 设备侧：`follow open` 后 55 ms 出现 `send 失败 code=-1`，紧接着 `control error carrier/closed` | 发帧失败是**已证实的事实**，而 `close` 没来 |
| 设备侧：`isOpen()` 一直为真（诊断显示「连接 live · 逻辑流 1」） | `state` 停在 OPEN，因为**没有任何事件把它推到 CLOSED** |

**机制**：socket 静默失效 → `close` 不来 → `state` 停在 `OPEN` → `isOpen()` 恒真 →
上层继续在死 socket 上开流 → `send` 失败 → 而又没有任何东西把 state 推到 CLOSED。
形成「**看起来已连接、实际什么都发不出去**」的死循环。

**已做的修正（本轮）**：`open()` 里 `socket.send()` 失败时升级为
`onSocketClosed('send 失败 …')`——把**已经证实**的「发不出去」变成连接失效，
于是重连控制器能介入。实测效果：错误文案从早先的
`stream error carrier/closed: ws error code=200 …`（含糊）
变为 `stream error carrier/closed: send 失败 code=-1`（**指向真实原因**），
且失败后连接能走到重连流程，而不是永远卡在 OPEN。

**刻意没做的事**：一见 `error` 就主动 `close()`。曾经想这么做，但实测反对——
同一个手工客户端在 `error` 之后**仍能正常工作**（收到了 `ready`、
后续还收到 `api-session/added`）。一见 error 就关会把**能用的连接**反复掐断，
制造重连抖动。收尾必须放在「确实发不出去」这个**被证实的**时刻。

**仍未解决**：`close` 不来的情况下，**没有心跳级探活**。
本轮只做到「发帧失败即判失效」——也就是说：**如果应用一直没有写操作，
它不会察觉连接已经死了**（只读浏览时表现为「数据不更新」而非「掉线」）。
彻底的修法是加一道**连接级**的探活（例如周期性发一帧或核对最近一次收帧时刻），
判据必须是**连接级**的，不能是「某条流有没有推数据」
（那个教训见 §8.7.10 的中间修法）。已记入 D4。

#### 8.7.14 连接级探活 + 「底层判死必须上报」（2026-09-11 实施）

按 §8.7.13 的结论做了两步，实测到位：

**① 连接级探活（`RemoteMux.startLivenessProbe`）**
每 `PROBE_INTERVAL_MS = 6000` 发一个上游必然应答的最小帧
（`surface.probeEndpoint`，取值 `settings/describe`——无副作用、参数可重复），
等**任何**回帧：

- 收到任何帧 → 链路双向可用，探活成功；
- `PROBE_TIMEOUT_MS = 8000` 内无回帧 → 判静默失效，`onSocketClosed()` 收尾。

> **2026-09-30 补：上面两行是 09-11 的原值，参数此后已放宽**（保留原值作历史）。
> 现值为 `PROBE_TIMEOUT_MS = 20000` + **新增** `PROBE_FAIL_THRESHOLD = 3`
> （**连续** 3 次无回帧才判死；收到**任何**帧即清零）。动因：高负载下单次超时
> 误杀健康连接。改后读数见 `docs/device-validation.md:4911-4924`。
> ⚠️ **但这组参数不是用户所见"跑任务时一直显示正在连接"的根因** —— 该现象的
> 根因在 WebView 侧（见 `docs/device-validation.md` 批次三十七）；`RemoteMux`
> 这组改动本身是"高负载下探活容错"的合理加固，保留，**但不可当成该现象的因**。

**为什么判据是「主动发的探针」而不是「有没有收到数据帧」**：服务端每 2 s 发的是
**WebSocket 协议级 Ping 控制帧**，它**不会**作为 `message` 事件交给应用，
所以静默期「最近收到数据帧的时刻」恒为很旧——用它判死会把**空闲但健康**的连接
全部误杀。这正是 §8.7.10 那版中间修法翻车的原因。
`probeEndpoint` 由兼容面注入而不是在 connection 里写死：它是**上游端点名**，
属于 `dshcompat` 的事实（D5 §1）。

**② `onSocketDead` 通知链（这是本轮真正缺的一环）**
实测发现：`RemoteMux` 把 `state` 置为 `CLOSED` 之后，**`Connection` 无从得知**——
后者只在需要时调 `isOpen()`，而诊断页读的是 `Connection` 自己的状态。
于是出现「底层已判死、界面仍显示 `连接 live`」。新增
`RemoteMux.setOnSocketDead()`，由 `Connection.handleMuxDead()` 接管：
记原因 → 把事件流 `markLost()` → `setState(CONNECTING, …)`。

> 用 `CONNECTING` 而非 `DISCONNECTED`：后者的语义是
> 「重试耗尽或凭证失效，需人工干预」，而这里**重连即将开始**，
> 用它会误导用户去手工处理一个正在自动恢复的问题。

**实测效果**：诊断横幅从**假的**「连接 live」变为**如实的**「连接 degraded」，
且不再卡在 `OPEN`。这正是本轮要修的东西——**状态必须反映事实**。

#### 8.7.15 恢复链的两处缺口：不驱动重连、不订阅状态（2026-09-11 定位并修复）

§8.7.14 让「底层判死」能被 `Connection` 知道，但实测发现**恢复仍然没发生**，
横幅也仍显示 `live`。逐条查下去是两个独立的缺口：

**缺口 1：`handleMuxDead` 只改状态、不驱动重连。**
`scheduleReconnect(sink)` 只被 `start()` 与事件流 `onEnd` 调用过——
**连接失效之后没有任何人再次进入重连循环**。修法：`start()` 时记下 `sink`
（`startSink`），`handleMuxDead` 用它重新进入循环。策略仍集中在
`ReconnectController`，这里**不自己实现退避**（否则会出现两条重连路径互相打架）。

**缺口 2：`SessionHub` 从不订阅连接状态。**
它过去**只**通过事件流 `onEnd` 感知失败，所以底层的降级对本层不可见——
于是出现了最坏的那种组合：**底层已经判死、界面还显示「连接 live」**。
修法：`connect()` 里 `conn.onStateChange(...)`，把载体事实映射到中枢阶段。

> **映射而不是照抄**：底层 `CONNECTING` 在中枢对应的是**降级**
> （数据还在、只是可能不新），而不是「正在首次连接」。
> 直接抄枚举会让界面把「重连中」显示成「首次连接中」，
> 误导用户以为自己从没连上过。

**设备实测的恢复链（trace 原文，逐行可核）**：

```
connection degraded: 第 1 次重试将在 264ms 后进行（档位 500ms）
connection disconnected: 重试已耗尽：探活发送失败 code=-1
events end 重试已耗尽：探活发送失败 code=-1
```

横幅显示 **`连接 degraded`**——不再是与事实相反的 `live`。

**剩下的阻塞在传输通道本身**：这台设备上 `hdc rport` 的转发会在数秒后失效，
而**重试也走同一条已死的转发**，所以重试必然全败。
因此「失效→恢复」的全流程**无法在 rport 上验证**，
需要在可靠通道上做（hostkit 隧道或真机直连）——
这同时也印证了 D1 §6.5 把 hostkit 定为跨设备验收通道的选择。

承接 §8.7.9 的两个候选。在**设备内部**新增一条探测用例
（`entry/src/ohosTest/ets/test/MuxProbe.test.ets`，连 `ws://127.0.0.1:3116/api/remote.mux`），
得到的结果**推翻了「载体被转发通道掐断」这个假设**：

| 观察（设备内部，8 s 窗口，两种配置各测一次） | 数值 |
|---|---|
| 升级成功 | `connected=true` |
| 窗口内是否收到 `close` 事件 | **`closed=false`（从未收到）** |
| `error` 事件到达时间 | **73–198 ms** |
| `error` 内容 | `code=200 message=undefined` |
| 连接是否存活整个观察窗口 | **是**（`closedAt=-1ms`） |
| 有无客户端心跳配置的差异 | **无**（`pingInterval=5000/pongTimeout=4000` 与不带心跳表现一致） |

**结论**：ArkTS 的 `WebSocket` 会在**链路健康**的情况下抛出
`code=200 message=undefined` 的 `error` 事件，而且**不伴随 `close` 事件**。
连接本身是好的——`hdc rport` 转发与 ArkTS 实现**都不是**问题。

**真正的缺陷在客户端**：`RemoteMux` 旧实现在 `socket.on('error')` 里直接
`onSocketClosed()`，于是：
- 全部逻辑流被以 `carrier/closed` 终止（症状正是「open 后 ~27 ms 就 closed」）；
- 上层看到「连接失效」，而物理链路其实是好的；
- 错误文案把排查方向指向「载体断了」——**一个错误的方向**，本项目的文档里
  因此长期记着「转发通道不可靠」这个错结论。

**修法（最终版）**：**不再围绕 `error` 事件做任何判定**。
`error` 只记入 `lastError` 供诊断页展示；判死只认 WebSocket 层的 `close` 事件
（权威信号）加上库自身的心跳（服务端每 2 s 发 Ping，未在 `pongTimeout` 内回 Pong
时库会关闭并触发 `close`）。

> **中间那版「活性宽限期」也是错的（值得留档）**
> 第一版修法是：`error` 后给 6 s 宽限期，宽限期内没有**数据帧**就判死。
> 它修好了 `$events`，却引入一个更隐蔽的误杀——宽限期计时器是**连接级**的
> （一个 mux 一个），而 `session/control` 在空闲时**根本不推数据帧**。
> 于是「`$events` 的 error 启动了计时器 → `control` 在计时器到点时被一起杀掉」，
> 杀掉的是一条**完全健康**的流。实测症状：启动后 3–6 秒必现
> `control error carrier/closed`。
>
> **教训：别把「数据帧静默」当判据。** 有些流本来就是静默的；
> 判死要么用连接级的权威信号（`close`），要么用连接级的存活探测（Ping/Pong），
> 不能用「这条流最近有没有推数据」。

**修复效果（设备实测）**：启动后 30 秒以上的观察窗口内
**不再出现** `control error carrier/closed`，也**不再出现**
`events end 重试已耗尽`；会话列表顶部不再出现错误横幅
（修复前 3–6 秒内必现）。

**顺带记录两条方法论**：
1. **`error` 事件 ≠ 连接已断**。判死要依赖一个真正的 `close` 事件，
   或者连接级的存活探测（Ping/Pong）；把 `error` 当死亡通知会制造出与真实链路状态
   相反的错误结论。
2. **`code=200` 在这种场景下不代表 HTTP 200**（那是 WebSocket 库自己的错误码空间）。
   先前把它读成「服务端返回 200」是误读。

**尚未单独验证**：审批/提问推送与设置页外部改动自动刷新在修复后的实际表现
（本轮只验证了「流不再被误杀」）。`session/control` 的误杀已由本轮修法消除，
因此这两项应当恢复可用，但需下一轮用真实动作复测。

#### 8.7.16 `workspaceFiles/list` 的根目录必须传 `"."`（空串被拒）；Host 版本号协议里读不到（2026-09-11 实测）

**事实 1：`path` 标必填还不够，「根怎么写」是另一件事。**

`docs/11-请求载荷契约.md` §2.1 记的是「`args = { workspaceFileScopeId, path }`（两者都必填）」
与「回复里 `path` 是**工作区相对路径**；工作区根为空串」。
把这两条合起来，最自然的做法是**请求也传空串**——实测这是错的：

```
POST /api/workspaceFiles/list  { workspaceFileScopeId: <sess>, path: "" }
→ 200 {"ok":false,"error":{"code":"gateway/bad-request","message":"path is required"}}

POST /api/workspaceFiles/list  { workspaceFileScopeId: <sess>, path: "." }
→ 200 {"ok":true,"value":{"path":"","entries":[{"name":".git","type":"directory"},
     {"name":"docs","type":"directory"},…],"truncated":false}}
```

要点四条：
1. **请求词法与回复词法不是一回事**：请求根写 `"."`，回复的 `path` 仍是 `""`。
2. 这个错误**不会表现为错误**。客户端把失败当成空目录时，用户看到的是
   「该目录暂无文件」——一个完全合理的界面状态，与真相（目录里有一整个仓库）相反。
   这就是本项目反复记录的那类缺陷：**没有报错，但有错**。
3. 子目录直接传工作区相对路径即可（`path: "docs"` 正常返回 8 个条目）。
4. 因此客户端把「请求路径」与「子节点路径前缀」拆成两个参数
   （`listDirectory(requestPath, parentPath, scope)`），并在
   `appstate/model/Wire.ets` 里导出 `WORKSPACE_ROOT_REQUEST_PATH = '.'`，
   由单测钉住（`LiveWire.test.ets`）。
   `workspaceFiles/read` 不需要这个区分：它传的是**文件**路径，没有「根」这种调用形态。

**事实 2：Host 核心包版本在协议面上**不存在**。**

`$events` 的 ready 帧实测只有 `{type:'ready', clientId, host:{home}}`（§8.7.12，本轮复核一致），
没有任何版本字段。因此：
- 设备页的「核心包版本」只能显示**未知**，不能拿「受支持版本矩阵」冒充 Host 的版本；
- 诊断页的版本判定只能得到 `unverified`（`checkVersion('', …)`），
  并必须把原因写进文案（「未能读取 Host 版本号」），而不是显示一个假的三态结论。

> **一个已经发生过的界面缺陷**：诊断页曾把 `supportedVersionsText()`
> （字符串 `"0.1.5-rc.1 / 0.1.2-rc.1"`）塞进 `versionVerdict`。而视图是按
> `supported|unverified|incompatible` 三态分支渲染的，于是**三个分支全部落空**——
> 该区域既没有图标也没有文案。它看起来只是「这里没内容」，
> 比显示一个错误结论更难被发现。

**结论（给客户端的动作）**：文件端点的作用域是会话级，而会话是**唯一**能提供
`workspaceRoot` 的东西。因此「工作区」页必须先选定一个 cwd 属于该目录的会话，
才能列目录；客户端把「文件浏览作用域」与「当前查看的会话」**解耦**
（`SessionHub.openWorkspace`），因为它俩本来就可以不同。

#### 8.7.17 附件链路实测：`fileUploads/upload` 的线上名是 `agentId`；`readAll` 给的就是可上传的 base64（2026-09-11 实测）

`.research/protocol/probe-upload.mjs` 对真实 Host 发了三次调用，逐字结果如下。

**① 正确形态（接受）**
```
fileUploads/upload { agentId: <sessionId>, request: { data: <base64>, name: "probe-readme.txt" } }
→ {"ok":true,"value":{"receiptId":"c4cb0e3b-…",
     "file":{"attachmentId":"sha256:4e3e5b3d…","name":"probe-readme.txt","bytes":48}}}
```
两点可直接依赖：`receiptId` 是回执；`file.attachmentId` 是 **`sha256:` 前缀的内容寻址 id**
（与 D2b §6.2 的说明一致，不是路径、不是带授权的 URL）。

**② 故意写错参数名（拒绝）——这条是负向证据，比正向证据更有力**
```
fileUploads/upload { agent: <sessionId>, request: {...} }
→ {"ok":false,"error":{"code":"gateway/arguments-invalid",
     "message":"typert gateway: fileUploads/upload: args fields do not match the descriptor:
                missing \"agentId\"; unexpected \"agent\"","details":{"endpoint":"fileUploads/upload"}}}
```

**③ 缺 `request`（拒绝）**
```
fileUploads/upload { agentId: <sessionId> }
→ gateway/arguments-invalid: missing "request"
```

**这直接证实了客户端的一处真实缺陷**：`Wire.ets` 的 `fileUploadPayload()` 曾按上游
`.d.ts` 的**形参名**把线上参数写成 `agent`。而生成上表里该端点的 `params` 是
`['agentId','request']`。这个端点在客户端里此前**从未被真正调用过**（附件功能一直
是「界面有按钮、链路没接」），所以错误一直没暴露——一接上就会以
`arguments-invalid` 出现，而错误信息里那句 `unexpected "agent"` 正是它。

> **与 `commands/execute` 那条的区别（重要）**：`images → submittedAttachments` 是
> **上游改名**，因此归 `PARAM_ALIASES` 管（按错误码换旧名重试一次）。
> 本条是**我们自己写错了**（上游一直叫 `agentId`），不属于改名，
> 因此**不能**放进别名表——那会把一个客户端 bug 伪装成上游漂移，
> 并且永远掩盖真正的改名事件。

**④ `workspaceFiles/readAll` 给的就是附件需要的字节**
```
workspaceFiles/readAll { workspaceFileScopeId: <sessionId>, path: "README.md" }
→ {"ok":true,"value":{"absolutePath":"D:\\…\\README.md","version":"…","bytes":19021,
     "offset":0,"data":"<25364 字符 base64>","eof":true}}
```
`data` 可直接作为 `fileUploads/upload.request.data`。因此「投喂 Host 侧文件」这条
功能**不需要任何新端点**：读整文件字节 → 上传拿回执 → 放进
`session/prompt.request.content[].type='file'`。
注意 `bytes = 19021` 与 `data.length = 25364` 的关系正是 base64 的 4/3 膨胀
（19021 × 4/3 ≈ 25361），可作为「data 是完整文件」的旁证。

**⑤ 收据的生命周期（客户端必须遵守的两条）**
- 收据是**会话（Agent）作用域**的 ⇒ 切会话必须清空本地待发附件；
- 收据在**成功进入某个 prompt 的收件箱后即被 Host 回收** ⇒ 发送成功后必须清空本地列表，
  否则再次发送会被判为未知回执，而用户以为附件还在。

#### 8.7.19 长连接必断的根因是**心跳**（不是转发通道）；`session/page` 的参数是 `{address, throughSeq}`（2026-09-11 实测收敛）

**一、根因（并推翻 §8.7.15 的归因）。**

`.research/protocol/probe-probe-harm.mjs` 对真实 Host 做了一组对照，唯一变量是
「客户端回不回 WebSocket Pong」：

| 客户端行为 | 结果 |
|---|---|
| 回 Pong | 15 s 观察窗内连接**保持** |
| 不回 Pong | 服务端在 **5.4 s** 主动 `CLOSE` |

而设备侧把地址换成**完全不经 hdc 转发**的 `10.0.2.2:3115` 后，症状一模一样：
约 5–6 s 后 `control error carrier/closed`，下一次 `send()` 以 `code=-1` 失败；
设备日志里两次成功的一元调用之间正好隔着 **5.3 s**（`14:11:07.000` → `14:11:12.316`）。

结论：**服务端心跳是硬要求**（每 2 s Ping，漏两次即 terminate），
而设备侧 ArkTS 的 `WebSocket` 不回 Pong（HarmonyOS 官方 FAQ 只承诺
"服务器要对**客户端**的 Ping 回 Pong，否则客户端 30 s 断开"，对反向要求只字未提）。

因此 **§8.7.15 把责任归给 `hdc rport` 的结论作废**：那条结论是在同一条可疑通道上得出的
（§8.7.13 的教训"别把数据帧静默当判据"是对的，但"转发通道是元凶"是错的）。
判别方法很简单——换一条不经转发的通道复现；**这次换了，症状不变，所以归因必须改**。

**二、客户端因此做出的两个改动（都不改上游）。**

1. **重连不再进入终态。** 档位表（6 档，末档 10 s）用尽后旧行为是置 `DISCONNECTED`
   并停止——在"5 秒必断"的环境里等于**应用永久不可用**。现在档位用尽时
   `reconnector.reset()` 再按固定 2 s 继续重连，并**保持 DEGRADED**（事实就是"降级但仍可用"，
   报成终态是在说谎）。每次重连都用 `session/follow` 的 **snapshot** 把整段历史重新同步回来，
   因此会话仍可读可发，只是可见延迟约等于重连周期。
   > 坑：第一版只 `setTimeout` 重新 `schedule` 而未 `reset()`，计数器只增不减，
   > 控制器便一遍遍回调 `onExhausted` 而**永不真正发起连接**——trace 停在一条日志上不动。

2. **不设客户端心跳选项**（去掉 `pingInterval/pongTimeout`）：它们不是解药
   （关连接的是服务端），保留只会让"谁关的"更难分辨。

**三、`session/page` 的请求体是 `{address, throughSeq}`，不是 `{sessionId}`。**

```
{ request: { sessionId } }
  → gateway/input-invalid: wire field "request" failed boundary validation
{ request: { address: {kind:'session',sessionId}, throughSeq: -1 } }
  → {ok:true, value:{records:[…], hasMore:false}}
```

两处值得记：
- `throughSeq` **必填**，`-1` 表示"到当前末尾"；
- 少字段的错误码是 `gateway/input-invalid`，读起来像"格式问题"，
  很容易被误当成"这个会话没有记录"。**两者必须分清**：前者是我们的 bug，后者是事实。

**四、「本项目自己起核心」的工作流（`tools/dev-host.mjs`）。**

一条命令：起 dsh 核心 → 抓它自己打印的令牌 → 建 `hdc rport` → 冷启动应用并用
`--ps dshHost/--ps dshToken` 带入地址与令牌（**界面零手填**）。三条纪律：

| 决定 | 理由 |
|---|---|
| 默认用**用户自己的** `~/.dsh`（`--isolated` 才用空目录） | 模型凭据/provider 都在里面；空目录下 `session/prompt` 返回 `{accepted:true}` 但 Agent **永不产出回复**——投递成功、无报错、没有回答，是最有欺骗性的一种失败（实测空 home 下 `session/page` 90 秒内始终 0 条记录） |
| 只绑 `127.0.0.1`，把客户端实际请求的权威用 `--trusted-host` **显式**加进信任栅栏 | 不绑 `0.0.0.0`（D1 §6.4 红线）；不伪造 `Host`/`Origin` |
| 启动应用前先 `aa force-stop` | 启动参数只在**冷启动**被完整消费；应用还活着时 `aa start` 走 `onNewWant`，而页面的自动连接有"只跑一次"守卫——实测症状是"换了地址，界面还连着上一个 Host" |

**五、仍未解决：`{accepted:true}` ≠ 消息已进入收件箱。**

在**用户自己的 `~/.dsh`**（模型目录正常：`default = deepseek-official/deepseek-flash`）
上重复验证：

```
session/prompt  {request:{requestId:<新铸>,sessionId, mode:'queue', content:[{type:'text',…}]}}
  → {ok:true, value:{accepted:true}}
session/page    {request:{address:{kind:'session',sessionId}, throughSeq:-1}}
  → {ok:true, value:{records:[], hasMore:false}}        （90 秒内始终为空）
session/list    → 该会话 projections.values.inbox = {"next-turn":[],"next-step":[]}
```

即 **`accepted:true` 与"消息真的进了 Agent 收件箱"是两件事**——收件箱投影是空的。
（另注：D2b §1.2 记过 `requestId` 的幂等语义——**同一 id 重复提交也返回 `{accepted:true}`**，
因此这个回复无论如何都不能当作"落地成功"的证据。这一条现在有了第二个理由。）

工作假设（未证）：Agent 循环需要**有客户端在 `session/follow` 上订阅**该会话才会跑；
一元投递只是放进收件箱。但本轮里应用确实打开过该会话，仍未产出记录，
所以还需要排除"凭据缺失/Provider 不可路由"这一类**静默失败**。

**下一个最小实验**（按顺序，每步都能单独定案）：
1. 用 `.research/protocol/probe-follow.mjs` 开一条**稳定**的 `session/follow`（不经设备、不经转发），
   再发 prompt，观察是否出现 `user/message`：能区分"需要订阅"与"投递本身没落地"；
2. 若仍无记录，直接看核心进程的 stdout（`tools/dev-host.mjs` 已把它的输出接到终端）——
   模型调用失败会在那里留痕，而**一元回复里不会有任何提示**；
3. 用 `dsh` 自己的 CLI/网页端在同一个 `DSH_HOME` 上发一条 prompt 作对照：
   若 CLI 能跑通而 HTTP 不能，则问题在 API 层；若都跑不通，则问题在凭据/Provider。

#### 8.7.20 结论：**任务能跑通**（真正的回复已产出）；缺的是凭据，不是链路（2026-09-11 定案）

上一节列的三种可能，实测全部收敛，结论如下。

**① Agent 不需要客户端订阅也会跑完整轮。**
`.research/protocol/probe-follow-prompt.mjs --late-follow 12`：**先发 prompt、完全不订阅**，
12 秒后再开 `session/follow`，快照里读到了完整的一轮：

```
snapshot records=19
permission/preset, sandbox/mode, approval/policy, agent/inbox/spliced,
turn/start, agent/inbox/spliced, step/start, system/message,
user/message ×3, request/header, request/context,
session/title, session/title-llm-request, assistant/message, step/end, turn/end
```

⇒ **这个平台限制（长连接约 5 秒必断）不会丢任务**：Host 侧照旧把这一轮算完并落盘，
客户端只要在下一次重连时用 follow 的**快照**重新同步就能看到答案。
可见延迟 ≈ 重连周期，而不是"永远看不到"。

**② 之前"什么都没发生"的真正原因是缺模型凭据。**
第一次带订阅的实验里，`turn/end` 的 reason 直接写着：

```
llm-deepseek: no API key for provider route "deepseek-official";
store DEEPSEEK_API_KEY through the credentials service
(the web Models page writes it), or export DEEPSEEK_API_KEY
```

补上密钥后同一个实验产出真实回复：
`assistant/message {role:'assistant', content:[{type:'text',text:'DSHM-OK'}],
source:{kind:'model',provider:'deepseek-official',model:'deepseek-flash'}}`，整轮 6.2 秒。
⇒ **「能执行任务」成立**，它需要两样东西：**凭据** + 一次 `session/prompt`（一元）。

> **`tools/dev-host.mjs` 现在会自动注入密钥**：先看 `process.env`，再看 Windows 注册表
> （用户级→机器级）。后者是必需的——实测机器级变量存在于注册表，
> 而**当前 shell 进程的环境块里没有**（变量是在 shell 启动之后设置的）。
> 值只在内存里传递，不打印、不落盘；打印的只有"已注入/未找到"。

**③ `session/page` 在这台 Host 上对**实时**记录恒返回空——不要用它轮询。**
三轮实验（含 19 条记录的那一轮）里 `session/page` 都是
`{ok:true, value:{records:[], hasMore:false}}`，而同一时刻 follow 快照里有 19 条。
⇒ 它读的不是同一条通路（或需要别的游标）。**对客户端的直接结论：读会话内容只信
`session/follow` 的快照与增量，不要用 `session/page` 轮询**——它的"空"会把
"这一轮失败了"和"还没有记录"混成同一个读数，正是本轮两次误判的来源。

**④ 客户端侧一个真实缺陷（已修）：载体恢复后不重开 `session/follow`。**
`SessionHub.handleConnectionState` 在 `CONNECTED` 时原本直接 `return`，
于是**一次断线之后轨迹永远停在断开那一刻**——用户看到的是"发出去了、永远不回"，
而 Host 其实早算完了（见①）。在"5 秒必断"的设备上，这条缺陷会让应用**看起来完全不能执行任务**。
修法：`CONNECTED` 时刷新会话列表，并重开当前会话的 follow（`selectSession` 的守卫放宽为
"同会话但流已断 ⇒ 重开"；同时把"清空附件/排队项"限定为**真的换了会话**时才做，
否则重连会把用户刚加好的附件悄悄丢掉）。

**⑤ 仍未收口的一环**：设备上 follow 开流后 ~40ms 内报 `follow error carrier/transport`
（旁路日志原文：`14:43:31.307 follow open` → `14:43:31.344 follow error carrier/transport`），
即它撞在载体的死亡窗口上。加上④的重开逻辑后它会不断重试；但"快照能及时落地并渲染"
还需要在下一次设备验证里确认（本轮只验证到"会重开、会重试"）。

#### 8.7.21 自动重连曾是**静默失效**的：两条创建路径里只有一条注册了失效回调（2026-09-11 定位并修复）

**现象。** 设备上首次静默掉线后，旁路日志**两分半钟一条记录都没有**，界面永远停在 `degraded`；
而同一个界面上的「手动重连」按钮**一点就恢复**（`连接 live` + `pluginInventory ok` /
`settings/describe ok` / `credentials ok`）。也就是说：链路是好的、重连逻辑是有的，
但**自动那条路径没有把任何东西跑起来**。

**两个独立的缺陷，都会造成"连上过一次，之后再也回不来"。**

**缺陷 1：事件流绑在**旧的** mux 上。**
`EventStream` 在构造时把 `RemoteMux` **实例**存了下来；重连会 `this.mux = undefined`
并创建新实例，而 `Connection` 复用同一个 `EventStream` ⇒ `open()` 第一句
`this.mux.isOpen()` 恒为假（旧 mux 已 CLOSED）⇒ 重连循环的表现是
「TCP 连上了、却永远开不了事件流」：`ready` 永不送达 → `CONNECTED` 永不发布 →
`SessionHub` 永远等不到"载体恢复" → 轨迹流永不重开。
**修法**：抽出 `bindEventStream(sink)`，在 `start()` 与**每次重连**里都重建（绑定当前 mux）。

**缺陷 2：重建出来的 mux **没有**失效回调。**
创建 mux 有两条路径：`connectOnce()` 与 `getMux()`；而
`mux.setOnSocketDead(...)` 的注册只写在 `connectOnce()` 的
`if (this.mux === undefined)` 分支里。重连路径是「先 `bindEventStream()`（内部 `getMux()`
建 mux）→ 再 `connectOnce()`」，于是 `connectOnce()` 看到 mux 已存在就**跳过了注册**：
新 mux 静默死亡时**无人知晓**，应用从此冻结。
**修法**：把注册移到**唯一的创建点** `getMux()`。

> **教训（两条一般化的）**
> 1. **"创建点不止一个"是这类缺陷的温床**：任何"必须对每个实例做一次"的初始化
>    （注册回调、加监听、打标记）都应该放在**唯一构造点**里，而不是放在某个
>    "顺路创建"的分支里。缺陷 2 就是这么来的。
> 2. **实例 vs 句柄**：长生命周期对象（事件流）持有短生命周期对象（每条连接一个 mux）
>    **实例**时，重连必然留下悬空引用。要么每次重建，要么持有**取用函数**而不是实例。

**修复后的设备表现**：`connection degraded: 连接失效，正在重连：探活发送失败 code=-1`
——这一行本身证明失效回调**已经被注册并触发**（修复前它是看不见的）。
诊断页显示 **端点/认证/TLS 三项通过**，**协议未通过：`WebSocket 已建立；事件流 opening`**，
即当前卡在"载体能连上、`$events` 拿不到 `ready`"——
这与 §8.7.19-一的心跳限制（服务端每 2 s Ping、漏两次即关）相符，
属于**这台模拟器上的传输层现状**，不是客户端的协议实现问题。

#### 8.7.22 「这一轮跑完了」只能靠 `turn/end` 事件判定（2026-09-11 实测）

`session/follow` 的快照里**没有 `running`**（形状是 `header/cursor/records/hasMore/projections`，
D2 §8.7.2 行 9），`projections.values` 里也没有它。因此**唯一可靠的"轮次结束"信号是
`turn/end` 事件**；失败与否在 `data.reason.kind`：实测失败轮次是

```
turn/end {turn:1, reason:{kind:'error', error:{message:'llm-deepseek: no API key …'}}}
```

**这条事实此前没有被用上，代价是一个用户可见的缺陷**：中枢的 `running` 只在
「发送被接受」与「assistant-stream 帧」上置真、只在「取消」时置假，
因此**一轮正常跑完之后界面会一直显示"运行中"**（停止按钮再也变不回发送按钮）。
修法：在 `turn/end` 上置 `running = false`，并按 `reason.kind === 'error'` 决定
发"完成"还是"失败"通知。判据**只认 `'error'`**：其它取值（含将来新增的）一律按正常完成——
把一次正常完成误报成失败，会让用户白查一场。

> 一般化的教训：**"某个投影里没有这个字段"本身是一条事实，必须查证并记下来**。
> 这里真正的错误不是"没读到 running"，而是**默认了它在投影里**，
> 于是没有任何代码去处理"轮次结束"，而缺了它界面就会一直卡在运行态。

#### 8.7.23 `session/page` 能读整段历史，但**游标必须真实**；`-1` 不是"到末尾"（2026-09-11 实测）

背景：设备上 WebSocket 长连接约 5 秒必断、`$events` 常拿不到 `ready`（§8.7.19），
而**一元 HTTP 一直是好的**。若有一条纯一元的读法，应用在 WS 不可靠的链路上就仍可用
（会话能列、能发、**也能读**）。实测（`.research/protocol/probe-page.mjs`）：

| `throughSeq` | 结果 |
|---|---|
| `-1` | `{ok:true, records:[], hasMore:false}` —— **一条都没有** |
| `0` | 1 条（含 seq 0） |
| `1` | 2 条 |
| `5` | 6 条 |
| `100` | ❌ `gateway/bad-request: session page through seq 100 is past cursor 18` |
| `18`（= `session/list` 的 `projections.asOfSeq`） | **19 条**（整段历史，含 `assistant/message`） |
| `19` | ❌ `past cursor 18` |

三条可直接依赖的结论：

1. **`throughSeq` 是包含式上界**（`0` 就返回第 0 条），超过游标会**明确报错**——
   这是一个"会自己说出边界"的端点，错误消息里带着真实游标。
2. **`-1` 不是"到当前末尾"**。D2b 早先按上游类型注释记的"-1 表示到当前末尾"与实现不符；
   照它写的读法会得到一页空记录，而**空记录与"这个会话是空的"长得一模一样**。
3. **游标从 `session/list` 的 `projections.asOfSeq` 取**（实测它与上界完全一致：18 → 19 条）。
   于是纯一元客户端的读法是：`session/list` → 取该会话的 `asOfSeq` → `session/page{throughSeq:asOfSeq}`。

**`session/page` 的 `records` 与 `session/follow` 快照的 `records` 同形**
（都是 `{type:'event', event:{type,seq,time,data}}`），因此同一条 `projectWireRecord()`
可以直接复用——客户端因此有了一条**不依赖长连接**的通路
（`SessionHub.refreshTrajectoryByPage()`）：开流失败/流被终结时按 3 秒节奏读回历史，
流一旦开起来就让位。

> 教训：**上游类型注释里的"特殊取值语义"（这里是 `-1`）必须实测**。
> 它与字段名、参数形态一样会与实现不符，而且不像字段名那样会立刻报错——
> 它只会安静地返回空。

#### 8.7.24 对齐 `0.2.0-rc.2`：契约层**纯新增**（+2 / −0），但"静默失效"的成因比 §8.7.13 记的多（2026-09-29）

##### 一、契约漂移：`138 → 140`，两条都是新增，零改动

`0.2.0-rc.1 → 0.2.0-rc.2` 的端点表差集**只有两条**，且都在新命名空间 `userQuestions` 下：

|---|---|---|
| `userQuestions/answer` | direct，NAMED（参数按名字传，非位置） | **零调用** |

逐条判定：

- **不改任何调用代码**：`userQuestions` 这个字符串在**全仓命中 0**（`dshcompat/`、`appstate/`、
  `entry/`、`connection/`、`tools/` 全扫），因此新增端点对现有功能面**无影响**。

  （`dsh/cores/` 下 rc.1 与 rc.2 同时在场，用户数据零变化）。

> **这是连续第三次"契约层零意外"**（`0.1.5-rc.2`、`0.2.0-rc.1`、`0.2.0-rc.2` 都是纯新增）。
> 值得记下的不是"上游很稳"，而是**判据的成熟**：每次升级先做端点表差集、
> 再用差集里的名字去全仓搜调用点，两步就能把"要不要改代码"这个问题关掉。
> 详见 `docs/40-上游升级手册.md` §4.1（升级记录表）与 §4.4（逐条判定）。

##### 二、端侧特有流程事实：**构建不按配方版本挑核心 zip**

这一条与协议无关，但它是 **D5 升级手册在端侧会静默出错的地方**，记在此处因为它同时属于
"契约快照与实际安装核心不一致"这一类问题（与 §8.7 的 `compat-drift` 陷阱同族）。

- `entry/src/main/resources/resfile/` 下**只能有一个** `dsh-core-*.zip`；
- `entry/build-profile.json5` 的 `copyCodeResource` 直接拷 resfile 里**实际躺着什么**，
  **不读** `hostcore/core-recipe.json` 的 `coreVersion`；
- 全仓 `dsh-core-*.zip` 的消费者**只有一处**：
  `entry/src/ohosTest/ets/test/CoreDecision.test.ets:139` 的 `parseArchiveName`（纯测试解析，不影响构建）；
- ⇒ **配方版本与 resfile 里的 zip 不一致时，构建会静默嵌错版本、全程零报错**。

因此升级必须显式四步：**删旧 zip / 放新 zip / 核对 sha256 / 用 `BOOT_10_ENV_READY` 确证**。

##### 三、长期结论：「静默失效」是这台设备上**真正的载体问题**，且成因不止一处

§8.7.13 记过一条结论："socket 静默失效是这台设备上真正的载体问题"。
本轮（7 路对抗性审核，2026-09-29）**证实了这条判断，同时证明它的覆盖面太窄**。
同一形态（**不报错、界面看着正常、结果与意图相反**）在至少五个层面各出现一次：

| 层面 | 静默失效的形态 | 位置 |
|---|---|---|
| 构建打包 | 配方版本 ≠ resfile 里的 zip ⇒ 嵌错版本，零报错 | `entry/build-profile.json5`（`copyCodeResource`） |
| 契约快照 | 快照版本 ≠ 实际安装核心 ⇒ 新增端点被读成"上游已移除" | `tools/compat-drift.mjs:128-145`（版本判定优先读 env/快照） |
| 契约接线 | 端点名不存在于任何一版快照 ⇒ 常量恒走 `missing` 分支，UI 入口仍在 | `dshcompat/src/main/ets/Aliases.ets:185,187,219` |
| Host 偏离 | 拦截 `process.exit` 后只打两行 diag ⇒ 上游 fail-loud 通道消失 | `hostcore/app/main.js:108-128` |
| 插件卸载 | 队列读不到 `.dir` ⇒ 回落默认 profile，删了另一个 profile 下的东西 | `hostcore/app/main.js:1545-1595` |

**共同判据**：这五处**都不会让任何门禁变红**，也不会在日志里留下"我失败了"的字样。
它们只在"人按文档操作、然后发现结果和说的不一样"时才暴露。
⇒ **凡"版本/身份/归属"类的判据，都必须有一处交叉验证**（构建后读真机版本、
快照与安装核心分别打印、常量与快照逐条比对、卸载后核对目标 profile）。
