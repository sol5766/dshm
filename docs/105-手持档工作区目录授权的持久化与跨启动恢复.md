# 105 · 手持档工作区目录授权：**只活一次进程**，所以要持久化 + 跨启动恢复

> 2026-10-06（第八轮，真机 HUAWEI Mate 80 / `VYG-AL00` / OH 7.0.0.105 / API 26 / `deviceType=phone`）。
> 用户报障原话：**「侧边栏工作区文件下午修复手机端的时候可用了，被你改了不能用了」**、
> **「上一个版本已经可以看到工作区文件了啊，咋又改坏了」**。
> 本篇是 **`docs/103` 的更正版**：103 的现象读数是真的，但**根因判错了一半**（详见 §5）。

## 1. 一句话结论

手机 / 平板上，系统 picker 给本应用的目录授权是**进程级临时**的：
**选完当场宿主读得到、进程一重启就被拒**。所以要把它 `persistPermission()`（记下来）
**并且**在启动时 `activatePermission()`（启用回来）——本仓此前只做了第一步。
修完之后：选一次目录 → 重启 → 文件页照样列出、预览照常打开（§4 是逐条真机读数）。

## 3. 关键实验：**同一条路径，两个时刻**

这一段是本轮最重要的一次测量，它把"平台边界"这个错误结论排除掉了：

```
                        ┌─ 选完当场（同一进程内） ──→ workspaceFiles/list: 3 个文件   ✅
同一路径 …/Download/harness
                        └─ 进程重启之后 ──────────→ workspaceFiles/list: permission denied ❌
```

* **不是"宿主路径能力"的问题**：读写都发生在**同一个 uid、同一个进程**里的 `node:fs`
  与 `fileIo` —— 12:50 那次**宿主真的把 3 个文件写进 `harness` 成功了**
  （目录 mode 是 `drwxrws--x`，属主 `20001006 file_manager`，"other" 只有 `--x`，
  按裸 DAC 连写都不该成功 ⇒ 能写成只能说明**授权层在放行**）。
* **也不是"哪条通路"的问题**：`fileIo`（`file_access_service` 代理）与宿主（裸 syscall）
  用的是**同一份**授权，"当场能读 / 重启不能读"是同一件事的**两个时刻**。
* 平台侧的机制因此很清楚：picker 给的是**临时 URI 授权**（进程级），要跨进程活下来必须
  `persistPermission` + `activatePermission`。SDK 原文（`@ohos.fileshare.d.ts`）：
  `persistPermission` = "Set persistence permissions for the URI"、
  `activatePermission` = "**Enable the URI that have been permanently authorized**"；
  `ohos.permission.FILE_ACCESS_PERSIST` 的 `grantMode=system_grant`、`availableLevel=normal`
  （`sdk/default/openharmony/toolchains/lib/PermissionDefinitions.json` 原文）
  ⇒ 本包声明即得，**不需要 AGC/ACL**（与"权限零差异铁律"不冲突：这条本来就在 11 项里）。

## 4. 修法

### 4.1 新模块：`platform/src/main/ets/system/FolderGrants.ets`

| 函数 | 做什么 |
|---|---|
| `rememberFolderGrant(ctx, uri, path)` | ① 把 `{uri, path}` 记进 `preferences`（`dsh_folder_grants`，按 uri 去重、上限 16、新的在前）→ ② `persistPermission()` → ③ `checkPersistentPermission()` **查证**；返回 `{persisted, note}` |
| `restoreFolderGrants(ctx)` | 启动时对**每一条**登记逐个 `activatePermission()`（逐个调：一条失效不许拖垮其余），返回 `3/5 已启用（…）` 这样的汇总 |
| `storedGrants(ctx)` | 读名单（读不到/JSON 坏 ⇒ 空数组，不猜不抛） |

三条纪律写进代码注释：**每步都带看门狗**（`persistPermission` 有"永不 settle"前科 ⇒ 超时与失败分开记）、
**判据只看 `checkPersistentPermission`**（`persistPermission` 没抛错不等于成功）、
**每一步读数落 `diag-folder-grants`**（`ISO 时间戳 + 登记/持久/查证/启用 的 status`）。

### 4.2 采纳判据（`FilePicker.pickFolder` 与 `WebApp.doPick` 同步）

手持档（phone / tablet）**只接受两类**路径，其余回落到应用专属目录并如实提示：

1. 落在**本应用按包名归属**的公共目录内（`Download/<包名>/`；官方 FAQ `faqs-local-file-manager-67`
   口径：该 URI 自带持久权限 ⇒ 跨重启有效）；
2. 用户自己的目录 **且** 这一次的持久授权已确认生效（`checkPersistentPermission` 为真）。

⇒ 于是**用户选的真实目录被采纳**（16:19 那次 `diag-resolve-dispatched path=…/harness`，
没有再出现 `diag-picker-public-fallback`）——103 那版"静默改成应用目录"的行为随之取消；
只有**授权确实建不起来**时才回落，且提示文案把 `note`（例如 `persist=失败(13900001 …)`）带上，
用户看到的是原因而不是"读不出来"。

> **同轮清理（去重）**：103 那一版留下的旧判据块（`if (!probePathWritable(realPath)) { … }`，用 2in1 文案提前回落）
> 与本轮的新块**在 `pickFolder()` 里并存过一小段时间**：手持档路径只要探写失败，旧块就会先命中、用 PC 文案回落。
> 本轮把旧块删掉、只留新块 —— 非手持档仍走 `probePathWritable` ⇒ **PC 行为逐字不变**（只多一行 `hilog.warn` 的 `handheld=/granted=` 字段）。

### 4.3 启动恢复（`EntryAbility.onCreate`，仅手持档）

放在 `autoStartHostForDiagnosis()` **之前**：宿主还要 `probe → 解包核心 → spawn`（秒级到十秒级），
用户点开文件页时恢复早已到位。2in1 / PC 整段跳过（PC 上宿主本来就读得到 picker 目录，不需要）。

## 7. 未做 / 待决

* **既有坏登记**（本机那条 `session-9a4b9b57…`，cwd = `…/Download/harness`）：本轮**没有删**——
  它属用户数据；重选一次同目录即自动具备持久授权（§2 的 16:19→16:20 就是这条路径的实测）。
  更早的登记若指向**别**的目录，同样"重选一次"即可，不需要卸载/清数据。
* **未登记 URI 无法凭空激活**：`activatePermission` 只认"已持久化过"的 URI，而持久化必须有一次
  真实选择 ⇒ 老的坏登记不会自动复原（这是平台的语义，不是取舍）。
* **平板档**（`deviceType=tablet`）与手机同归手持、走同一判据，但没有单独的真机读数。
* 手机 / 平板的**终端**问题与本篇无关，仍是 `docs/104` 的结论（真 shell 无解、真命令有解）。
