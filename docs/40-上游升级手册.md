## 1. 设计前提：上游知识只允许出现在一个地方

```
                  ┌────────────────────────────────────────────┐
                  │  dshcompat（HAR）—— 唯一的上游事实落点        │
                  │   · Endpoints.ets   端点上表（自动生成，74 条）│
                  │   · Surface.ets     路径/端点/心跳等载体事实   │
                  │   · Aliases.ets     字段别名 + 常用 endpoint  │
                  │   · CompatIndex.ets 能力映射 + 版本矩阵 + 判定 │
                  └───────────────┬────────────────────────────┘
                                  │ 注入 ProtocolSurface / FIELD_ALIASES
                                  ▼
       connection（机制层）                      appstate（状态层）
       载体/信封/cookie/退避/诊断              投影/派生/呈现契约
       ——不含任何具体端点或字段名——            ——不认上游字段名——
                                  │
                                  ▼
                                 UI（entry）
                            ——只认呈现层契约——
```

**判定标准（评审时逐条检查）**：

- [ ] `connection/src` 中 grep 不到任何具体 endpoint 名字（`session/`、`settings/` 等）与具体字段名；
- [ ] `appstate/src` 中 grep 不到上游字段名字面量（除 `raw` 透传）；
- [ ] `entry/src` 中 grep 不到 endpoint 字面量与字段名；
- [ ] 新增上游依赖时，只改 `dshcompat`。

> 违反任一条即为**架构回归**，与功能 bug 同级处理。

## 2. 升级流程（五步）

### 步骤 0：确认当前状态

```sh
# 当前兼容面绑定的上游身份（受支持矩阵中的版本）
node tools/compat-drift.mjs
```

输出会打印「当前环境核心包 / 已提交基线核心包 / 端点数量」。若此时已报漂移，说明基线未同步，先处理存量差异再升级。

### 步骤 1：提取新上游的契约

```sh
# 指向新的上游安装位置（或多版本并存时用 DSH_NODE_MODULES 指定）
node tools/protocol-contract.mjs --json .research/protocol/contracts.json
```

产物包含每个 endpoint 的：`id`、`namespace`、`method`、`invocation.kind`、**是否流式**、`cancellable`、`parameters[].name`（参数 wire 名）、`result.typeSymbol`、`sourceLocation`。

> **两个已知陷阱**（都已在本工具里修掉，换个实现时容易重犯）：
> ① 流式标记**不在** descriptor 里，而在 `Remote({ mode: "stream" })` 装饰器中；
> ② 所有 descriptor 都集中装配在 `dsh-api-remotes`，**声明包要从 `id` 里取**（`<declPkg>#<ns>/<method>`），不能用文件所在包。

### 步骤 2：跑漂移门禁

```sh
node tools/compat-drift.mjs
```

- 退出码 **0** = 无漂移，可跳到步骤 4；
- 退出码 **1** = 有漂移，报告会按四类给出精确差异：
  - **上游新增端点**（可能是我们尚未接入的新能力 → 考虑加能力映射）；
  - **上游移除端点**（我们的调用会返回 HTTP 404 → 必须处理，见 §3）；
  - **契约变化**（参数形状 / 流式标记 / 参数名 / cancellable / id 变化 → 会导致调用失败）；
  - 报告末尾给出处置步骤清单。

> 门禁自身有**解析自检**：若生成物格式变化导致解析出的条目数与声明的 `endpointCount` 不一致，会直接报错退出，
> 而不是静默报告「无漂移」。这一点是必需的——本项目第一版门禁就因为正则过严而变成「永远说无漂移的假门」，
> 用注入式负测试才发现（见 §5）。

### 步骤 3：重新生成上表并处理差异

```sh
node tools/gen-compat-endpoints.mjs
```

改动点通常只有两处（都在 `dshcompat`）：

| 文件 | 何时改 |
|---|---|
| `dshcompat/src/main/ets/Endpoints.ets` | **由生成器改写**（勿手改）。若能力映射需要调整，改生成器里的 `CAPABILITIES` 常量后重跑 |
| `dshcompat/src/main/ets/Aliases.ets` | 上游**字段改名**时更新 `FIELD_ALIASES`（别名顺序 = 优先匹配顺序） |
| `dshcompat/src/main/ets/CompatIndex.ets` | `SUPPORTED_VERSIONS` 加入新版本；`PROTOCOL_SKELETON` 若骨架端点变化则同步 |
| `dshcompat/src/main/ets/Surface.ets` | 载体路径 / 事件流端点 / 开流 payload 变化时 |

### 步骤 4：分层判定影响面

| 差异类型 | 影响 | 端侧行为要求 |
|---|---|---|
| 新增端点 | 无（默认不调用） | 可选：接入新能力，走正常需求流程 |
| 移除端点 | 该能力不可用 | **必须**降级：入口置灰 + 说明原因（`evaluateCapability` 的 `missing`） |
| 参数形状变化 | 调用会失败 | 更新上表；**禁止**在调用点写兼容分支（形状只由上表决定） |
| 流式标记变化 | 载体用错，被拒（`gateway/signature-invalid`） | 更新上表；`buildArgs` 之外不得自行判断载体 |
| 状态码/错误码语义变化 | 错误呈现与重试策略受影响 | 更新 `CompatIndex` 的判定与 D2 §8.4 的错误码表 |
| 骨架端点缺失 | 不兼容 | `checkVersion` 直接给 `INCOMPATIBLE`，拒绝连接并说明 |

### 步骤 5：验证与回写

```sh
# 1) 静态：漂移门禁必须为 0
node tools/compat-drift.mjs

# 2) 动态：对真实 Host 跑只读探测矩阵，确认端点可用性与错误码语义
dsh web --no-open --port 3111 --host 127.0.0.1     # 输出里的 token 用于下一步
node tools/protocol-probe.mjs --base http://127.0.0.1:3111 --token <token>

# 3) 构建与单测
devecocli build
devecocli build --modules entry@ohosTest
devecocli run                                        # 设备侧：跑生效验证（POC-1 页面）
```

回写清单（缺一不可）：

- [ ] `docs/10-协议兼容事实基线.md`：更新 §0 版本、§8 附录（端点/错误码/实测矩阵）、未决问题状态；
- [ ] `docs/00-开发任务书.md` §11.4 版本兼容矩阵更新；
- [ ] `docs/30-技术验证清单.md`：受影响 POC 的结论重跑；
- [ ] 提交说明中逐条列出漂移报告的差异条目（便于回溯）。

## 3. 降级策略（上游移除能力时）

**原则：能力降级而非崩溃（D1 §5.2 原则 4）。**

| 场景 | 端侧行为 |
|---|---|
| 必需端点缺失（能力不可用） | 入口置灰 + tooltip 说明缺失端点与影响；不隐藏入口（避免用户困惑） |
| 可选端点缺失 | 功能局部降级（如缺少 `session/fork` 则隐藏分支入口），不提示错误 |
| 尚未探测（unknown） | **按可用处理**，不阻断；首次调用失败后再置灰（避免误判） |
| 骨架缺失 | 拒绝连接，明确提示「Host 版本过旧或不是 dsh Web 表层」 |

实现落点：`dshcompat` 的 `evaluateCapability()` 返回 `CapabilityState`（`present` / `missing` / `unknown`），
诊断页与各入口消费该结果。

## 4. 版本矩阵维护

`dshcompat/src/main/ets/CompatIndex.ets` 的 `SUPPORTED_VERSIONS` 是**受支持矩阵的唯一声明处**。

| 判定 | 条件 | 端侧行为 |
|---|---|---|
| `SUPPORTED` | 版本号在清单内 | 正常使用 |
| `UNVERIFIED` | 版本号不在清单内，但骨架端点齐全 | 可用 + 顶部常驻提示「Host 版本未经验证」+ 「查看详情」 |
| `INCOMPATIBLE` | 骨架端点（`session/list`、`session/create`、`session/prompt`）缺失 | 拒绝连接并给出升级建议 |

> 版本号判断只读**核心包** `@deepseek-ai/dsh` 的版本，不读外层打包包版本
> （本机外层 `deepseek-harness-pkg` 与核心包版本不同，混用会造成误判；见 D2 §0）。

**这一轮暴露的一个真实陷阱（值得记进流程）**：跑完第 3 步生成新上表后，
若**不同步刷新 `tools/compat-drift.mjs` 的默认契约快照** `.research/protocol/contracts.json`
（该文件自带 `.meta.json` 自报版本，见 §4 的「契约自描述」），门禁会把**新增**端点读成
**上游移除端点**并报「这些调用会返回 HTTP 404」——**方向完全相反**，且版本行显示旧版本号。

```sh
# 采集（第 1 步）之后，把新契约同时作为"当前基线"
cp .research/protocol/contracts-0.2.0-rc.1.json .research/protocol/contracts.json
cp .research/protocol/contracts-0.2.0-rc.1.json.meta.json .research/protocol/contracts.json.meta.json
node tools/compat-drift.mjs; echo "exit=$?"   # 期望 0，且版本行显示 0.2.0-rc.1
```

> 判别方法：报告里的「上游移除端点」若恰好等于你**刚刚在漂移报告里看到的新增端点**，
> 就是快照没刷，不是真的删除。**看到"删除"先怀疑基线，再怀疑上游。**

### 4.4 0.2.0-rc.2 的漂移（逐条判定）

| 端点 | shape | 流式 | 我方是否调用 | 处置 |
|---|---|---|---|---|
| `userQuestions/answer` | NAMED | 否 | 未调用 | 无 |
| `userQuestions/attachWait` | NAMED | **是（可取消）** | 未调用 | 无 |

> 全仓检索 `userQuestions` 字面量（排除 `node_modules` / `build` / `dist` / `oh_modules` / `.git`）
> **只命中契约 JSON 自身**，我方源码零调用 ⇒ 本轮只做「重生成上表 + 更新矩阵」，
> 不动任何调用代码与能力映射。这一轮同样踩到了 §4.3 末尾记的快照陷阱：
> 采集完 rc.2 契约后若不同步刷 `.research/protocol/contracts.json`，`compat-drift` 会把
> 上面这两个**新增**端点读成"上游移除"。处置与 §4.3 完全相同：

```sh
cp .research/protocol/contracts-0.2.0-rc.2.json      .research/protocol/contracts.json
cp .research/protocol/contracts-0.2.0-rc.2.json.meta.json .research/protocol/contracts.json.meta.json
node tools/gen-compat-endpoints.mjs            # 140 端点 / 13 流式 / 15 能力 / 86 未被能力引用
node tools/compat-drift.mjs; echo "exit=$?"    # 期望 0，版本行 0.2.0-rc.2
```

**本轮新增的一条流程事实（端侧特有，PC 侧没有）**：`entry/src/main/resources/resfile/` 下
**只能有一个** `dsh-core-*.zip`，且 HAP 打包**不按 `core-recipe.json` 的版本去挑 zip** ——
`entry/build-profile.json5` 的 `copyCodeResource` 直接拷 `resfile/` 里"实际躺着什么"。
全仓 `dsh-core-*.zip` 的消费者只有 `entry/src/ohosTest/ets/test/CoreDecision.test.ets:139`
的 `parseArchiveName`（纯测试解析）。⇒ **配方版本与 resfile 里的 zip 不一致时，构建会静默
嵌错版本，全程零报错**。故升级时必须显式：删旧 zip、放入新 zip、核对 sha256 与
`dist/core/<新 zip>` 一致，再用 `BOOT_10_ENV_READY core=…/<新版本>` 在真机上确证。

---

> **rc.2 这类升级的正确处置是"什么都不改"**。这条记录的价值不在于改了什么，
> 而在于它证明了**门禁能把"没变"和"变了但没看见"区分开**：
> 端点表逐条比对为 0 差异、类型声明的 sha1 差异只落在与我们无关的 8 个文件上、
> 另起 rc.2 Host 复跑探测得到逐字相同的结果（含两条负向证据）。
> 如果没有这三层证据，"没有漂移"就只是一句印象。

**触发方式**：本机 dsh 被桌面端自动升级，漂移门禁随即变红。这说明门禁的定位是对的——
它不是「升级时跑一下的检查表」，而是**常驻的失真探测器**。

**本次新增的工具能力**（都是被这次升级逼出来的，顺手补上）：

| 能力 | 用法 | 解决什么问题 |
|---|---|---|
| 版本间比对 | `DSH_CONTRACTS=<旧契约>.json DSH_VERSION=<旧版本> node tools/compat-drift.mjs` | 不动机器上的 dsh 安装，也能算出「A 版本 → B 版本差了什么」 |
| 跨版本生成 | `DSH_CONTRACTS=<目标契约>.json DSH_VERSION=<目标版本> node tools/gen-compat-endpoints.mjs` | 在旧机器上生成新版本的上表 |
| 契约自描述 | `protocol-contract.mjs --json out.json` 会同时写 `out.json.meta.json` | 契约文件本身不带版本号，下游工具只能靠「当前装了哪个 dsh」猜版本；跨版本操作时必然猜错。让采集者自报版本，下游就不再猜 |

> **教训**：`contracts.json` 曾是纯数组、无版本字段，于是 `compat-drift.mjs` 会把
> 「被比对的那份契约」的版本打印成「当前环境安装的那个版本」。
> 一旦用 `DSH_NODE_MODULES` 指向别的安装目录，报告里的版本行就是**张冠李戴**的——
> 而版本号是兼容判定的依据，标错会直接误导升级决策。现已改为优先读契约的自描述元数据。

## 5. 门禁的自我验证（必做）

漂移门禁是这套机制的地基。**每次修改门禁后必须做一次负测试**，证明它真的会失败：

```sh
# 备份 → 注入一处漂移 → 期望：非零退出 + 精确差异 → 恢复 → 期望：无漂移
cp dshcompat/src/main/ets/Endpoints.ets /tmp/Endpoints.bak
# 手工把某个端点的 shape 或 stream 标记改错（模拟上游漂移）
node tools/compat-drift.mjs; echo "exit=$?"     # 期望 exit=1 且列出该端点差异
cp /tmp/Endpoints.bak dshcompat/src/main/ets/Endpoints.ets
node tools/compat-drift.mjs; echo "exit=$?"     # 期望 exit=0
```

**这条纪律的由来**：本项目第一版 `compat-drift.mjs` 用「固定字段顺序的整行正则」解析生成物，
生成物的缩进/字段顺序一变就解析出 0 条 → 门禁恒报「无漂移」。
只有做了注入式负测试才暴露出来。**未被负测试验证过的门禁，等于没有门禁。**

## 6. 可选的 CI 集成

```sh
# 上游升级检查（在有 dsh 安装/checkout 的 runner 上）
node tools/protocol-contract.mjs --json .research/protocol/contracts.json
node tools/compat-drift.mjs   # 非零即失败，阻止把未同步的基线合入

# 门禁的负测试（CI 里也必须跑，否则门禁可能在悄悄失效）
DSH_CONTRACTS=.research/protocol/contracts-0.1.2-rc.1.json node tools/compat-drift.mjs \
  && { echo "门禁失效：对旧基线竟然报无漂移"; exit 1; } || echo "负测试通过（如期报出差异）"

# 架构回归检查（防止上游知识泄漏出 dshcompat）
# 期望：以下命令都无输出
grep -rnE "session/|settings/|workspace/|pluginInventory/" connection/src appstate/src entry/src/main/ets/view
grep -rn "sys.symbol" --include=*.ets connection/src appstate/src | grep -v dshcompat

# PC 侧搭桥服务（与主工程解耦，独立测试）
node --test hostkit/test/
```

> **负测试为什么必须进 CI**：本项目已经吃过一次亏——第一版门禁因解析 bug 恒报「无漂移」，
> 只有注入式负测试才发现。把负测试放进 CI 后，门禁**自己失效**也会被抓住，
> 而不是等到某次真实升级漏掉了端点才暴露。
