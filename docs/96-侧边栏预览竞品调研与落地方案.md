## 2. 真机事实

- 模块名：三者 `hapModuleInfos[0].moduleName` 都是 `electron`；ability 集合逐字相同（`BrowserAbility`/`EntryAbility`/`StatelessAbility`），
  extension 集合逐字相同（`BrowserEmbeddedAbility` type=21、`StatusBarEntryAbility` type=264）。同模板还见于 codearts.agent / mkcode / codex4hmpc / feishu_pc / wechat.pc / htbrowser。
- 自带引擎二进制：WorkBuddy 11 条 = electron + node/npm/npx/corepack + python3.12 + bash + editor_sdk；Qoder 2 条 = electron + qoder-context-rg；千问办公该字段为空。
- MIME：三者与 doc/docx/ppt/pptx/xls/xlsx/pdf/png/jpg/html/md/txt 相关的注册条目 **均为 0**；WorkBuddy 唯一与外文件有关的是 `sendData` + `scheme=file`（分享入口）。
- 权限：`ACCESS_USER_FULL_DISK` + `CUSTOM_SANDBOX` + `FILE_ACCESS_PERSIST` + `kernel.ALLOW_WRITABLE_CODE_MEMORY`/`LOAD_INDEPENDENT_LIBRARY`（WorkBuddy 另有 `ALLOW_EXTERNAL_NATIVE_CODE`）⇒ 指向"自带引擎 + 自己读盘"。
- 运行时（持久 hilog，`/data/log/hilog/hilog.*.gz`，shell 可读且 tag 首段即进程名）：WorkBuddy 15:29–15:31 出现 `Ace/electron/Electron/chromium/AceXcomponent/OHOS::RS/2DGraphics/LIBUV`，AMS 记录 `com.tencent.workbuddy_electron_EntryAbility_37522` ⇒ Chromium 在本进程内渲染到 XComponent 原生表面；磁盘 606.03 MB。
- 千问办公 / Qoder 在 1000 份持久日志窗口内**零出现**（该窗口未启动），运行时进程构成查不到。

**对照：真正走"系统打开方式"的**：系统预览宿主 `com.huawei.hmos.hipreview`（92 个 MIME + `PreviewUIService` type=269）、WPS `PromeAbility`（44）、Foxit（15）、360zip（19）、airnotepad（84）。

## 4. 落地方案（顺序即优先级）

> **2026-10-05 18:09 更新**：C 已由真机闭环 —— 根因不在客户端 abort、也不在 `[dshm-link]` 包装器，
> 而在宿主纯 JS undici 垫片 `hostcore/app/fetch-shim.js` 的 `DshmResponse`（不支持 `new Response(FormData)`）：
> 上游对**带附件的 RPC 结果**用 FormData 构造响应，`readBytes` 的 `Uint8Array` 必然走该分支 ⇒ 垫片把 FormData 原样交给 `bridge()` 的
> `for await/res.write` ⇒ `ERR_INVALID_ARG_TYPE` ⇒ 服务端 `res.destroy()`（一个字节未写）⇒ 客户端 `ERR_EMPTY_RESPONSE(-324)`。
> 时间线佐证：`b4bdcb5`（10-05 11:42 引入内部 undici 垫片）让 `globalThis.Response/FormData/Blob` 从 Node 原生实现变成垫片类；
> 最后一次成功 10-04 14:17、第一次空响应 10-05 12:27（该 commit 首次装机冷启动）。
> ⇒ **plan B（ArkTS `readFileAsDataUri` 同步桥）不做**：它只绕开 `readBytes`，而垫片这个洞会让**任何带附件的 RPC** 继续空响应。
> ⇒ 另记：此前的 `DSHM_DOC_LOAD_DEDUP`（面板自持 abort + 去重）治的是**不存在的病**，属无效补丁；
> 其中"失败后清去重键"一行位于 `if (started…) return` 之后，是**死代码**（失败后同键不会自动重试）。
> —— **已于 `coreVersion` +dshm.6 整段撤除**（`tools/pack-core.mjs` 的注入函数与调用点已删，并加了"撤除守卫"门禁，见 `docs/97`）。

**C（先做，零代码）**：验证 `readBytes` 是否已随补丁修好。
步骤：打开 `common/sample.png`、`sample.pdf`、`sample.xlsx`、`common/sample.html` 各一次；
读数：`dshm-host.log` 里 `workspaceFiles/readBytes` 的 请求/成功/取消。
判据：取消 = 0 且 成功 = 请求。

> **2026-10-05 收尾：C 已完成，且落法与本段原设想不同（以代码为准）。**
> 真机读数 `152/3/149 → 153/4/149`（成功 +1、取消零增长；`sample.html` 作为预览标签**直接内联渲染**，
> 详见 `docs/97` §4）。原设想的"把插件 `loading` **按类型分档**改回 `bytes-complete`"**没有采用**：
> 实际做法是把插件的**认领收窄为 Office-only 9 项**
> （`hostcore/plugins/dshm-office-system-preview/lib/client.js:79-93` 的 `EXTENSIONS`），
> 图片 / PDF / HTML / 表格 / SVG 交回**上游内联渲染器** ⇒ 插件不再需要按类型分档，
> 其 `loading` 依旧是 `"text-pages"`（`:359`；因为插件正文本来就不渲染文件内容）。
> 于是"谁能内联"与"插件的 loading"**解耦**：内联由上游渲染器负责，插件只负责 Office 的「系统预览」按钮。

**B（C 不成立时）**：ArkTS 壳加 `readFileAsDataUri(path)` 同步桥（挂既有 `__DSHM_BRIDGES__`），范围限定 png/jpg/jpeg/gif/webp/bmp/svg/pdf/html/htm；
Office 与 `md` 维持现状。风险：base64 内存膨胀；ArkWeb 内置 PDF 在 2in1 的 syscap 需实测。

**A（保底）**：维持「系统预览」按钮；已做的 R3 使其不再有必然失败的类型。

## 5. 方法学坑（复现时必读）

- `ps` 的 STIME 比真实时间**慢 3h52m45s** ⇒ 进程启动时间用 `stat -c '%y' /proc/<pid>`。
- `bm dump` 的 stdout **不能在设备侧重定向**（0 字节、退出码 0）⇒ 宿主侧捕获 Buffer。
- 持久 hilog 是二进制且 shell 可读，`hilog -x` 才是 dump；tag 首段即进程名，可当"进程台账"用。
- HAP 内容与 el2 数据对 shell（uid=2000）不可读 ⇒ 竞品的实际渲染实现无法阅读，本文档对"千问办公用哪个 Office 渲染库"如实标注为查不到。
