# 技能：ArkTS 运行时崩溃修复

**适用场景**：ArkTS/JavaScript jscrash、运行时崩溃、未捕获异常、堆栈跟踪、faultlog、hilog 诊断；应用闪退/崩溃/白屏、点击/启动/启动后退出、构建成功但运行时失败。

**自动触发条件（满足任意一条即应主动阅读本文件）**：
- 运行时崩溃、闪退、白屏、启动后退出、点击后退出。
- 用户提供 jscrash、faultlog、hilog、堆栈跟踪或未捕获异常文本。
- 构建成功但运行行为异常，需要从设备端日志或崩溃锚点定位根因。

---

## 1. 核心方法

**优先获取具体崩溃锚点**，再进行广泛的代码探索。好的锚点来源：

- 用户提供的崩溃日志
- 堆栈跟踪
- 用户明确指出的页面或模块
- 设备端最近的 faultlog 或 hilog

**避免在没有锚点时**广泛执行 `Read` / `Glob` / `Explore`。

## 2. 常见崩溃特征

| 特征 | 典型原因 | 首要修复方向 |
|------|---------|-------------|
| `TypeError` 属性访问 | 渲染或生命周期中 null/undefined 状态 | 防护 null 状态，提前初始化，移至更安全的生命周期 |
| `ReferenceError` | 错误作用域、过期导入、缺失符号 | 修复符号所有权、导入路径或回调捕获 |
| `RangeError` | 无效索引、递归循环、越界访问 | 添加边界检查、打破循环、限制索引 |
| `BusinessError` / `ParameterError` | 框架 API 前置条件未满足 | 验证参数、权限或调用时机 |

## 3. 诊断流程

### Case A：用户已提供原始崩溃文本

1. 解析崩溃日志提取错误类型、错误信息、嫌疑文件、堆栈
2. 聚焦应用代码帧，忽略框架噪音
3. 将第一个具体的 `.ets`/`.ts`/`.js` 路径作为起点
4. 信任用户给出的复现步骤

### Case B：用户提供日志文件路径

1. 解析日志文件
2. 同 Case A 后续步骤

### Case C：仅有症状，无日志

1. 读取 `AppScope/app.json5` 获取精确 `bundleName`
2. 不要从 `vendor`、模块文件夹名或前缀猜测 `bundleName`
3. 确定目标设备：
   - 有 `deviceId` 则使用
   - 无则列出设备
   - 多设备时让用户选择
   - 无设备时报告无法收集设备端证据
4. 用户复现后收集 faultlog 或 hilog
5. 解析获取锚点

## 4. 崩溃分析解读规则

- **优先应用帧**，而非框架噪音
- 第一个具体 `.ets`/`.ts`/`.js` 路径是起点，不是最终结论
- 用户给了复现步骤时，信任它们胜过简化的堆栈推断
- 堆栈指向非入口页时，假设是交互触发路径，除非证明是冷启动崩溃
- **不要广泛重构**，先修复崩溃路径

## 5. 修复约束

- **禁止**仅凭提示推理声称修复了崩溃
- **禁止**用重试、任意延迟或广泛防御性重写替代根因修复
- 涉及不熟悉的 `@ohos.*` 或 `@kit.*` API 时，先查约束再编辑
- **禁止**使用 `setTimeout`/`sleep`/人工延迟作为"修复"
- **禁止**在后修复日志证明成功前移除仪表代码

## 6. 对话形态

1. 说明你已有什么证据
2. 如果缺少日志，说明正在使用 faultlogger 还是 hilog 获取更好的锚点
3. 一旦有锚点，切换到聚焦的代码阅读和最小修复

## 7. 与其他规则的边界

| 场景 | 使用规则 |
|------|---------|
| ArkTS 语法限制，无 UI 组件关注 | `skill-arkts-standards` |
| 编译报错、构建失败后的类型错误 | `skill-arkts-error-fixes` |
| ArkUI 组件、布局、状态装饰器 | `skill-arkui-knowledge` |
| ArkTS 项目调试工作流（含日志插桩） | `skill-arkts-debug` |
| 需要设备连接、启动应用、采集 HiLog、bugreport | `skill-device-hdc-debug` |
