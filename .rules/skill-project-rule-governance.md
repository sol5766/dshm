# 技能：项目专属规则、Harness 与个人偏好治理

**适用场景**：Agent 在 NGF 工程或使用 NGF 的应用工程中，需要建立、读取、提炼、更新或复核项目专属规则、执行 Harness、用户长期偏好或架构决策时使用本技能。

**自动触发条件（满足任意一条即应主动阅读本文件）**：
- 用户要求创建、维护、沉淀、复用或审查项目规则、Agent Harness、工作流或个人偏好。
- 用户表达持续性偏好或约束，例如“以后都……”“本项目统一……”“我偏好……”“不要再……”。
- Agent 发现已验证的项目模式、重复出现的约束、跨会话恢复需要，或需要创建/更新 `.agent-rules/`。
- 新建、接手、迁移或长期维护使用 NGF 框架的应用工程。

---

## 1. 目标与规则分层

规则必须按作用域保存，不能把一次性判断、机器路径、个人偏好和 NGF 共享契约混写在同一份文件中。

| 内容 | 目标位置 | 是否默认提交 | 是否自动成为强制规则 |
|------|----------|--------------|----------------------|
| NGF 框架跨项目契约、ArkTS 硬约束、通用技能 | 根目录 `AGENTS.md`、`.rules/` | 是 | 是 |
| 某个 App 的架构、产品边界、集成方式、验收标准 | `<app-root>/AGENTS.md`、`.agent-rules/project-rules.md` | 是 | 仅 `active` 条目 |
| 用户在该工作区的长期、非敏感偏好 | `.agent-rules/preferences.local.md` | 否 | 是，但不能覆盖高优先级规则 |
| 当前机器、SDK、设备、命令实测事实 | `.local-rules/*.local.md` | 否 | 仅环境事实范围 |
| 当前任务进度、未完成验证、阻塞信息 | `.agent-state/<task-id>.local.md` | 否 | 否，只用于恢复 |
| 未验证或仅出现一次的推测 | `.agent-rules/project-rules.md` 的 `candidate` 区 | 是 | 否 |

当前用户明确指令始终优先。个人偏好不能覆盖安全要求、HarmonyOS 官方约束、NGF 框架契约、已确认的项目架构或当前用户的相反指令。

---

## 2. 规则收集与分类

Agent 必须先判断信息是否值得持久化，再选择正确落点。不要把每次对话、每条日志或单个代码样本都变成长期规则。

| 信息来源 | 处理方式 |
|----------|----------|
| 用户明确表示持续适用，且范围清晰、非敏感 | 自动写入 `active` 项目规则或本地偏好，并在交付中说明。 |
| 当前任务限定的临时要求 | 只保留在当前任务检查点，不持久化为规则。 |
| 配置、代码、官方文档可直接验证的项目事实 | 写入 `active` 项目规则，并附上准确来源和复核方式。 |
| 两处及以上相互独立、已成功验证的同类项目模式 | 可提炼为 `active` 项目规则，并记录至少两个证据来源。 |
| 单次实现、猜测、临时绕过、未复现问题 | 仅记为 `candidate` 或任务状态；不得强制执行。 |
| 本机 SDK、路径、设备或命令结果 | 写入 `.local-rules/*.local.md`，不得写入项目规则。 |
| 对多个 NGF 使用方都有效的规律 | 不得自动写入根 `AGENTS.md` 或 `.rules/`；在交付中说明证据，并由开发者显式触发 `skill-rules-update.md` 流程。 |

收集个人偏好时，仅保存会影响后续实现选择的清晰偏好，例如语言、命名、交付粒度、验证偏好、UI 风格或技术取舍。不得保存身份信息、联系方式、账号、密钥、健康/财务信息、私密业务数据，或用户未表示希望长期保留的敏感内容。

## 3. 项目 Harness 初始化与文件格式

当用户明确创建或长期维护一个 App，且 App 根目录已确定时，Agent 可以在该根目录自动初始化下列最小 Harness；创建前先检查目标是否已存在，合并已有内容，禁止覆盖用户已有规则。

```text
<app-root>/
  AGENTS.md
  .agent-rules/
    README.md
    project-rules.md
    preferences.local.example.md
  .agent-state/                 # 本地任务检查点，忽略提交
```

如果 App 使用本仓库的 NGF 源码，初始化模板位于 `.rules/templates/ngf-app-agent-harness/`。若 App 位于独立仓库，Agent 应把模板内容复制并替换占位符，而不是引用一个将来不存在的相对路径。

每条项目规则必须短、原子、可执行，并使用下列格式：

```markdown
### PR-001 规则名称

**状态**：active / candidate / deprecated
**范围**：适用模块、页面、功能或交付场景
**指令**：满足什么条件时必须做什么；不适用时的边界是什么。
**来源**：用户长期指令 / 配置文件 / 已验证源码路径 / 官方文档。
**证据**：精确文件、命令结果或至少两个已验证模式。
**验证**：完成任务时如何检查该规则仍被遵守。
**更新时间**：YYYY-MM-DD
```

`candidate` 条目只能帮助后续调查，不能约束实现。`deprecated` 条目保留变更原因，不能继续执行。发现同类规则时优先修订已有条目，不得无止境追加近义规则。

## 4. 强制读取与执行流程

只要当前项目存在 `.agent-rules/`，Agent 在读取或修改目标源码前必须执行以下流程：

1. 读取当前项目及父目录链中适用的 `AGENTS.md`。
2. 读取 `.rules/README.md`，并完整阅读本任务命中的技能文件。
3. 读取 `.agent-rules/README.md`、`project-rules.md` 中全部 `active` 条目，以及存在时的 `preferences.local.md`。
4. 形成“有效规则记忆”：列出本任务实际适用的项目规则、个人偏好、NGF 框架约束和可验收条件。
5. 实现、复核和交付前都回看该记忆；规则冲突时按优先级解决并记录理由。

发生上下文压缩、中断、交接、目标切换或用户新增要求后，必须重新读取有效规则并重建规则记忆。仅凭聊天摘要、过期检查点或文件名猜测不得继续执行。

当 Agent 在任务中发现符合第 2 节条件的新规则时，应在完成验证后更新正确的规则文件，并在交付中说明：新增或修订了什么、证据是什么、后续会在哪些任务中生效。用户明确要求不持久化时，只在当前任务遵守，不写入任何规则或偏好文件。

---

## 5. 冲突、降级与防止规则膨胀

按以下顺序处理冲突：当前用户明确指令 -> 安全、法律与官方平台要求 -> 更深层 App `AGENTS.md` -> 根目录 NGF `AGENTS.md` 与命中 `.rules/` -> `active` 项目规则 -> 本地个人偏好 -> `candidate` 和任务笔记。

- App 专属规则不得把 NGF 框架改造成单一业务 App，也不得绕过其公开契约或安全边界。
- 不得因偏好或历史代码而跳过必要验证、忽略编译/运行任务中的实际错误，或修改用户未授权的范围。
- 不得为了“收集规则”额外执行构建、设备操作、网络访问或大规模重构；收集工作必须复用当前任务已有的证据。
- 每次任务结束时，只回顾与本次任务直接相关的候选规则。没有足够证据就保持 `candidate` 或删除无价值笔记，不得制造空泛口号式规则。
- 当现有 `active` 规则被新证据推翻时，更新为 `deprecated` 并写明替代规则和原因；不得静默删除导致行为变化的规则。

---

## 6. 交付前检查

- [ ] 已读取并应用所有 `active` 项目规则和适用的本地偏好。
- [ ] 新规则有明确范围、指令、来源、证据和验证方式。
- [ ] 未把机器事实、敏感信息、一次性决策或未经验证猜测升级为强制规则。
- [ ] 未自动修改共享 `.rules/` 或根 NGF `AGENTS.md` 来承载仅属于某个 App 的规则。
- [ ] 已说明本次新增、修订、保留为候选或拒绝持久化的规则结论。
