# 技能：NGF 新应用启动与项目 Harness

**适用场景**：用户希望基于 NGF 框架新建、迁移、拆分或长期维护一个独立 App、应用模块或产品原型时使用本技能。

**自动触发条件（满足任意一条即应主动阅读本文件）**：
- 用户提出“用 NGF 做一个新 App”“新建应用”“基于 NGF 搭建产品”“迁移现有 App 到 NGF”。
- 需要为新的 App 根目录、新模块、独立产品仓库建立 Agent 规则、项目 Harness、产品边界或长期执行约束。
- 当前任务从 NGF 框架验证工程扩展为面向具体应用的功能、页面、数据或发布设计。

---

## 1. 启动原则

NGF 是核心运行框架和框架验证工程，不应因为创建一个具体 App 而被改写为该 App 的业务实现。新 App 默认应拥有独立的应用根目录或明确的应用模块边界；只有用户明确要求时，才在当前 `entry` 验证模块中实现应用功能。

启动前必须先确认：

1. App 根目录或模块边界，以及它与当前 NGF 仓库的关系：同仓库独立模块、同仓库演示页、独立消费者仓库，或迁移目标。
2. NGF 的接入方式：本地 HAR、版本化依赖、源码模块或仅参考框架模式。
3. 用户已确认的产品目标、目标设备、首要用户流程、数据/网络边界、语言、设计方向和交付范围。
4. 哪些信息仍未确认。未确认项写入“开放决策”，不得伪装成项目规则或业务需求。

若用户只描述了功能目标，Agent 可以作最小、可逆的产品假设并在第一次交付中说明；涉及包名、数据收集、账号体系、支付、外部服务、发布渠道或不可逆架构选择时，必须先获得用户方向。

---

## 2. 建立 App 专属 Harness

在用户已授权创建 App 或应用模块的范围内，先建立或补全下列文件，再开始大范围功能实现：

```text
<app-root>/
  AGENTS.md
  .agent-rules/
    README.md
    project-rules.md
    preferences.local.example.md
  .gitignore                         # 忽略 .agent-state/ 与 *.local.md 偏好文件
```

使用 `.rules/templates/ngf-app-agent-harness/` 作为起点，并按目标 App 的实际结构替换占位符。存在同名文件时，先读取并增量合并；禁止用模板覆盖用户已有的 `AGENTS.md`、规则、偏好或 Git 忽略项。

Harness 建立完成后，`AGENTS.md` 必须要求后续 Agent：

- 在读取或修改源码前，读取 `project-rules.md` 的全部 `active` 条目和存在时的本地偏好。
- 在上下文恢复、目标切换或新增报错后重新读取有效规则。
- 使用 NGF 已公开的 facade、contract、starter、uiShell 与资源能力；先查真实导出和相邻源码，再决定是否扩展框架。
- 将产品专属判断留在 App 规则中，不把它们反写为 NGF 框架默认行为。

`skill-project-rule-governance.md` 是本 Harness 的规则收集、升级、降级和执行依据，必须在创建 Harness 前完整阅读。

## 3. 初始项目规则的最小集合

只写已经确认或可直接验证的内容。以下领域应逐项检查，缺失信息写为开放决策，而不是猜测：

| 领域 | 需要记录的项目专属信息 |
|------|------------------------|
| 产品边界 | 目标用户、核心场景、明确非目标、首个可交付范围。 |
| 架构边界 | App 层职责、NGF 接入点、禁止直接依赖的内部实现、模块所有权。 |
| UI 与内容 | 设计语言、导航方式、品牌资源、无障碍、i18n 语言与文案所有者。 |
| 数据与隐私 | 本地存储、网络来源、账号/权限、敏感数据处理和离线要求。 |
| 质量门槛 | 哪些变更需要静态复核、构建、设备验证或人工验收；保持根规则的默认“不自动构建”原则。 |
| 交付偏好 | 变更粒度、日志要求、文档要求、是否需要测试清单或截图。 |

一条规则必须能回答“在什么范围内、遇到什么条件、Agent 应做什么、如何检查”。例如“UI 要好看”不能作为规则；“设置页沿用 HDS 导航壳和项目定义的三种语言资源，新增用户可见文本必须补齐对应资源”可以成为可验证规则。

## 4. 与 NGF 框架的协作边界

- App 层新增能力前先读取 `skill-component-reuse.md`，优先复用 `ngf_framework` 公开导出；不能仅因现有 API 不熟悉就手写平行能力。
- 需要更改 NGF 框架时，先说明该能力是否能服务多个 App；若仅服务当前产品，应优先留在 App 层。
- App 的业务文案、页面流程、品牌资源、后端协议和产品偏好不得进入 `ngf_framework` 的共享层，除非用户明确要把它设计为框架通用能力。
- 涉及 ArkTS、ArkUI、HDS、窗口、系统任务、主题、语言或发布时，继续按 `.rules/README.md` 自动命中并阅读领域技能；App Harness 不能取代这些技术规则。

---

## 5. 执行闭环与交付

每项应用功能都遵守根 `AGENTS.md` 的轻量 Harness：`评估 -> 实现 -> 验证 -> 完成`。在评估阶段写明适用的 App 规则和验收条件；在实现和验证阶段确认它们没有被绕过；在交付时说明本次是否新增、更新或拒绝沉淀项目规则。

对于跨会话的 App 开发，可使用 `.agent-state/<task-id>.local.md` 保存任务检查点；该文件仅用于恢复，不构成产品需求或强制规则。重复失败且没有新证据时，遵守三次上限，停止空跑并报告阻塞条件。

## 6. 初始化检查清单

- [ ] 已确认 App 根目录、NGF 接入方式和用户授权范围。
- [ ] 已建立或合并 App `AGENTS.md` 与 `.agent-rules/`，未覆盖既有用户规则。
- [ ] 已区分已确认规则、个人偏好、机器事实、开放决策和候选模式。
- [ ] 已保留 NGF 框架与具体 App 的职责边界。
- [ ] 已明确本次是否执行构建、运行、设备验证或仅静态复核。
